# 格式杂乱聚合文档的标准处理工作流（SOP）

> 适用范围：源 markdown 为**整段粘连 / 无条目边界**的聚合文档（判别器 est 正确、但切分失败 got=0 或 ≪est）的规范重建。
> 首个落地案例：专长 R1 三聚合文件 HTML 重建（2026-08-01，PR #6，42 条目，est↔got 15/15、14/14、13/13）。
> 前身雏形：`docs/未整理目录HTML回退处理记录.json`（亡灵杀手手册整理期，2026-07-18）。
> 与 `docs/WORKFLOW.md` 的关系：本工作流是「审计 → 分类 → 修复 → 验证」迭代中**修复类目下的一类标准路径**（聚合文档重建），复用时按 WORKFLOW.md 通用约束执行（每步提交 Git、类目无关、设计变更用户拍板）。

---

## 一、触发条件（判定清单）

同时满足以下 3 条，即判定为「格式杂乱聚合文档」，走本工作流：

| # | 信号 | 判定 |
|---|---|---|
| 1 | 判别器 `fc_deviation_matrix.json` 对账失败：该 rel `est > 0` 但 `got = 0` 或 `got ≪ est` | est 对不上 |
| 2 | 源 markdown 打开后是**整段粘连**：无 `**` 条目级标题、无字段标签，或仅按节名拆出极少数 chunk | 结构缺失 |
| 3 | 判别器 est 与**原始 HTML 条目数一致**（数一遍能数出来） | 识别正常 → 是切分问题，不是识别问题 |

> 判别方式：先看文件内容确认「无边界」，再回 HTML 数条目数核对 est。若 est 与 HTML 数不符，属识别问题，走 WORKFLOW.md 常规迭代，不走本流程。

## 二、处理流程（6 步主线）

```
问题文档 ──① 文档头溯源──▶ 源 markdown ──② 定位──▶ 源 HTML
                                              │
                                              ▼
                                          ③ 可行性判断 ──可操作──▶ ④ 生成规范文档
                                              │                          │
                                       不可操作（分支见 §三）              ▼
                                              │                    ⑤ 产 chunk 块
                                              ▼                          │
                                  回源 md / 豁免登记 / KN                  ▼
                                                               ⑥ 验收 + 登记物
```

### 步骤 0 · 问题文档（输入）

聚合页 / 判别器对账失败的 rel。特征：从其他页面切出的单独规则书页，内容为一段段专长/法术/物品描述粘连在一起。

### 步骤 1 · 文档头溯源 → 定位源 markdown

- 读文档头注释 `<!-- <来源>-source:<page>.md:<zh>(<en>) -->`，拿到来源页面名 `page_xxx`。
- 无注释时按 `未整理 → <书> → <模块>` 的路径线索定位。
- **产物**：来源页面名（如 `page_547`）。
- **分支**：若 `pf_rules_md` 下存在同名源 markdown 且已结构化 → 直接复用/微调，跳过 HTML（最小动作原则）。

### 步骤 2 · 定位源 HTML

- 源页面 HTML：`~/.openclaw/workspace/pf_rules/page_xxx.html`。
- 粗转 HTML → 文本：`BR→\n`、`STRONG→**`、`EM→*`、去其余标签、`gb18030`（兜底 utf-8）解码。
- 人工阅读提取：① 完整条目名清单（zh / en 各一）；② 非条目区位置（变体 / 血脉 / 法术 / 章节标题）。

### 步骤 3 · 可行性判断（决策门）

见 §三。**可操作** → 步骤 4；**不可操作** → 走退化分支。

### 步骤 4 · 生成格式规整的文档

1. 写重建脚本（模板要点见 §四），条目名清单**人工核对**后写死进脚本。
2. 产出 draft → **人工核对**（条目数 / 字段完整 / 无混入）→ 确认无误后复制为正式源文件。
3. 产物格式对齐既有模板（如反派法典 VC）：`<!-- <来源>-source:<page>.md:<zh>(<en>) -->` + `**中文（English）**`（标题尾双空格）+ `> 来源：…`（通道 1 来源解析优先，逐字保留）+ `*描述*` + `**字段：**值`。

### 步骤 5 · 处理生成 chunk 块

```bash
cd pf_data/phase1
bash regen_feat_chunks.sh        # 单入口：pipeline → 四后处理 → pytest → verify（同类目模块换对应 regen 脚本）
```

- ⚠️ regen 脚本 Step 2 内含四后处理脚本（apply_chm_toc_mapping → apply_feat_creation_source_promote → backfill_chm_toc_path → backfill_feat_source，**顺序不可变**，2026-08-03 补齐）——重生成会重置 book/source/toc 产物，**禁止绕过**（教训 B1 二度回归）；CI 闸口（`.github/workflows/ci.yml`）与本地脚本同链路。
- 对照判别器：该 rel 的 `got` 应与 `est` **精确匹配**。
- chunk 总数变化应能解释（+N = 重建条目数 − 原粘连误产），不构成静默扩量。

### 步骤 6 · 验收 + 登记物

- `verify_feats.py` 五检查全绿：判别器回归（静默丢失 0）、召回、字段健康、R5 probe、title 合法；pytest 全绿。
- 同步登记：
  - 豁免文档 `docs/state/feat_exemptions_20260801.md`：撤销已解决的豁免（6→3），更新 k2.7 等待确认项。
  - 交付文档（如 `docs/专长/三聚合文件HTML重建_交付_20260801.md`）：来源、条目数、关键处理点、验证数据。
  - 若涉审计：在审计结论文档追加「已解决」注记。
  - memory：更新对应 memory 文件 + MEMORY.md 索引。
- **每步提交 Git**（WORKFLOW.md 通用约束）。

## 三、可行性判断决策门

判断标准：**能否机械地按 HTML 信号重建出「规范条目」**——即 ① 条目名可枚举（zh/en 能对齐）；② 字段边界可截断；③ 非条目区（变体/血脉/法术/章节）可过滤。

| 情形 | 判定 | 处置 |
|---|---|---|
| HTML 条目名完整、字段结构可识别、非条目区可正则拦截 | ✅ 可操作 | 步骤 4 重建 |
| HTML 也杂乱 / 纯散文（无条目名、无字段标签） | ❌ 不可操作 | 豁免登记（verify 豁免表，不阻断）；确属未整理页登记 KN |
| 源 markdown 已有部分结构（部分条目有 `**` 标题） | ⚠️ 优先 md 层面 | 改源 markdown 手动补边界，不动 HTML |
| 涉及设计/口径变更（如多份取主版本、新形态） | 🛑 需用户拍板 | 按 WORKFLOW.md「设计层面修改需用户拍板」提交问题+方案 |

> 铁律：**禁止在通用 pipeline 里硬编码 `if 书名 == "X"` 做业务特判**（全局规范）。重建走数据层面（改源文件/建脚本），不动 `formats/*.py` 的通用逻辑；确实需要动解析器时，先登记结构不变量并在 verify 加断言。

## 四、重建脚本模板要点

参考实现：`docs/专长/build_feat_md_aggregate_rebuild.py`（可复算）。新场景复用其骨架，替换 4 处：

| 部件 | 要点 |
|---|---|
| `coarse()` | HTML 粗转（BR/STRONG/EM/gb18030），逐行 strip、去空行 |
| `ENTRIES` | 条目名清单（zh, en）**人工核对**后写死；兼容全角/半角括号变体 |
| `split_entries()` | 去星后**行首匹配** zh 定位条目起始行（避免命中正文引用）；块结束=下一标题行 |
| `parse_entry()` | 规范化加粗标点；`FIELD_PAT` 字段边界 + `SECTION` 非条目区边界（**按场景扩展**：变体/血脉/法术/章节标题/种族专长）；字段值**折叠为单行**（防 M6/M9 把续行误判成幽灵标题）；描述 EM 优先（要求换行前导，避免吞 `**标题**` 第二个 `*`） |
| `build_md()` | 对齐 VC 模板（source 注释 + 标题尾双空格 + `> 来源：` + `*描述*` + `**字段：**值`） |

关键坑（必查）：

- **字段值多行折叠**：源 `<BR>` 在英文术语/句子中部断行，保留换行会让续行（中文开头+英文括号）被 `formats` 的 M6/M9 裸中英行逻辑包成幽灵条目 → 字段值 `re.sub(r'\s+',' ',val)` 折叠单行。
- **非条目区残留**：变体/血脉/法术等章节若未拦截，会混入上一条目字段值 → `SECTION` 正则覆盖该场景。
- **多页合并**（如同一本书分两页）：每页独立 split，按页面顺序组装，来源注释用各自 page。
- **判别器矩阵只读**：`fc_deviation_matrix.json` 只读不改，回归按全量 rel 对账。

## 五、验收与登记物清单

```text
□ 重建脚本入仓（可复算，输出 _rebuild_draft/ 待核对）
□ 正式源文件就位（条目数与 HTML 一致）
□ regen 单入口 EXIT=0：chunk 总数变化可解释
□ pytest 全绿
□ verify 五检查全绿：判别器回归 est↔got 精确匹配、静默丢失 0
□ 豁免文档同步（撤销已解决 / 新增登记）
□ 交付文档（来源/条目数/关键处理/验证数据）
□ 审计结论注记（如涉审计）+ memory 更新
□ Git 提交（每步）+ PR（draft，独立分支避免污染原 PR）
```
