## 一、开工前机制（Prepare 阶段）

### 1.1 先判形态——词条型 vs 章节型（第二形态模板）
① **内容**：规则模块是**第一个章节型模块**——chunk 单元 = 语义节（一节规则 1 chunk），无字段体系；词条型（法术/职业/专长/装备/种族/背景/技能）的单条目 = 1 chunk + 字段体系 + field_status 三态。形态判定直接决定：chunk 粒度 / 是否建字段词表 / verify 检查结构（章节型不查字段健康、改查 toc_group 值域）。
② **落地**：**新模块（怪物=数据块词条型、规则书新主题=章节型）开工第一个问题：这是词条型还是章节型？**——章节型模板 = 语义节分派（§2.1）+ 表格跟随（§2.2）+ 无 field_status + 判别器 est 口径声明（§1.1 延伸，章节型 est 粗估漂移大，见 §3.1）。

## 三、产出/修复时机制

### 3.1 oversize 递归切分——阈值单向下传（KN203 死循环调试）
① **内容**：全量首跑 80 个 chunk > 5000 → `_oversize_split`（split_into_items 全出口统一包裹）+ `_split_oversize_body`：非表格超限按段落级（`\n\n`）累积切分 → 无段落边界行级（`\n`）→ 段级切出超限段递归行级再拆；续块 title = `原title（续N）`；**阈值统一 `thr = limit - allowance`，递归只随链首下传——否则区间 [limit-allowance, limit] 的块被递归体全收形成无限递归**（Spell UI 4 行 4723 案例死循环调试）；表格 chunk（text 首行 `|`）不拆、`|` 行独立成段保护、min_tail 并入逻辑删除（数学上恒不触发）。结果 80 → 7 残留全定性（TDD 8 测试）。
② **落地**：**递归切分/清洗的阈值必须单向下传**（父调用计算，子递归继承，禁止子递归重算）——死循环调试教训（装备 §2.4「守卫可达性」同族：不是有逻辑就行，是逻辑挂载/传递方式决定行为）；残留 7 全定性 = 超长单行无界 4 + 预拆后超长表行 1 + 整表 1 + 标题行混合正文 1（结构锚不可拆）。
