## 3. 工作流（对齐种族模块 #97~#101 先例）

1. **移动纳入**：9 个文件 `git mv` 到 §2.1 目标位置（移动不复制——根目录副本清理是 KN077 另立任务，本任务移动后根目录不再有这 9 个文件；注意逐字节保持行尾，git mv 天然安全）

3. **人工门 1**：格式簇判定 + est 对账 + §4 去重策略，一次性交付人工确认

6. **产出即检三件套** + 判别器对账 + `python3 -m vectorizer.verify.verify_races` + `python3 -m vectorizer.cicd verify --category race` 全链
7. **交付**：对账报告更新 + KN107 状态更新 + 交付文档（附复算命令），交 k3 审计立项复核

## 4. 去重策略（原则 + 先例，具体方案勘探后定）

**原则**：数据层保真不硬删，重复在检索端消解（KN093 feat_index/fe 先例）；但若两段内容**完全同源同文**（page_18 的「双重天赋」vs 汇总文件的「双重天赋」），允许在勘探后由人工门拍板二选一：

- 选项 A：9 页全量切分，重复 chunk 保留，登记 KN（检索端按 title 去重优先汇总文件——汇总文件来源标注更全）
- 选项 B：9 页的替换特性段在 normalize/勘探阶段标记跳过（doc_role 排除），只切介绍段+标准特性+FCB 段
- **红线**：不得静默丢弃——无论选哪个，丢弃/保留的条目数必须进判别器对账（est 定性）

**FCB 段的 race_name 语义**：既有 fcb_entry 的 `race_name` 填的是职业名（抽查发现，如「审判者」）。9 页 FCB 段按页归属种族填 race_name（页级种族名从目录/页标题取），修复方案随元数据设计一并过人工门；既有 3 个错位的 `人类天赋职业奖励` chunk 是否一并修正由人工门定。
