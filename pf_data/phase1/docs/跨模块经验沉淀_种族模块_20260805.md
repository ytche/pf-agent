## 一、开工前机制（Prepare 阶段）

### 1.1 Prepare 三闸口——机器基线失效时的真相来源
① **内容**：机器正则基线对复杂语料失效是常态（race 6 类标题形态 RE_TITLE_CAND 全测不到，101/112 文件同向偏差），但「逐字普查 census + 自包含闸口 firstlast + 幻影三分类人工取证 phantom」把偏差收敛为「零虚构」的确定性结论（phantom 42 = 39 in_own_file + 2 invented + 1 cross_file，人工取证全为表达差异）。
② **落地**：新类目开工第一件事跑三闸口（`python3 -m vectorizer.prepare.{census,firstlast,phantom} --category <新类目>`），只需注册 `--category` 语义表；勘探交付必须附三闸口执行记录。

### 1.2 人工确认门全流程——钳形结构，决策成本一次付清
① **内容**：大任务拆成「k3 交接文档（诊断已定 + 逃生舱协议 + 数字红线 + 验收红线）→ 执行模型勘探 → 人工门 1 交付五件套（格式簇判定 / est 对账（每页 count_basis）/ 去重策略 / 基线评估 / 风险核查）→ k3 **不信任声明、独立复算**（文件系统/资产行数/est 算术/chunk 数据，非核对交付）→ 修正落地 → 才进 TDD」。
② **落地**：交接文档模板直接复用护栏清单（E1~E5 编号延续：结构严重不符 / 重叠率不符 / 无法定性的偏差 / 需改既有基线 → 停工上报）；交付时逐条自查打勾。

### 1.3 勘探簇分配表三合一 + 判别器矩阵 + 召回基线双资产
① **内容**：`format_cluster_assign.json`（文件 rel → 簇 ID）同时驱动①输入范围过滤②format_cluster 元数据③簇感知映射（D 簇 sidebar→monster_block）——一份 JSON 三种用途，杜绝三份清单漂移；待定簇 X 前缀在 processor 归一（`_CLUSTER_NORM`：X_race_full→A 等）。machine_scan.jsonl（判别器矩阵：doc_role/est/count_basis/traps/dedup_note 每文件一条）与 audit_baseline.jsonl（权威召回基线）是后续一切对账的事实源——**锚定文件，不锚定「文档里的数字」**。
② **落地**：新类目建「勘探簇 ID → 定稿簇」归一表；簇感知映射只允许按簇值做，禁止按文件名单个特判。

### 1.4 范围复算 + pipeline 真实输入对账
① **内容**：输入范围类问题一律先跑 `audit_chm_scope_gap.py` 定性「输入缺口 vs 解析缺口 vs 源数据缺口」再修——KN118 神裔血统定性反转（非输入缺口而是 mega chunk 未拆分）证明该前置的价值；KN107 教训：**pipeline 真实输入是 organized/根目录子树全量，不是勘探清单快照**（page_195 不在专长勘探清单却产出 412 chunks；专长还有根级 rel 在根目录、传子目录整批漏扫的坑）。
② **落地**：管线入参约定「输入必须是 organized 根目录」+ 守卫校验；CHM 目录 ↔ organized 文件逐页对账作为 Prepare 第 0 步固化。**数据范围硬要求（E5 原文，已登记于 `docs/流程教训沉淀.md`）：类目输入范围 = CHM 目录该类目子树对应全部文档 ∪ `pf_rules_md_organized/` 全量的并集，不得缺失 CHM 目录对应文档**；两个口径陷阱（E5）：①per_file 勘探清单 ≠ 真实输入（page_195 实证）；②根目录留档区「均为重复副本」假设要逐页验证（page_12~18 根目录即唯一副本）。

## 二、实现时机制（TDD / 解析器）

### 2.1 状态机 + 关键字表——子串命中只是候选，必须形态校验才切态
① **内容**：`_SECTION_KEYWORDS` 顺序敏感（长词/特例在前），但关键字子串匹配是已知陷阱——race_spell 需「组 1 以『法术』结尾 且 EN 匹配 Spells?$」双条件才切态（KN098/KN103：44 doc/174 条「法术抗力」等条目标题含「法术」子串误判）。
② **落地**：凡关键字可能是条目标题常见词的，切态前加形态级判据（组 1 词位 + 组 2 形态 + 虚词排除集合），并配「条目标题含关键字不误切」**负例测试**。

### 2.2 表特征判定——不硬编码行号
① **内容**：`_parse_overview_row` 用「列格数（6/9/11）+ 内容特征（岁/寸区分年龄/身高表、后续格含数字区分数据行）+ 列名全集（_OVERVIEW_HEADER_CELLS 判表头行）」三个维度判定表型，一套代码覆盖三个表；拒干扰表（武器表含尺无岁寸）。**表头行要显式剥除而非靠特征间接拒掉**（否则走 pending flush 污染组标题 chunk，KN134 教训）。
② **落地**：枚举「表头特征/数据行特征/干扰表特征」三判别维度，每个表型配正例 + 干扰表负例测试。

### 2.3 词表驱动守卫 + 元数据兜底链
① **内容**：所有「格式知识」以词表常量存在（字段标签 / 怪物章节词 / 去重词 / GLUE 守卫词 / race_name 纯净性黑名单），刻意排除的合法形态**在注释中写明理由**；词表增删必须带「为什么不入表」注释。元数据兜底链四级：intro 登记（黑名单过滤）> 路径归属（三级目录/文件名/页号映射表）> 「——」拆分 > title 兜底——**文件级继承会污染的例外形态（汇总页表格行/组标题）特判写在兜底链最前**（KN113：page_11 70 行 race_name 全成「年龄」；KN134：组标题落空）。
② **落地**：字段词表一次定全（KN100：登记 1 实例实测 40——词表缺口先全库扫描定性再定稿）；兜底链例外特判加回归测试。

### 2.4 状态机弹 cur 后置 None——三条路径对称
① **内容**：章节切换 / 标题去重 / 裸标题分支三处弹 cur 后**都必须 cur = None**，后续行改走 pending_text 由下一条目 flush 承接——否则正文 append 进已弹死 dict 整段丢失（KN107 正文零丢失三层根因；KN122 M2 代码审查不对称同类 bug）。弹前判 `not cur.get("text")`（有正文绝不弹）。
② **落地**：cur 生命周期（创建/切换/弹掉/承接）画示意图进设计文档，代码评审对照图逐条核对。

### 2.5 公共层守卫参数化 + 跨类目回归门禁（最贵教训 KN112）
① **内容**：公共 normalize 函数需类目专属行为时加 `guard=True/False` 参数由调用点显式传入（feat 默认旧行为、race 传 True），不在公共函数写死也不复制一份。**race 修复只跑 race 测试 → feat 武器大师手册 6 技法类别标题整段丢失（chunk 6026 含回归）**，二分定位到 e80ec0e 才发现。
② **落地**：公共层（normalize_common 等）改动 = 全类目 pytest + 全类目 pipeline 重跑 + 各类目 verify 全过，立为硬性门禁；CI 装配表按类目全量收集测试。门禁判定必须「重生成产物再断言」，读既有产物不构成回归证据（KN136，2026-08-05）。

### 2.6 TDD 簇机制——真实形态样本 + 完整链模拟 + 负例三件套
① **内容**：每个修复前建 TestCluster 簇（簇 I/T/F3/K1~K6…），测试用**源数据真实行形态样本（必须含章节行触发正确 state）**；「单行直调成功、整段 normalize 失败」假绿重演 4 次（M3/M8/M14 正则缺 re.MULTILINE；M13 死守卫从未触达）——测试必须完整 normalize 链模拟。每个守卫/词表测试三件套：正例（新形态切出）+ 负例（不误伤合法条目）+ 回归例（旧 KN 场景仍绿），误伤面守卫的负例数 ≥ 正例数。
② **落地**：新正则测试用多行段落真实形态样本（含前/后无关行），禁止单行字符串测试；每次新增守卫后显式验证其真实语料触发次数。

## 三、产出/修复时机制

### 3.1 产出即检五合一 + 簇级对账 + 每次增减全量定性
① **内容**：pipeline 产出后立即五合一即检（title 合法性 / 字段健康度 / 召回率 / **新正则触发计数**（回归哨兵）/ 高危 probe），发现问题当场 TDD 修复不留审计轮。对账两层：簇级（doc_role 聚类，est 2132 vs got 2390 +258 逐簇定性）+ 关键文件级。「**chunk 数变化的每个增减必须归因**」是全流程铁律——含 -1。
② **落地**：diff 定性一律用 `git worktree add /tmp/基线 HEAD` 对比法（stash 法会被并行会话污染，B6）；任何修复后走「pytest → pipeline 重跑 → verify → 判别器静默丢失 0 → 闸口 → chunk 定性 → KN 更新 → git 提交」完整链。**git 提交必须含 finalize 再生成报告**（`chm_toc_backfill_report.md`/`source_补齐报告.md` 等 pipeline 输出状态报告随重跑刷新，KN130~133 与 KN134/135 两次交付均漏提交，由验收方代提交 dd2abe6/88f0c4d——提交前 `git status` 核对工作区无报告残留）。

### 3.2 修复按根因归并批次 + 修点名必扫全族
① **内容**：全量排查六组 subagent（A~F 按文件分组全覆盖）→ 问题**按根因机制归并（M1~M22）**而非按文件修 → 批次按优先级排（P1 解析 TDD → 源数据/清洗）→ 每机制独立走完整回归链并留修复要点备忘。「修聚合文件漏页文件」（M22 修 ISR 聚合漏 page_752 52 条，KN131）、「修点名实例留同族」（KN135 三残留）反复重演——**修复范围按「同类形态全库」而非「点名文件」**。
② **落地**：每个机制修复后固定追加「全库同类扫描」（形态/关键字/文件清单三向），扫描结果写入交付文档。

### 3.3 源数据字节级读写（CRLF 约定）
① **内容**：organized 源数据混合行尾，文本模式读写全文件行尾转换污染 diff——**两次事故**（M18 27 文件全转 LF；KN133 page_806/26 误转 LF + 21 行法术表错误拆行）。
② **落地**：源数据修改脚本固定 `read_bytes/write_bytes + UTF-8 替换串 + 跨行串适配 \r\n`，提交前 `git diff --stat` 核对行数变化为精确预期 + 核对 CRLF/LF 分布。

## 四、验收/审计时机制

### 4.1 四合一验收方法论 + 有条件通过 + 返修要点编号
① **内容**：验收 = ①回归链实测（k3 独立重跑与交付声明逐项对表）②交付清单逐项实证 ③抽样复核（subagent）④争议项亲验（grep 源文件实锤）。结论三档（通过/有条件通过/不通过），有条件通过必须输出**编号返修要点**（严重度+修复方向），返修后按 KN 单项定向复验，无需再次全量。**subagent 的数值类/存在类指控登记 KN 前必须回源文档亲验**——subagent 结论不作登记依据（本轮三次误报全靠亲验拦截：大地精罗圈腿 +4 正确、土元素裔缓慢速度与官方一致、灵猴族 BotB FCB 实为已产出）。
② **落地**：返修交付时提供「返修项 ↔ 闭环结果 ↔ 防回归检查」对照表；验收报告开头给回归链实测对表，每个数字自己重跑一遍。

### 4.2 验收建议必落 verify 检查项 + KN 四字段登记-闭环
① **内容**：k3 验收发现的问题其防回归检查**必须补进 verify 成为常驻闸口**（page_11 行级召回、page_752 component_type 补为 verify_races 八检查第 7/8 项，TDD 先行 10 用例）——让审计结论反哺自动化，防声明-现状再漂移。KN 固定四字段（发现时间/问题归类/严重程度/状态）+ 处置（修复命令/commit/防回归/教训），修复后同 commit 更新状态。
② **落地**：每条 P1 返修要求附带「补 verify 检查项」条款；「审计后必更新 KN 状态 + grep 裸数字查残留」作为每次审计/验收收尾固定动作（本次沉淀发现 KN107 状态行滞后反例，见 §六）。

### 4.3 行级对账 + 已否证清单
① **内容**：判别器回归（doc 级 100%）+ 召回（doc 级 37/37）全绿仍漏 page_11 三族整行丢失（KN130）——**doc 级检查天然不覆盖行级**。verify 检查设计时自问「最细粒度是什么」：汇总表/列表类页面必须加「源表数据行 ↔ chunk 逐行对账」检查（从源文件现读行，不依赖勘探产物）。「已否证/澄清清单」（subagent 误报项 + 否证证据）单列防下轮重复追查。
② **落地**：源数据是表格/列表结构的（装备表每行、怪物数据块每字段）必须源表逐行对账；每轮验收报告附已否证清单。
