# 专长模块开工前：法术模块流程抽象与预防清单

> 生成时间：2026-07-30（k3 汇总：3 路并行调研——审计流程教训 / KN 根因分类 / 可复用资产 + 专长源数据实测摸底）
> 用途：专长（feat）模块开工前的流程配置与预防扫描依据。同样适用于后续装备/怪物模块。

---

## 〇、一句话结论

法术模块 24 条 KN 中 **13~15 条可用一次开工前源数据扫描拦下**；5 轮审计返工的 8 类失实模式各有对应的流程补丁，**开工前一次配齐可把"5 轮不验收"压缩到约 2 轮**。工作流资产几乎 100% 模块无关，技术资产按"直接复用/改配置/新设计"分层。

## 一、开工前必配的流程补丁包（来自 5 轮审计 8 类返工模式）

法术 KN011~018 五轮审计的教训：每项流程补丁都精准消灭了一类错误，但全部是事后补的。专长模块开工时一次配齐：

| # | 补丁 | 消灭的错误模式 | 法术模块代价 |
|---|---|---|---|
| 1 | **先存基线快照再动手**（chunks.jsonl 备份 + git tag） | 回归无法 diff、160 chunk 干净→脏到第 2 轮才发现 | 第 1~2 轮 |
| 2 | **后处理链开工即固化单入口** `regen_feat_chunks.sh`（重生成→后处理→pytest→verify） | 重生成覆盖 link 后处理产物，已验收功能静默回退 | 第 3 轮整轮返工 T1 |
| 3 | **验收口径锁定同一脚本**（执行方 verify = 审计方 audit 同一口径，禁止窄口径冒充） | 口径偷换（窄正则测 0 冒充广义口径）、单方面放宽目标值 | 第 2 轮不验收主因 |
| 4 | **豁免程序开工即写明**（先立定性标准再豁免；逐项 chunk_id+值+理由，书面申请；禁止 ℹ️ 自行放行） | 豁免洗白真缺陷（26 个真吞正文豁免掉 16 个）→ 登记规模失真 | 第 4 轮不验收主因 |
| 5 | **每个 ✅ 必须附复算命令，跑不出就停下来查，禁止手填** | 交付声明与真值矛盾（每轮 4~6 项："已恢复"实测零命中、"253/253"实测 0/253） | 每轮不验收主因 |
| 6 | **交接清单自身先机检核对**（条数 vs 计数一致；登记物禁引 /tmp，落 `docs/state/`） | "19 条写 20 条"传染执行方漏登 4 条；/tmp 清单易失 | 第 4~5 轮返工 U4 |
| 7 | **宽启发式扫查开工即做**（不止点状指标） | 44 罗马数字伪标题、~23 D 类续段标题是三轮共同盲区 | KN019 三次扩编 |
| 8 | **旧数字 grep 用裸模式**（`69`、`（20`，不止 `~69`、`20（CRB 9`） | 改完文档旧数字残留 | 第 5 轮 V1/V2 |

另有两条工作纪律已被验证有效，直接继承：

- **告警有效性验证**：不能只断言"告警=0"，要对已知丢弃样本验证告警可触发（第 1 轮 N4 空虚通过）。
- **归因必须验证**：任何"X 归因于 Y"的表述须给实测证据（第 3 轮"M1 残留归因 KN019 同根因"实测交集为 0）。

## 二、开工前预防扫描（五合一，可拦 13~15/24 条 KN 同类问题）

历史 KN 按根因层分布：源数据格式 6 / 正则缺陷 5 / 拆分边界 4 / 字段解析 3 / 格式变体 3 / 元数据推断 3。**除正则缺陷 5 条外，全部可在开工前扫描发现或预警**。以下五组扫描对应法术模块的真实 KN 编号：

### 2.1 标题形态扫描（对应 KN006 / KN008 / KN016 / KN019-A）

一次性正则盘点全部 `**...**` 标题行形态。专长源数据**实测已命中**：

- **断行英文名**（KN006 同款）：`**突袭警惕（Ambush \nAwareness）**` 英文名换行断裂，普遍存在
- **类型标签后缀**：`**…（English）〔战斗〕**`（KN008 `[种族]` 后缀同款变体）
- **同文件重复条目**：`专长11.md` 内"突袭警惕"出现两次（无标签版 + 〔战斗〕版）——跨文件/文件内去重策略需前置设计
- 罗马数字/散文碎片抢注标题（KN019）的宽启发式在勘探阶段即跑

### 2.2 粘连/内联模式扫描（对应 KN004 / KN009 / KN010 / KN012 / KN019-D）

字段不换行、值与标签同行、超紧凑内联。实测：`专长1/20/40.md` 标准条目名行内正则零命中，格式与 `专长11.md` 明显不同——**格式簇勘探（见三）必须在写 formats/feat.py 前完成**。

### 2.3 结构缺失扫描（对应 KN002 / KN003 / KN005 / KN015）

有条目模式但无标题层级、分组标题会误产 chunk、无中文标题/破损星号簇。

### 2.4 特殊标记扫描（对应 KN022 / KN023 / 职业线 001 / 005 / KN021）

- **`](http` 链接**：`专长11.md` 单文件 **103 处**（法术 Spell OA.md 才 12 处就已造成 33 处截断）——**KN023 链接剥离 bug 是专长模块的头号预防项，写 formats 前先修清洗层**
- **`![[图片]](...)` 行首**：PFS 图标链接（职业线 001 同款：行首图片导致标题不识别、能力错挂）——且 PFS 图标本身是"PFS 合法"标记，**应提取为元数据而非当噪声剥掉**
- `◎[` 引用格式、孤立英文行、译者署名行、粗体滥用盘点

### 2.5 列表对账（对应 KN007 / KN017）

开工前先把**权威清单**建好：职业专长列表页 + 专长汇总表（若存在）→ 作为产出后召回验收基线（复用 `verify_spell_list_recall.py` 模式换专长清单）。源数据内部对账：条目字段标记 vs 列表页交叉核对。

## 三、Prepare Phase 勘探（法术模块最大教训的解法）

KN006~010 的共同根因：**写 formats 代码时只看了 3~5 个典型文件**。Prepare Phase（docs/HANDOVER_PREPARE_PHASE.md、VECTORIZER_ARCHITECTURE_DESIGN.md §4.4）是解法，专长模块必须第一步执行：

- **3 勘探维度**：格式指纹 / 陷阱清单 / 预估条目数
- **4 产出物**：`专长_per_file.jsonl` / `专长_format_clusters.md` / `专长_source_spec.md` / `专长_test_seeds.jsonl`（落 `vectorizer/exploration/专长/`）
- **格式簇驱动开发**：按"标题模式 × 字段布局"联合指纹聚簇（法术聚出 13 簇驱动 7 种变体实现），按簇排优先级，TDD 写 formats
- 专长源数据规模：**62+ 个 `专长*.md` + `专长/` 目录（含 CRB/MA 子目录与 page 文件）**，簇数预计不少于法术

## 四、产出后首轮即检三件套（不可预防类的最低成本早检）

正则缺陷类（KN014/017/018/020）源扫描不可见，靠这三件把发现时间从多轮审计压到首轮产出：

1. **title 合法性扫描**：非"中文+（English）"形态的 title 全量列出（KN019 四类全命中）
2. **字段值健康度**：值长分布、含句号数、含 `**` 残留数（KN013/020 全部判据）；field_status 诚实性抽查（status=missing 但 text 含标签）
3. **列表召回率**：清单条目 ↔ chunk title+aliases 一对一召回（KN016/017/022 的实际发现手段）

外加：**每条新写正则做全量触发计数 + 抽样人工裁决**（KN017 的 632 触发/622 误伤一检即出）；含高危模式位置取"链接后 N 字 probe"全库检索（KN023 的 33 处确认口径）。

## 五、技术资产复用清单

### 直接复用（零改动）

- WORKFLOW.md 全文（Step 0~5、决策树、并行策略）；审计-返工文档协议（交接→审计要求→交付审计→审计报告）与独立复测原则
- `pipeline.py`（编排器类目无关）、`diagnostics.py`、`audit.py` Tier 1+3、`processors/base.py` 模板方法、`formats/base.py` 两阶段、`processors/__init__.py` 注册机制、8 个通用 SourceProvider
- `parse_fields` 算法、`_is_semantically_empty`、field_status 三态方案
- TDD 6 类普适测试 + `test_per_file_chunk_counts`（数据驱动）；verify 双模式（集成验收 + 随机抽样召回含 KN019/020/021 质量旗标）
- KN 登记机制、regen 单入口脚本模式

### 改配置复用

- `registry.py` → **拆包为 `registry/spell.py` + `registry/feat.py`**（接第二个类目的必然重构，即架构文档预言的 CategoryPipeline 触发点）
- `config/` → 新建 `feat_types.json`（战斗/超魔/物品制造/团队/神话/怪物等白名单，中→英映射，未知值保留原文）
- audit.py Tier 1 类目标识信号参数化（school → feat_type）；Tier 2 键名泛化
- 勘探 4 产出物按专长目录重跑；不变量数值按专长重定

### 需新设计（专长专属）

- `formats/feat.py`：按勘探簇新写（法术 7 变体修复函数不可搬）
- `processors/feat.py`：**feat_type 多通道提取**——专长类型常在**标题行括号**（`猛力攻击（Power Attack）〔战斗〕`）而非字段行，这是与法术最大的解析差异
- **先决条件结构化解析器**：`"力量13，猛力攻击，BAB+1"` → 能力值/前置专长/BAB/技能分级列表；前置专长引用可建**专长依赖图**（检索增值点，法术无此物）
- 专长字段 schema（初版）：`feat_type`（≈school）/ `prerequisites`（≈spell_level）/ `benefit`（核心）/ `normal` / `special`（多数专长没有 → not_applicable 白名单）/ PFS 合法标记
- 去重策略：62+ 文件存在同文件重复与跨文件重复（如同名专长在不同书），合并/链接规则前置定稿
- `test_feat_metadata_v0_1.py`、专长专属不变量清单

### 不应复用（法术专属）

15 法术字段、学派/子学派/描述符白名单、formats/spell.py 全部变体修复函数、LEGACY_*_LABELS、SpellIndexProvider、link_mythic_base_spells.py、verify_kn011_018.py、法术不变量数值（4138/4200）

## 六、建议开工顺序

1. **Prepare Phase 勘探**：62+ 文件 → 4 产出物 + 格式簇（含 §二 五合一扫描，一次跑完）
2. **元数据 schema 设计（人工确认门）**：Prepare Phase 之后、pipeline 之前。基于勘探的字段标签清单/〔类型〕标签分布/先决条件形态统计，产出 `docs/专长元数据设计.md`（字段表、field_status 三态白名单、feat_type 枚举、先决条件结构），**须经人工确认后方可进入实现**——法术教训：v0.3 返工源于首跑前 schema 只看少量样本定稿，专长改为勘探数据驱动 + 人工拍板
3. **流程补丁包配齐**：git tag + chunks 基线快照 + `regen_feat_chunks.sh` 单入口 + verify/audit 同口径脚本 + 豁免程序写入审计要求
4. **修 KN023 链接剥离**（通用清洗层，法术/专长共同受益，先修再写 formats）
5. **TDD 写 formats/feat.py + processors/feat.py**（test_seeds.jsonl 驱动；schema 即 `test_feat_metadata_v0_1.py` 断言）
6. **产出 → 首轮即检三件套 + 全量召回验收**
7. 进入 V/N 迭代闭环（审计-返工协议）
