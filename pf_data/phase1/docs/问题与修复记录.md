## 002. 女巫巫术/职业能力/庇护主来源书错标

- **发现时间**：2026-07-20
- **问题归类**：来源标注
- **严重程度**：需要人工校验（影响规则问答的溯源准确性）
- **状态**：已验证 / 已关闭
- **验证提交**：`fd6a696`（代码重构与修复）、`e0de6bf`（文档与博客）

### 1. 问题描述

排查 `class_name == 女巫` 的 chunk 后发现，来源书 `book_abbreviation` 存在系统性错标：

| 类别 | 当前错误示例 | 应为 | 影响数量 |
|---|---|---|---|
| **巫术** | `凶兽（Beast of Ill-Omen, Su）` 标为 APG | UM | 21 个（含普通/强力/高等巫术） |
| **职业能力** | 冬女巫的 `冰魔法`、`冻抚` 等标为 APG | ISM | 8 个 |
| **庇护主** | `盛夏/深秋/寒冬/林地` 标为 APG | UW（极限荒野） | 8 个（含重复） |

具体被错标的 UM 巫术：凶兽、嗅童、野嚎、利爪、浸毒、槛发、瘢痕、沼鬼、狂兽、水息、兽眸、烹人、秘居、白霜、冰冢、感染、梦谈、魔酿、凶兆、唤魂、魔居。

### 2. 根因分析

1. **page_92.md 的 APG/UM 巫术来源表未被解析**：该文件顶部有一个对照表，明确列出哪些巫术出自 APG、哪些出自 UM。但当前 `detect_book` 只认 `> 来源：` 引用行和 HTML 注释，不认表格里的来源列，导致整个 page_92.md 被默认标为 APG，UM 列巫术跟着错标。
2. **变体下的职业能力未继承变体来源**：冬女巫本身是 `ISM`，但其下 `class_feature` 因为和基础职业能力同处一个文件，被标成了文件默认来源 APG。
3. **`出自《...》（Abbreviation）` 纯文本来源标记未被识别**：`全变体未整合.md` 里四季庇护主和 UW 庇护主段落前有 `出自《极限荒野》（Ultimate Wilderness）`，但脚本没把它当作来源标记，导致这些庇护主被标为 APG。

### 3. 修复实现

为避免在通用流程中写 `if class_name == "女巫"` 硬编码分支，本次修复按 K3 设计约束收敛到 `WitchProcessor` 子类与注册表：

1. **解析 page_92.md 巫术来源表**：
   - 新增 `parse_witch_hex_source_table()`，专门处理表格单元格跨行的情况。
   - 在主流程中预解析 `基础职业/女巫/page_92.md`，把 UM 列的 21 个巫术中文名写入 `ctx["witch_um_hex_names"]`。
   - `WitchProcessor.resolve_source()` 在默认推断后，若 chunk 标题中文名命中该集合且默认被标为 `APG`，则覆盖为 `UM`。

2. **变体职业能力继承变体来源**：
   - `WitchProcessor.resolve_source()` 中，若 `class_feature` 位于变体面包屑下且默认来源仍为职业默认书（`APG`/`?`），则查询变体主表 `archetype_masters` 并继承该变体的来源书。
   - 冬女巫能力因此正确标为 `ISM`。

3. **识别纯文本来源标记 + 四季/林地庇护主覆盖**：
   - `detect_book()` 增加对 `出自《书名》（Abbreviation）` 纯文本来源标记的扫描。
   - 对于子 chunk 无法直接拿到段落前来源标记的情况（如四季庇护主子表），`WitchProcessor.resolve_source()` 通过祖先面包屑关键词（`四季庇护主`、`UW里的其余庇护主`、`极限荒野`、`Ultimate Wilderness`）覆盖为 `UW`。

4. **Processor 架构调整**：
   - 将模块级 `build_chunk()` 内聚为 `FileProcessor.build_chunk()` 模板方法，拆出 `resolve_source()` / `infer_feature_subtype()` 等可覆盖子钩子。
   - 将 `FileProcessor.expand()` 中的庇护主拆分逻辑迁到 `WitchProcessor.EXPAND_STRATEGIES` 注册表。
   - `create_processor()` 把所有路径含 `女巫` 的文件路由到 `WitchProcessor`。

## 001. 行首图片链接导致加粗变体标题无法识别

- **发现时间**：2026-07-20
- **问题归类**：数据格式 / 规则识别
- **严重程度**：需要人工校验（导致变体缺失/错挂，影响检索质量）
- **状态**：已验证 / 已关闭

### 1. 问题描述

在 `pf_rules_md_organized/职业/` 下的多个源文件中，变体标题行以 PFS（Pathfinder Society）图片链接开头：

```markdown
![[图片]](https://www.aonprd.com/images/PathfinderSocietySymbol.gif) **冬女巫（Winter Witch）**
```

`vectorization_prep_profession.py` 的标题提升函数（`promote_bold_headings`、`promote_leading_bold_headings` 等）要求行首直接是 `**` 或特定模式，因此无法识别这类标题。结果是：

- 不产生独立的 `class_archetype` chunk；
- 职业能力被错误挂到前一个变体下（如冬女巫的能力挂到山脉女巫）；
- 变体主表中的来源书覆盖（如 `冬女巫 → ISM`）无法生效，回退为职业默认来源书（如 `APG`）。

### 2. 根因分析

CHM 转换后的 Markdown 用 `![alt](url) **标题**` 标记 PFS 可用变体。`clean_file` 的标题提升链没有针对这种“行首图片链接 + 加粗标题”的排版做归一化处理。

### 3. 解决方案

1. **标题提升**：在 `clean_file` 的标题提升链最前端新增 `promote_image_prefixed_headings` 步骤：
   - 识别 `![alt](url) **标题**[正文]` 格式，把图片链接去掉，并将同行的正文拆到下一行；
   - 让 `promote_bold_headings` 像处理其他顶层变体标题一样将标题提升为 `##` 二级标题；
   - 安全阀：去掉图片后不以 `**` 开头的普通图文行原样保留。

   插入位置：

   ```
   _merge_unclosed_bold_spans → merge_line_breaks → promote_image_prefixed_headings（新增）
   → promote_bold_headings → promote_leading_bold_headings → promote_inline_ability_headings
   → promote_inline_archetype_headings
   ```

2. **段落合并边界**：`merge_line_breaks` 把 HTML 来源注释行（`<!-- HH-source:... -->`）作为硬边界，不再让它与下一行标题合并，避免 `**` 剥离后标题丢失。

3. **同名变体块合并**：补充书中常见“无标记标题 + 带【职业变体】标记标题”结构（如 `**振奋乐师（Solacer）**` 后接 `**振奋乐师（Solacer）【吟游诗人变体】**正文`）。在 `merge_small_blocks` 中：
   - 若前一块与当前变体同名，把前者（通常含来源引用）作为上下文并入当前块；
   - 合并后把当前块提升到与前一块同级，并从面包屑中去掉无标记祖先，避免当前块被错挂为子级能力。

4. **变体面包屑归属修正**：`build_chunk` 中查找 `class_feature` 所属变体时，原来的循环会错误地把当前标题本身当作祖先。修正为只在 `breadcrumbs[:-1]` 中查找，使冬女巫的能力正确归属到 `冬女巫` 而不是各自标题本身或前一个变体。

5. **变体基类提取补全**：`extract_archetype_info` 增加对 `【X变体】` 的解析，使 `贤者之血（Enlightened Bloodrager）【血脉狂怒者变体】` 这类标题能正确归属到基职业。

6. **来源书补全**：修复后发现冬女巫、古墓破坏者、切利亚斯歌姬等 ISM 变体的来源书仍被错标。
   根因是 `规则书缩写对应表.md` 缺少 `Inner Sea Magic / 内海魔法 / ISM` 条目，导致变体主表解析 `内海魔法（ISM）` 时无法命中。
   解决方案：在缩写对应表中补充该行。

## 003. 圣武士/圣骑士变体来源书错标

- **发现时间**：2026-07-20
- **问题归类**：来源标注
- **严重程度**：需要人工校验（影响规则问答的溯源准确性）
- **状态**：已验证 / 已关闭
- **相关提交**：待补充

### 1. 问题描述

排查 `class_name == 圣骑士` 的 chunk 后发现，圣骑士变体来源书被系统性错标为 `CRB`（职业默认），即便汇总文件 `page_55.md` 顶部已用表格明确标注来源。

| 变体示例 | 错误来源 | 正确来源 |
|---|---|---|
| 神圣防卫者 / 医护骑士 / 神圣使徒 / 光耀骑士 / 亡灵制裁者 / 圣光斗士 | CRB/None | APG |
| 神性猎手 / 天界骑士 / 圣铳卫 / 神策使 / 死骸骑士 / 圣盾使 | CRB/None | UC |
| 义洛理圣武士 | None | ISC |
| 艾奥梅黛执法者 | None | DA |
| 殉道骑士 / 心魂卫士 / 受苦骑士 | CRB | HA |
| 守林人 / 狩邪圣武士 / 荒野守望者 | CRB | UW |
| 神炼勇士 | CRB | WMH |
| 灵刃骑士 | CRB | OO |

同时，独立补充文件 `异能源始OO_圣骑士变体.md` 文件名带 `OO`，内部变体仍被标为 `CRB`。

### 2. 根因分析

1. **`detect_book()` 瀑布优先级倒置**：职业默认（`核心职业/圣骑士` → `CRB`）排在目录/CHM TOC 之前，`page_55.md` 没有文件名缩写或标题来源标记时，整页直接被职业默认覆盖。
2. **变体主表解析失败**：
   - `_looks_like_source_cell()` 对 `医护骑士（Hospitaler）` 这类含英文缩写的变体名单元格误判为来源单元格，解析失败后又未隔离 `last_source`；
   - `_parse_source_cell()` 对 `内海战斗（ISC）`、`神圣选集（DA）` 等中文书名识别失败，导致 `last_source` 被置空，后续继承行变成 `None`；
   - 主表覆盖仅在 `source_book` 非空时生效，`None` 的变体回退到 `CRB`。
3. **段落级来源标记未利用**：`page_55.md` 主表未收录的变体依赖标题前后 `> 来源：...`、`出自《...》（Abbreviation)`、HTML 注释，但 `detect_book()` 只扫描正文前 500 字，不会针对变体 block 局部回溯。
4. **独立补充文件被职业默认覆盖**：文件名 token 置信度不够高，或主表/职业默认在后置步骤中覆盖了文件名结果。
5. **类名不匹配**：`page_55.md` 标题是 `圣武士（Paladin）`，但目录路径使用 `圣骑士`，导致 `archetype_masters` 查询时以 `圣武士` 为 key 找不到圣骑士主表。

### 3. 修复实现

本次重新设计了**通用的来源书判定框架**，不新增圣武士专用 Processor，而是把能力收敛到 `FileProcessor.resolve_source()`，使所有职业共享：

1. **抽象 `SourceProvider` 框架**
   - 用 `SourceContext` 统一封装块上下文、同文件 blocks、标题、正文、面包屑、变体名等。
   - 用 `SourceCandidate(confidence, provider)` 聚合多个 Provider 的候选，取置信度最高者。
   - 显式标记（HTML 注释、`> 来源：`、`出自《...》`）置信度 95，文件名 token 85，变体主表 80，局部回溯 75，目录/TOC 60，职业默认 30，容器默认 20，CRB 兜底 10。

2. **重写 `parse_archetype_master_table()`**
   - 预先把跨行单元格（`| ... |` 被硬换行拆开）合并回单行；
   - `_looks_like_source_cell()` 误判时，若 `_parse_source_cell()` 返回空，则保留上一个有效 `last_source`，并把当前单元格当变体名单元格处理；
   - 扩展 `_parse_source_cell()` 对中文书名和 `pg./page/页` 后缀的支持；
   - 主表 key 使用 `_master_key()` 取标题前导 CJK 字符，与变体 chunk 的 `archetype_name` 对齐。

3. **新增 `InlineSourceProvider`**
   - 扫描当前 block 文本前 800 字、前一个 block 末尾、标题本身；
   - 命中模式包括 `出自《书名》（Abbreviation）`、`> 来源：...`、`【Abbreviation】`、HTML 注释来源标记等；
   - 置信度 75，低于显式标记和主表，避免误命中。

4. **增强 `ExplicitMarkerProvider` 防泄漏**
   - `SourceMarker` 增加 `anchor` 字段；
   - HTML 注释 `<!-- XX-source:file:anchor -->` 在应用前校验 `anchor` 是否命中当前块的标题或面包屑，防止 marker 被错误应用到不相关 block。

5. **文件名/目录名 Provider 增强**
   - 文件名/目录名中的英文缩写（如 `OO_圣骑士变体`、`荒野源始WO`）置信度 85，高于职业默认；
   - `_name_variants()` 增加对 `pg. N / p. N / page N / N页` 后缀的剥离。

6. **类名归一化兜底**
   - `FileProcessor.build_chunk()` 在 `archetype_masters` 中查不到标题-derived 类名时，尝试用路径-derived canonical 类名（如 `圣骑士`）再查一次，解决 `圣武士` vs `圣骑士` 不匹配问题。

7. **变体下能力继承来源**
   - 基类 `resolve_source()` 中，若 `class_feature` 位于变体面包屑下且默认来源为职业默认/CRB/未知，则继承变体主表中该变体的来源书。

## 004. 圣律沿循者子誓约被错误识别为独立变体 + heading 层级降级

- **发现时间**：2026-07-21
- **问题归类**：数据格式 / 规则识别
- **严重程度**：需要人工校验（影响规则问答的检索质量 — 10 个子誓约不应作为独立 archetype）
- **状态**：**核心修复已验证** / 仍遗留 3 项变体识别问题（源数据层面）

### 1. 问题描述

`核心职业/圣骑士/page_55.md` 中 `圣律沿循者` 段下挂的 10 个子誓约（反腐化誓约 / 反邪魔誓约 / 反野蛮誓约 / 反亡灵誓约 / 反邪龙誓约 / 反混乱誓约 / 仁慈誓约 / 贞洁誓约 / 忠诚誓约 / 复仇誓约）被错误识别为 10 个独立 `class_archetype` 变体。这些子誓约实际上是 `圣律沿循者` 变体的子能力（`class_feature`），应归属到 `圣律沿循者` 变体下，不应作为独立变体列出。

期望结果：圣骑士变体数从 81 降为 71（去掉 10 个误识别变体）；`圣律沿循者` 变体下的子能力 chunk 正确归属。

### 2. 根因分析

`_fix_paladin_page_55` 步骤 2 的正则：

```python
if re.search(r"(?<=.)##\s|(?<=.)###\s|(?<=.)<!-- ", line):
```

设计目的是识别"内容行里嵌入的 heading / 来源行 / HTML 注释"，把被前一段吞掉的 heading 拆出来（如第 2164 行 `复原祷言` 段落）。但 lookbehind `(?<=.)` 匹配任意字符 — **包括 `#`**。结果：

- 内容行 `foo## bar`：lookbehind 是 `o` ∈ `.` ✓ 正确识别内嵌 heading
- 内容行 `foo<!-- bar`：✓
- 合法标题行 `### 神祇（Deity）`：位置 2 的 lookbehind 是 `#`（位置 1），`(?<=.)` 通过，`###\s` 匹配位置 2-4，整行被错误地当作"内嵌 heading 的内容行"处理。
- `_split_swallowed_headings` 把第一个 `#` 当成上一段尾巴切掉，剩下的 `## 神祇` 被重新提升为 `##`（level 2）

最终 `### / ####` 嵌套标题被强制降级为 `##`（level 2）。

**传播链**：
1. `### 反腐化誓约` 降为 `## 反腐化誓约`（与 `## 圣律沿循者` 同级）
2. `split_into_blocks` 切块时 `## 反腐化誓约` 与 `## 圣律沿循者` 互为兄弟节点
3. `looks_like_archetype_title` 规则 3（变体文件 + level≤3 + 带英文名）匹配 → True
4. `classify_component` 判定为 `class_archetype`
5. `infer_archetype_name` 取标题 → `archetype_name = 反腐化誓约`
6. 圣律沿循者下挂的 10 个子誓约全部变成"伪变体"

### 3. 修复实现

两处改动，都在 `vectorization_prep_profession.py`：

1. **`_fix_paladin_page_55` 步骤 2 的正则**：lookbehind 从 `(?<=.)` 改为 `(?<=[^#])`，排除 `#` 字符：

```python
if re.search(r"(?<=[^#])##\s|(?<=[^#])###\s|(?<=[^#])<!-- ", line):
```

原理：
- 内容行 `foo## bar`：lookbehind `o` ∈ `[^#]` ✓ 仍能识别吞掉的 heading
- 合法标题行 `### 神祇`：位置 2 lookbehind 是 `#`，`[^#]` 拒绝 → 不进入 split 流程 ✓

2. **`FileProcessor.keep()` 第二关**：修复修复引发的回归 — heading 块 text 只剩 `> 来源：xxx` 一行时，`is_pure_table_or_nav` 判定为纯导航，把短 archetype heading 过滤掉。增加 `class_archetype` 豁免：

```python
if (
    is_pure_table_or_nav(chunk.text)
    and not _looks_like_class_table(chunk.text)
    and chunk.component_type != "class_archetype"  # ← 新增豁免
    and chunk.feature_subtype not in (...)
):
    return False
```

### 2. 根因分析

1. **间接根因**：`vectorization_prep_profession.py` 的 `promote_leading_bold_headings`（第 1417 行）将 `**标题**正文` 模式提升为 `##` 标题。当 `**` 包裹的内容是 lore 章节名（如"选拔与入阁"）或职业字段标签（如"本职技能"）时，它们被提升为与真正变体标题同级的 heading，继而 `classify_component` 匹配 `looks_like_archetype_title` 规则 3（变体文件 + level≤3 + 含英文名）→ True。
2. **直接根因**：源数据中大量使用 `**粗体**` 标记不仅用于变体/能力标题，还用于章节名称、字段标签、表格标签等。脚本无法辨别"这个 `**粗体**` 是变体标题还是章节名"。
3. **Bug E 特因**：`**` 闭合标记缺失或格式异常 → `promote_leading_bold_headings` 只提取了标题部分，正文被粘合到字段值（title 字段）。
