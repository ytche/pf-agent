## 1. 背景

### 1.1 为什么有这一批

职业（profession / classes）与法术（spell）是数据侧最早的两个模块，先于 vectorizer 框架（Pipeline / FileProcessor / Format / cicd 验证链）建成，因此：

## 3. 关键设计决策：职业产物 schema 采用 StandardChunk（方案 A）

**决策**：职业迁移后输出 **StandardChunk**（框架 13 个统一顶层字段）。以下为**完整字段映射表**（设计定稿，执行不得擅自变更；确有出入时停线回报）：

| 老 ClassChunk 顶层字段（20） | 新 StandardChunk 位置 |
|---|---|
| `chunk_id` / `doc_id` / `category` / `component_type` / `title` / `text` / `chm_toc_path` / `aliases` / `book_abbreviation` | 顶层同名（9 个 1:1） |
| `book_source` | 顶层 `book_name_cn` |
| `book_source_english` | 顶层 `book_name_en` |
| `class_name` / `archetype_name` / `feature_subtype` | `metadata.class_name` / `metadata.archetype_name` / `metadata.feature_subtype` |
| `source_paths` / `heading_breadcrumbs` / `source_markers` / `terms` / `is_deprecated` / `char_count` | `metadata.<同名>` 下沉 |
| —（新增） | 顶层 `source_confidence`：由 `infer_metadata` / `resolve_source` 钩子按框架口径输出；`extra` 留空 |

**Java 侧适配**（`com.pfagent.agent.rag` 包）：

- **退役删除**：`ClassChunk.java`、`ClassChunkMapper.java` 及其测试 `ClassChunkMapperTest.java`（已拍板，一次性切干净，不留兼容层）。
- **改造**：`ClassDataLoader.java`（:35-49）改读 `StandardChunk`，`classes-path` 指向新产物。
- **新增** `ProfessionChunkMapper implements ChunkMapper<StandardChunk>`：复用 `StandardChunkMapper` 的映射，额外把 `metadata.class_name` / `archetype_name` / `feature_subtype` 扁平化为 Document metadata 顶层键。
- **过滤层零改动（重要结论）**：`FilterTranslator.translateClass`（:95-110）目标键为扁平键 `class_name` / `archetype_name` / `feature_subtype` / `component_type` / `book_abbreviation` / `title`；后三个 `StandardChunkMapper` 已顶层输出，前三个由 `ProfessionChunkMapper` 补齐即可。`FilterTranslator` 本身不改。
- `application.yml:31` `classes-path`：`../../pf_data/phase1/vectorization_prep_profession/chunks.jsonl` → `../../pf_data/phase1/vectorizer/output/职业/chunks.jsonl`。
- 老产物附带的 `class_archetype_index.json`：**Java 侧无消费方**（全仓库 grep 确认）。迁移后由 ProfessionProcessor 继续生成等价索引，仅作审计 artifact，不进验收硬指标。

**评测兼容性硬约束**：`chm_toc_path` 口径必须保持不变（evaluate.py 的 class 题锚点为 doc 级 tocPath），否则评测 50/50 基线会出现假性回退。

**备选（否决）**：保留 ClassChunk schema 只迁 pipeline —— 否决理由：Java 侧双 schema 长期维护成本，且与「全类目统一 StandardChunk」的框架方向相悖。
