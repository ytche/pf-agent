# 规则书向量化规则

> 适用范围：`pf_data/phase1/vectorization_prep_profession.py` 及后续规则书向量化预处理脚本。
> 目标：把 `pf_rules_md_organized/` 下的 Markdown 源文件清洗、分块、富化元数据，输出高质量、可溯源、语义清晰的 chunk。

---

## 1. 分块组件类型

每个 chunk 必须归属到以下三类之一：

| 组件类型 | 含义 | 典型内容 |
|---|---|---|
| `class_overview` | 职业整体概览 | HD、BAB、擅长技能、职业定位、职业表、通用规则说明 |
| `class_feature` | 单个职业能力/天赋 | 女巫巫术、狂暴之力、盗贼天赋、变体替换的职业能力 |
| `class_archetype` | 单个职业变体 | 医护骑士、亡灵制裁者、魔镜女巫 |

判断优先级：
1. 标题显式含 `Ex/Su/Sp` 或英文能力名 → `class_feature`
2. 标题符合变体模式（见第 3 节）且祖先不在特性章节 → `class_archetype`
3. 变体主表确认的变体 → 强制 `class_archetype`
4. 其余 → `class_overview`

## 2. 清洗规则

### 2.1 头部噪音过滤

以下整行视为噪音，直接丢弃：
- URL 链接行（`http://` / `https://`）
- 图片/链接行（`![...](http://...)`）
- 译者/整理者/校对/编辑署名（`译者：xxx`、`校对：xxx`）
- `---校对分隔线---`

判断前先剥离首尾 `**` / `~~`，避免 `**译者：xxx**` 漏过。

### 2.2 跨行粗体合并

源数据里常见标题被换行切断：

```markdown
**凋零（****Blight,
Su****）**：...
```

必须先按 `**` 成对计数把未闭合的粗体 span 跨行合并为单行：

```markdown
**凋零（****Blight, Su****）**：...
```

表格行不参与该合并。

### 2.3 段落硬换行合并

把因排版换行拆开的段落重新合并，但以下块级元素处必须断开：
- Markdown 标题（`#` 开头）
- 表格行（`|` 开头）
- 列表行（`*` / `-` / `+` / `>` / 数字. 开头）
- **HTML 来源注释行（`<!-- HH-source:... -->`）**：来源标记不应与下一行标题合并，否则 `**` 剥离后标题会丢失

合并条件：前一行没有句末标点（`。！？：；.!?;:,`）时直接拼接。

### 2.4 标题提升

将以下 Markdown/类 Markdown 结构提升为真正的标题，方便后续分块：

1. **独占一行的粗体标题**：`**标题**` → `## 标题`
2. **行首粗体 + 正文**：`**能力名（English）**正文` → 标题 + 正文
3. **内联能力标题**：`**能力名（English, Ex）：**描述` → 标题 + 正文
4. **变体补充文件中的内联变体标题**：`守望女巫(Witch-Watcher)【女巫】描述` → 标题 + 正文
5. **图片链接前缀的加粗标题**：`![alt](url) **变体名（English）**` → 去掉图片链接，将标题与正文拆成两行，再按 1/2 处理

标题必须带 heading 信号（含英文字母、`Ex/Su/Sp`、【来源缩写】等），否则保持原样。

PFS 图片前缀标题按变体标题处理，而不是普通图文行。

### 2.5 删除线变体标记

清洗前先收集带 `~~` 删除线的标题，作为 `is_deprecated` 标记；清洗后再剥离 `**` / `~~`。

## 3. 变体识别规则

一个标题被识别为变体，需满足以下任意条件，且**不满足排除条件**：

### 排除条件（先排除）
- 属于通用标题：`职业变体`、`变体`、`Class Archetypes`、`Archetypes` 等
- 显式含 `Ex/Su/Sp`
- 含“巫术”且英文名以 `Hex/Hexes` 结尾（避免把荒生巫术等误判为变体）

### 识别条件
1. 含 `〔X变体〕` / `［X变体］` / `（X变体）` / `【X变体】`
2. 含 `名称（English）【来源/职业标记】`（如 `【APG】【吟游诗人变体】`）
3. 在变体相关文件中，标题 `level <= 3` 且带有英文名括号

变体主表（职业基础页顶部的来源-变体表）解析结果优先级最高：即使某变体标题看起来像职业能力，只要主表里有，就强制识别为 `class_archetype`。

对于补充书中出现的“无标记标题 + 带【职业变体】标记标题”这种重复结构（如 `**振奋乐师（Solacer）**` 后接 `**振奋乐师（Solacer）【吟游诗人变体】**正文`），合并时以带标记的标题为准，并把前者（通常含来源引用）作为上下文并入，避免拆成两个同名块或把后者错挂为子级能力。

---

## 4. 职业能力识别规则

一个标题被识别为具体能力，需满足以下任一条件：
- 含 `Ex/Su/Sp`
- 含英文名的括号（如 `尖笑（Cackle, Su）`）
- 以 `【来源缩写】` 开头

注意：仅含章节名（如 `巫术（Hex）`、`强力巫术（Major Hex）`）的标题不是具体能力，应作为章节标题处理。

---

## 5. feature_subtype 推断规则

`feature_subtype` 只赋给 `class_feature`，用于细化能力类别。

### 5.1 推断来源
1. **面包屑推断**（最近祖先标题）：`巫术`→`hex`、`强力巫术`→`major_hex`、`高等巫术`→`grand_hex`、`庇护主`→`patron` 等。
2. **文件名兜底**：文件名含 `巫术/hex`、`强力巫术/major`、`高等巫术/grand`、`庇护主/patron` 等关键词时作为 `doc_subtype_hint`。

### 5.2 过滤与覆盖
- 若 chunk 位于变体面包屑下（`archetype_name` 非空），则清空 `feature_subtype`；变体特性不应被标为通用子类型。
- 若 subtype 为 `hex/major_hex/grand_hex`，但标题不是具体巫术条目（如章节标题），则清空 subtype。
- **含 `Ex/Su/Sp` 的能力标题不应从“庇护主”等祖先继承 subtype**：真正的庇护主条目不带动作标签，带动作标签的通常是变体特性或误标章节。
- 女巫示例：
  - `page_92.md` 面包屑含“巫术/强力巫术/高等巫术/庇护主”，具体条目如 `凋零（Blight, Su）` 标记为 `hex`
  - 补充文件 `荒野源始WO_女巫巫术.md` 通过文件名兜底得到 `hex`
  - 变体特性如 `引导能量（Channel Energy, Su）` 因 `archetype_name` 非空而不标记 `hex`

## 6. 小块合并规则

分块后需合并过小的相邻块，规则如下：

| 场景 | 行为 | 说明 |
|---|---|---|
| 当前块是变体标题，前一块不是变体 | 当前块独立 | 防止变体标题被前面的小 overview 吞掉 |
| 前一块标题属于 `推荐巫术/建议巫术/推荐/建议` | 前一块独立 | Build 建议保持独立 chunk |
| 当前块标题以 `【法术速查】` / `【特性速查】` 开头 | 在 `MAX_CHUNK_CHARS` 内并入前一块 | 速查解释是父能力的补充说明 |
| 当前块无实质文本（空标题） | 当前块独立 | 防止章节空标题吞掉首个能力 |
| 前一块是具体能力标题且文本短小 | 前一块独立 | 防止 `魔釜（Cauldron, Ex）` 等短巫术被下一块吞并 |
| 当前块已由条目表标记 `feature_subtype` | 当前块独立；短小的前文说明可合并为上下文 | 补充书条目不被章节 overview 吞掉，同时保留章节导语 |
| 前一块文本 `< MIN_CHUNK_CHARS` 且合并后 ≤ `MAX_CHUNK_CHARS` | 合并 | 普通短小段落合并 |

合并时优先保留前一个块的标题；如果前一块没有实质文本（空标题），则保留当前块更具体的标题。

## 7. 来源书识别规则

来源书推断不再使用硬编码的 10 级瀑布，而是采用**多 Provider 置信度聚合**模型：每个 `SourceProvider` 针对同一份 `SourceContext` 给出来源候选和置信度，最终取置信度最高的候选。若置信度相同，则按 Provider 注册顺序取前者。

### 7.1 `SourceContext` 与 `SourceCandidate`

```python
@dataclass
class SourceContext:
    rel_path: Path
    source_markers: List[SourceMarker]
    title: str
    text: str
    breadcrumbs: List[str]
    component_type: str
    class_name: str
    archetype_name: Optional[str]
    block_index: int
    file_blocks: List[Dict]
    book_lookup: Dict[str, Any]
    md_mapping: Dict[str, Dict[str, Any]]

@dataclass
class SourceCandidate:
    book: Tuple[str, str, str]   # (中文名, 英文名, 缩写)
    confidence: int              # 0-100
    provider: str
```

`SourceContext` 同时携带块级上下文和同文件所有 blocks，便于 Provider 做局部回溯（如变体标题前后 800 字扫描）和跨块继承（如变体下职业能力继承变体来源）。

### 7.2 内置 Provider 与置信度

| Provider | 置信度 | 职责 |
|---|---|---|
| `ExplicitMarkerProvider` | 95 | HTML 注释 `<!-- XX-source:... -->`、`> 来源：...`、`出自《...》（Abbreviation）` 等显式标记；HTML 注释带 `anchor` 时会校验 anchor 是否命中当前块上下文，防止 marker 泄漏 |
| `FilenameTokenProvider` | 85 | 文件名或目录名中的英文缩写，如 `荒野源始WO_圣骑士变体.md` → `WO` |
| `ArchetypeMasterProvider` | 80 | 变体基础页顶部“来源书-变体名”主表，仅对 `class_archetype` 生效 |
| `InlineSourceProvider` | 75 | 变体/能力标题前后 800 字内扫描来源书标记，覆盖主表未收录的变体 |
| `DirectoryTocProvider` | 60 | 目录名/CHM TOC 路径中的来源书，如 `掉链子（Unchained）` → `PU` |
| `ClassDefaultProvider` | 30 | `CLASS_DEFAULT_BOOK` 职业默认（如 `女巫` → `APG`） |
| `ContainerDefaultProvider` | 20 | 容器默认（`核心职业` → `CRB`、`混合职业` → `ACG`） |
| `CRBFallbackProvider` | 10 | 职业根节点兜底 `CRB` |

核心变化：
- **职业默认不再高于目录/文件名/局部标记**。只有在没有任何更具体证据时才回落到职业默认/CRB 兜底。
- **变体主表解析失败不产生候选**，避免 `last_source` 被污染导致后续变体错标。
- **局部回溯 Provider** 专门处理“汇总页内表格未收录、但标题前后有独立来源标记”的变体。

### 7.3 变体主表解析

变体基础页（CHM TOC 末级为 `职业变体/变体`）顶部常有一个社区整理的 Markdown 表格，列出“来源书-变体名”对应关系。

解析规则：
- 从第一个 Markdown 表格开始，到表格结束；
- 每行第一单元格可能是来源书或变体名；
- 来源单元格含 `（英文缩写）` 或中文书名关键词；
- 变体名单元格格式：`中文名（English Name，备注）`；
- 来源单元格与变体单元格可能跨行合并，使用 `last_source` 继承，但**仅在来源解析成功时更新 `last_source`**；
- 带 `~~` 的变体名标记为 `is_deprecated`；
- 解析失败时记录警告，不影响后续行。

### 7.4 变体下职业能力继承变体来源

若某 `class_feature` 位于变体面包屑下（`archetype_name` 非空），且默认推断来源仍为职业默认书，则查询变体主表 `archetype_masters` 并继承该变体的来源书。该机制在 `WitchProcessor.resolve_source()` 中首次实现，随后推广到基类 `FileProcessor.resolve_source()`，对圣武士/圣骑士等职业同样生效。

### 7.5 圣武士/圣骑士案例

圣武士在源数据中存在“一页多书”和“同名不同书”现象，是来源书推断的典型标杆：

- **第一部分**（主表）：`核心职业/圣骑士/page_55.md` 顶部表格覆盖神圣防卫者/医护骑士/神圣使徒/光耀骑士/亡灵制裁者/圣光斗士（APG）、救赎者/石之领主/宁静卫士（ARG）、圣律沿循者（UM）、神性猎手/天界骑士/圣铳卫/神策使/死骸骑士/圣盾使（UC）、神圣向导/神殿勇者（ACG）、义洛理圣武士（ISC）、勇气之刃（ISM）、幽冥猎手（OA）、艾奥梅黛执法者（DA）等。
- **第二部分**（主表未收录的变体）：`page_55.md` 后续变体通过标题前后的 `> 来源：...`、`出自《...》（Abbreviation）`、HTML 注释等局部标记识别，如殉道骑士/心魂卫士/受苦骑士（HA）、灰骑士（UI）、守林人/狩邪圣武士/荒野守望者（UW）、神炼勇士（WMH）、圣使（AMH）、驱魔卫士（MHH）、鼓舞卫士/恩惠/神契（HH）、克拉肯杀手（BotS）、泰尔曼多圣从者（AG）等。
- **第三部分**（独立补充文件）：`荒野源始WO_圣骑士变体.md`、`异能源始OO_圣骑士变体.md` 等通过文件名 token 和内部 `> 来源：` 标记识别，如滥觞卫士（WO）、灵刃骑士（OO）。

对于来源格式极差、无独立标题或被合并进其他块的变体（如 `神选之子`、`珍珠寻者`、`薄暮骑士`、`神卫`），当前脚本无法自动提取，保留为人工补全项。

## 8. 职业基础页与变体主表

CHM 目录末级决定文件类型：

| CHM 末级 | 文件类型 | 说明 |
|---|---|---|
| `职业变体` / `变体` | `archetype_base` | 需解析顶部变体主表 |
| `巫术/庇护主` | `feature_base` | 女巫巫术/庇护主基础页 |
| `科研发现` | `feature_base` | 炼金术士科研发现基础页 |
| `法术列表` | `spell_list_base` | 职业法术列表基础页 |
| `职业特性` / `特色专长` / `领域` / `血承` / `流派` | `feature_base` | 其他特性基础页 |
| 其他 | `supplement` | 补充文件 |

变体主表解析规则：
- 从第一个 Markdown 表格开始，到表格结束
- 每行第一单元格可能是来源书或变体名
- 来源单元格包含 `（英文缩写）` 或中文书名关键词
- 变体名单元格格式：`中文名（English Name，备注）`
- 带 `~~` 的变体名标记为 `is_deprecated`

### 8.1 职业基础页归档

`pf_rules_md/` 中的职业基础页（CHM TOC 路径为 `职业 → 容器 → 职业名`，如 `page_91.md`）必须复制到：

```
pf_rules_md_organized/职业/<容器>/<职业名>/<原文件名>
```

这样 `vectorization_prep_profession.py` 才能处理基础职业信息（生命骰、BAB、豁免、技能、武器防具擅长、法术、职业特性等）。复制时不应删除原文件，避免破坏 CHM 映射。

### 8.2 职业基础页的分块规则

1. **顶层标题视为 `class_overview`**：职业基础页的第一个标题（如 `女巫（Witch）`）因含英文括号容易被误判为 `class_feature`，`FileProcessor.classify_component()` 会检测 CHM TOC 路径为 `职业/容器/职业名` 且面包屑深度为 2 时，强制归为 `class_overview`。
2. **保留职业等级表**：`is_pure_table_or_nav()` 会丢弃 80% 以上为表格的 chunk，但含 `基本攻击加值 / 强韧豁免 / 反射豁免 / 意志豁免 / 等级` 的职业等级表属于规则内容，必须保留。
3. **职业表过大时拆分**：当某个 `class_overview` block 因同时包含“本职技能描述 + 完整职业表”而超过 `MAX_CHUNK_CHARS` 时，`expand()` 会在首个 `| 表：职业名 |` 处拆成：
   - 一个描述 chunk（标题保持原样，如 `本职技能`）
   - 一个职业表 chunk（标题为 `表：职业名`）

## 8.5 庇护主奖励法术拆分

女巫 `page_92.md` 的“庇护主（Patron）奖励法术”章节包含一张总览表和多张“XX庇护主奖励法术”子表。脚本必须把它拆成：

1. **一个总览 chunk**：包含庇护主通用规则说明和总览表。
2. **每个庇护主一个独立 chunk**：标题为 `中文（English）`，`feature_subtype=patron`。

拆分步骤：
- 用正则 `^(.+?)庇护主奖励法术$` 定位每张奖励法术子表的表头。
- 用表头之前的总览表建立 `中文名 → 英文名、来源书` 映射。
- 从总览表的来源书分组（如 `进阶玩家手册（APG）`）推断每个庇护主的 `book_source`。
- 子表本身通常是纯 Markdown 表格，需在过滤阶段为 `feature_subtype=patron` 的 chunk 豁免 `is_pure_table_or_nav`，避免规则内容被误删。

## 9. 过滤与保留规则

### 9.1 短小 chunk 过滤
- 默认丢弃 `< MIN_CHUNK_CHARS` 的 chunk
- 例外保留：
  - `component_type == class_archetype`
  - 具体职业能力（`class_feature` + 已知职业 + `looks_like_ability_title` + 不是速查/专长速查标题）

### 9.2 纯表格/导航 chunk 过滤
若 chunk 文本中 80% 以上行是表格、分隔线、HTML 注释或引用块，则丢弃。

**例外**：
- `feature_subtype` 为 `patron`、`domain`、`bloodline`、`arcane_school` 等规则内容型表格时，保留该 chunk。这些表格本身就是可检索的规则条目。
- 职业基础页中的职业等级表（见 8.2）也会被保留。

## 10. 输出规范

向量化脚本输出到 `vectorization_prep_profession/`（gitignored）：

- `chunks.jsonl`：所有 chunk 的完整 JSON，每行一个
- `manifest.json`：统计信息（组件分布、来源书分布、subtype 分布、解析错误等）
- `class_archetype_index.json`：职业 → Overview / Feature / 变体 的索引
- `quality_report.md`：人类可读的质量报告

每个 chunk 必须包含：
- `chunk_id`、`doc_id`、`source_paths`
- `component_type`、`class_name`、`archetype_name`
- `book_source`、`book_source_english`、`book_abbreviation`
- `chm_toc_path`
- `title`、`heading_breadcrumbs`
- `feature_subtype`
- `is_deprecated`
- `text`、`char_count`

## 11. Processor 钩子与多态规则

`vectorization_prep_profession.py` 使用 `FileProcessor` 模板方法处理单文件，职业特化逻辑通过子类覆盖/注册表注入，避免在通用流程里写 `if class_name == "女巫"` 这类硬编码分支。

### 11.1 `FileProcessor` 主流程

```
run()
  ├─ clean(lines)          # 清洗
  ├─ split(lines)          # 拆成 block
  ├─ expand(blocks)        # 按 EXPAND_STRATEGIES 展开特殊结构
  ├─ merge(blocks)         # 合并小块
  └─ 对每个 block：
       build_chunk()       # 模板方法
         ├─ classify_component()
         ├─ infer_class_name()
         ├─ infer_archetype_name()
         ├─ get_archetype_master()
         ├─ resolve_source()
         ├─ resolve_chm_toc_path()
         ├─ extract_terms()
         ├─ infer_feature_subtype()
         ├─ is_deprecated()
         └─ _make_chunk_id()
```

### 11.2 可覆盖子钩子

| 钩子 | 默认职责 | 典型覆盖场景 |
|---|---|---|
| `classify_component` | 判断 `component_type` | 极少需要覆盖 |
| `infer_class_name` | 从路径/标题/面包屑推断职业 | 极少需要覆盖 |
| `infer_archetype_name` | 推断所属变体 | 极少需要覆盖 |
| `resolve_source` | 推断来源书 | **女巫** UM 巫术、变体能力继承、四季/林地庇护主 |
| `resolve_chm_toc_path` | 解析 CHM 目录路径 | 极少需要覆盖 |
| `get_archetype_master` | 查询变体主表 | 极少需要覆盖 |
| `extract_terms` | 术语命中 | 极少需要覆盖 |
| `infer_feature_subtype` | 推断 `feature_subtype` | 可通过 `doc_subtype_hint` 或条目表扩展 |
| `is_deprecated` | 判断是否废弃 | 极少需要覆盖 |
| `_make_chunk_id` | 生成唯一 ID | 极少需要覆盖 |

### 11.3 展开策略注册表 `EXPAND_STRATEGIES`

特殊结构拆分不写在基类 `expand()` 的 `if` 里，而是通过类属性 `EXPAND_STRATEGIES` 注册策略函数：

```python
class FileProcessor:
    EXPAND_STRATEGIES: List[Any] = []

    def expand(self, blocks):
        for strategy in self.EXPAND_STRATEGIES:
            new_blocks = []
            for b in blocks:
                new_blocks.extend(strategy(b, self.ctx))
            blocks = new_blocks
        return blocks
```

女巫在 `WitchProcessor` 中注册庇护主奖励法术拆分策略：

```python
class WitchProcessor(FileProcessor):
    EXPAND_STRATEGIES = [_split_patron_reward_tables_strategy]
```

### 11.4 女巫 `WitchProcessor` 注入的规则

`create_processor()` 把所有路径含 `女巫` 的文件路由到 `WitchProcessor`（注册过的补充书带上 `SupplementSpec`，其他文件 `spec=None`）。`WitchProcessor` 覆盖 `resolve_source()` 注入三条规则：

1. **UM 巫术覆盖**：预解析 `page_92.md` 的 APG/UM 巫术来源表，UM 列的 21 个巫术在默认被标为 `APG` 时覆盖为 `UM`。
2. **变体能力继承**：`class_feature` 若位于变体面包屑下且默认来源仍为职业默认书，则继承该变体在变体主表中的来源书（如冬女巫能力 → `ISM`）。
3. **四季/林地庇护主覆盖**：`class_feature` + `feature_subtype=patron` 且祖先含 `四季庇护主` / `UW里的其余庇护主` / `极限荒野` 等关键词时，覆盖为 `UW`。

### 11.5 设计约束

- 通用引擎（`FileProcessor` / 模块级函数）不写 `if class_name == "某职业"`。
- 职业特化规则收敛到对应 `Processor` 子类或注册表条目。
- 新增职业时，优先新增 `Processor` 子类并覆盖钩子，而非修改基类。

## 12. 质量验收：抽样核对

脚本输出后必须进行抽样验收，避免“一眼判错”的 chunk 进入下游 Agent。

### 12.1 必核项

每处理一个职业/主题，至少核对：

1. **核心数量是否对得上**
   - 基础页列出的普通/强力/高等巫术数量 vs `feature_subtype=hex/major_hex/grand_hex` 的 chunk 数量
   - 基础页变体主表变体数量 vs `class_archetype` 的 chunk 数量
   - 庇护主/血承/领域等基础页列出的条目数量 vs 对应 subtype chunk 数量
     - 女巫 `page_92.md` 应产生 26 个 `patron` chunk（APG 12 + UM 14）

2. **关键条目是否被遗漏**
   - 抽查 3~5 个耳熟能详的条目（如女巫的 `凋零`、`尖笑`、`魔釜`），确认存在且内容完整
   - 检查短条目（如 `魔釜（Cauldron, Ex）`、`浸毒（Poison Steep, Sp）`）是否被错误过滤
   - 检查庇护主列表是否完整：APG 12 项 + UM 14 项

3. **标题是否被错误合并**
   - 检查是否存在把能力 A 的正文合并进能力 B 的情况
   - 检查 `【法术速查】` / `【特性速查】` 是否作为独立 chunk 输出（正确做法：并入父能力）

4. **变体与通用能力是否混淆**
   - 变体特性不应被标为通用 `hex` / `rage_power` / `rogue_talent` / `patron` 等 subtype
   - 通用巫术章节标题不应生成独立 `hex` chunk
   - 含 `Ex/Su/Sp` 的条目不应被标为 `patron`

5. **来源书是否可追溯**
   - 抽查 3~5 个 chunk 的 `book_abbreviation` 是否与文件路径/正文“来源：”提示一致
   - 变体 chunk 的来源书优先以变体主表为准

## 14. 文件级处理器架构

为支持职业/规则书特有的清洗与分块逻辑，同时避免主流程膨胀为单一巨型函数，引入 `FileProcessor` 文件级处理器。

### 14.1 基类模板方法

```python
class FileProcessor:
    def clean(self, lines) -> List[str]: ...
    def split(self, lines) -> List[Dict[str, Any]]: ...
    def expand(self, blocks) -> List[Dict[str, Any]]: ...
    def merge(self, blocks) -> List[Dict[str, Any]]: ...
    def build(self, block) -> Optional[Chunk]: ...
    def keep(self, chunk) -> bool: ...
    def run(self) -> List[Chunk]: ...
```

默认实现委托现有模块级函数，**行为零 diff**。职业或特殊规则书的特化逻辑通过子类覆盖 `clean` / `expand` 等钩子实现。

### 14.2 工厂分发

`process_profession_corpus` 主循环按 `rel_path` 创建 processor：

- 默认文件 → `FileProcessor`
- 女巫补充书（文件名含 `庇护主` 且位于 `基础职业/女巫` 下）→ `WitchProcessor`

### 14.3 设计边界

- 职业共有逻辑（`classify_component`、`infer_feature_subtype`、`_split_patron_reward_tables` 等）继续留在模块级，为将来类目层抽象预留。
- `Chunk` 增加 `extra: Dict[str, Any]` 字段，供未来法术/专长元数据扩展。

## 15. 段落合并边界：`>` 引用行硬边界

`merge_line_breaks` 合并跨行段落时，`>` 开头的引用行作为**段落硬边界**：后续普通正文不得拼接到该引用行上，避免整段正文被胶水成以 `>` 开头的“引用/导航”块而被误过滤。

引用行自身仍可按现有规则与前序普通行合并（保持改动最小）。

## 16. 补充文件结构改写器

对于排版被压缩成单行的补充规则书（如 HotHC/CoP 女巫庇护主），不通过巨型正则硬拆，而是采用**“文本改写器”**策略：

1. 先走标准清洗链（去噪、跨行粗体合并、段落合并）；
2. 由职业处理器按已核对的条目表，把不规则文本改写成通用管线能识别的标准 Markdown：
   - 章节 → `## 章节名`
   - 具体条目 → `### 中文名（English, tag）`
3. 改写后继续标准标题提升、分块、分类流程，下游零改动。

### 16.1 条目表注册表

```python
SUPPLEMENT_STRUCTURE_REGISTRY = {
    "基础职业/女巫/皇庭英豪HotHC_庇护主.md": SupplementSpec(...),
    "基础职业/女巫/格拉里昂的纯洁勇士_女巫庇护主与巫术.md": SupplementSpec(...),
}
```

条目表包含中文名、英文名、subtype（`patron` / `hex` / `major_hex` / `grand_hex`）、动作标签（Ex/Su/Sp）。

### 16.2 通用切分器 `structure_supplement`

- 归一化后按条目名/章节名定位锚点（容忍 `**`、空格、逗号、大小写、全半角、弯引号）；
- 按锚点顺序切分，每段 = 条目名 + 到下一锚点前的正文；
- 发射标准 Markdown 标题，**必须补回英文名**，否则 `classify_component` 会误判为 `class_overview`；
- 奖励法术列表在 `N级——` / `Nth—` / `Nnd—` / `Nrd—` / `Nst—` 前补换行；
- 段首残留的 `(Ex/Su/Sp)`（含大写、空格、弯引号）二次清理，避免正文被 tag 污染；
- 把文件顶部的 `> 来源：...` 引用行追加到每个条目输出，使拆分后的子 chunk 仍能通过正文来源识别命中来源书。

### 16.3 校验

- 条目表中的条目定位失败 → **报错**并保留原文，不静默跳过；
- 文本中发现未登记在条目表中的疑似标题 → **警告**，但只在条目段首扫描，避免奖励法术列表里的法术名触发噪音。
