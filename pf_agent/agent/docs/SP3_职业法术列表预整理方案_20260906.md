## 1. 背景与定位

开源单体计划第 3 子项目。「XX职业N环法术有哪些」类列举提问当前走 F-001 的 `searchByMetadata`（`spell_level_<职业>` 元数据过滤 + topK 500），但数据侧勘察证实此路**不可依赖**：

- `metadata.spell_level` 缺失率 **35%**（1449/4171 条为空）——枚举必然漏；
- 职业名 **59 种脏变体**（吟游诗人/游吟诗人/诗人、炼金术士 4 变体、召唤师括号 3 变体、22 条 class=None）——过滤键不可靠。

**但权威数据源存在**：规则书官方的按职业法术列表页（`pf_rules_md_organized/职业/<大类>/<职业>/page_N.md`，CHM TOC 28 处，`verify_spell_list_recall.py` 已硬编码 27 个路径与条目抽取正则）。书的列表本身就是完整枚举，不受 chunk 元数据质量影响。

本批：数据侧把 27 职业列表页预整理为结构化 JSON 产物，Agent 侧加 `getSpellList` 直查工具，LLM 对列举类提问直接命中清单，摆脱元数据过滤 + topK 截断。

## 2. 目标 / 非目标

**目标**：
1. 数据侧脚本生成 `spell_lists.json`：27 职业 × 环级（0~9）→ 法术条目（中英文名、来源书、可交叉的 chunk_id），附职业别名表。
2. 条目数与列表页解析结果**全量对账**（自校验，对齐 F-012 纪律）。
3. Agent 侧 `getSpellList(className, level)` @Tool：直查清单、别名归一、结果紧凑格式化 + 长度护栏；溯源锚定列表页。
4. LLM 工具路由：列举类提问优先 `getSpellList`（工具描述引导，不改 prompt 主体、不加分类器——延续 F-001 决策）。
5. 评测集补 2~3 道「XX职业N环法术」题（当前 56 题零覆盖此形态），全量评测不回退。

**非目标**：
- **不修 spell_level 脏数据 / 不补 35% 缺失**（独立数据质量批次的事，本批清单绕开它而非依赖它）。
- 不动 spell pipeline / chunks.jsonl / 向量库（cicd 冻结面不变）；不改 searchByMetadata/vectorSearch。
- 不做列表页之外的「准列表」推断（如按领域法术、血脉法术）；不做前端改动。

## 3. 设计决策（D1~D7）

- **D1 数据源**：规则书官方职业法术列表页（权威、完整），**不用** chunk `spell_level` 元数据（35% 缺失 + 脏名，仅作交叉引用时的辅助，不作枚举依据）。
- **D2 产物形态与位置**：`pf_data/phase1/vectorizer/output/法术/spell_lists.json`（与 chunks.jsonl 同目录，同为 gitignored 产物；脚本入库、产物由脚本再生，与现有数据产物纪律一致）。
- **D3 产物 schema**：

```json
{
  "version": "1.0",
  "generated_from": "职业列表页 27 路径（脚本内注册表）",
  "classes": {
    "法师": {
      "aliases": ["奥能师"],
      "source_page": "职业/核心职业/法师/page_65.md",
      "list_chunk_id": "class_page_65_xxxx",
      "levels": {
        "0": [{"cn": "酸液飞溅", "en": "Acid Splash", "book": "CRB", "chunk_id": "spell_Spell CRB_0001"}],
        "1": []
      }
    }
  }
}
```

  - `chunk_id`：按「中英文名 + 来源书」与 chunks.jsonl 对账交叉；对不上（该法术未入库/书名差异）置 null，**不阻塞**生成，但对账报告须统计 null 率。
  - `aliases`：覆盖 27 职业的常见变体（诗人→吟游诗人、圣武士→圣骑士、审判官→审判者等；脚本内注册表，数据侧拥有）。
  - 共用页（术士/法师同 page_65 等）按列表页实际归属拆出各自职业条目。
- **D4 Agent 加载**：遵循工程现有先例——`@Value` 文件路径（`pf.spell-lists.file-path`，默认 `../../pf_data/phase1/vectorizer/output/法术/spell_lists.json`）+ `@PostConstruct` 加载进内存 Map；文件缺失 → warn 日志 + 工具注册但返回「清单不可用」提示（不炸启动，对齐 DataLoader 宽松语义）。
- **D5 工具签名与行为**：`@Tool getSpellList(String className, Integer level)`：
  - `className` 经别名表归一；未知职业 → 返回可读提示 + 27 个合法职业清单（让 LLM 自纠，对齐 searchByMetadata 的错误自纠风格）。
  - `level` 必填 0~9；为空 → 返回该职业各环级条目数概览 + 提示指定环级（避免一次塞 9 环全量打爆上下文——法师全表上千条）。
  - 单环级结果紧凑格式化（`序号. 中文名（English） [书]`），超 `pf.search.metadata-result-chars`（4000）复用同一护栏截断 + 提示。
  - **溯源**：把该职业的列表页 chunk（`list_chunk_id`，职业库）作为 Document 交 `SourceCollector`——用户可追溯列表来源；单个法术不逐条挂溯源（清单页即权威出处）。
- **D6 工具路由**：只写工具描述（「列举某职业某环级法术时优先用我，比 searchByMetadata 更全更准」），LLM 自主选择；不改 system prompt、不动 F-001 链路。
- **D7 与检索的关系**：`getSpellList` 是**枚举直达通道**，与 searchByMetadata（模糊/组合过滤）互补共存；本批检索代码零改动。

## 7. 风险与回滚

| 风险 | 缓解 |
|---|---|
| 列表页格式不统一（分环标题/表格形态跨书差异） | T1 先出对账报告，27 页逐页解析成功率入报告；个别页解析失败 → 停线报 k3 裁定，不硬编正则 |
| 条目↔chunk 交叉对不上（译名差异/未入库） | chunk_id 允许 null 并在报告量化；不影响清单枚举功能（溯源靠列表页锚定） |
| LLM 不用新工具（路由不生效） | 评测新题实证；必要时迭代工具描述（不动 prompt 主体） |
| 回滚 | 单分支 revert；产物可删可再生；检索零改动无连带 |
