## 一、总体战略（用户拍板）

1. **先完善业务功能** → **开源一个可独立部署的单体项目**（服务有技术能力的社区用户自部署）。
2. **之后再拆微服务**：用户管理独立成服务（登录/鉴权/token 成本控制），pf_agent 与 5e 车卡小程序共用该鉴权服务（服务无技术背景的社区用户，托管版有 token 成本，必须登录）。
3. 微服务拆分是**学习目的驱动**（用户无 Spring 微服务实战经验，仅有用友自研微服务接触），运维成本接受（可能多几台机器）。

## 二、微服务版（暂缓，已拍板的选型）

- 技术栈：**全家桶**——Nacos（注册+配置中心）+ Spring Cloud Gateway + OpenFeign + Spring Security + JWT
- token 校验：**方案 A，JWT 无状态验签**（用户服务签发，资源服务本地验签；Gateway 路由 + RequestRateLimiter 全局限频；Feign 仅用于真实管理类调用）
- 鉴权策略：**匿名配额 + 登录无限**（未登录每会话限 N 轮，登录放开）
- 用户体系：**用户名+密码注册**（5e 车卡的微信登录届时再扩，用户表预留扩展）
- 范围：只做用户服务 + pf_agent 接入，5e 车卡立项时复用
- 部署拓扑：现有 2C2G + 新增 1 台
- 数据库：（原定 MySQL，后被开源单体阶段的 PG 决策覆盖，见 §三）

### 关键技术约束（讨论中确认）

- **embedding 模型一致性**：向量库由 bge-m3 构建，运行时查询 embedding 必须用同一模型，否则检索全废。「云 API」只能选托管版 bge-m3（如硅基流动），不能换模型；换模型 = 全量重建 600MB 向量库 + 重跑所有评测基线（不建议）。
- **向量库将来也要进 DB**（用户拍板的"后话"）：现在只做预留——数据访问边界收干净，不泄漏 `SimpleVectorStore` 特性到业务层；Spring AI `VectorStore` 接口抽象已是天然切换点。
- 因向量库确定进 DB，**数据库选型从 MySQL 改为 PostgreSQL 16 + pgvector 一统**（业务 + 向量同一个 DB，避免双组件运维；用户确认 PG 学习成本低、业务简单风险可控）。

### SP1 已确认设计（第 1~3 节）

**第 1 节 · 选型与架构**
- 持久层：**Spring Data JPA**（简单 CRUD 零 SQL；MyBatis-Plus 已议过不选）
- PG 对自部署用户：**默认内存、PG 可选**——不配 `spring.datasource.url` 则行为与现在完全一致
- pf_agent 单仓继续，不拆物理仓

**第 2 节 · 表结构**
```sql
chat_conversation(
  id              VARCHAR(36) PK,      -- conversationId（后端生成的 UUID）
  created_at      TIMESTAMPTZ,
  last_active_at  TIMESTAMPTZ,         -- 排序/清理
  message_rounds  INT                  -- 冗余轮数（F-005 判断 + SP2 配额复用）
)
chat_message(
  id              BIGSERIAL PK,
  conversation_id VARCHAR(36) FK → chat_conversation(id) ON DELETE CASCADE,
  seq             INT,                 -- 会话内消息序号
  role            VARCHAR(10),         -- user / assistant
  content         TEXT,
  created_at      TIMESTAMPTZ
)
-- INDEX (conversation_id, seq)
```
- 只落 [user, assistant] 对（对齐现有 L1 记忆语义，工具调用中间态不落库）
- F-005 保留轮数：**默认 20 轮**，配置项 `pf.chat.history-rounds`，写入时裁剪
- conversationId 现状：前端 localStorage 持有，空则后端生成 UUID（表结构与此兼容）

**第 3 节 · ChatMemory 持久化实现与切换**
- 新增 `JdbcChatMemory implements ChatMemory`（Spring AI 接口，对齐官方标准形态）：
  - `get(cid, lastN)` 查最近 N 条装 Message；`add()` 事务包住「写消息 + 更新 last_active_at/rounds + 超 20 轮裁剪」；`clear()` 删会话
- 切换：`pf.chat.memory: memory|jdbc`（默认 memory）+ `@ConditionalOnProperty` 二选一装配
- `ChatService` 零改动（只面向 `ChatMemory` 接口）
