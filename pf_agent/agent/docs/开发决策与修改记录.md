## D01 · 完善 system prompt 断言约束 + class 基础页 chunk 加权（2026-08-11）

### 状态

已实施并端到端验证（AKN-003 闭环）。

### 背景

用户问「女巫职业等级表 + 每级豁免 + 每日法术位」，Agent 回答主体正确，但**顺带**扩展了"女巫是自发施法"——错误描述（PF 1e 女巫是准备施法者）。LLM 在回答主体正确时凭训练印象扩展了未检索到的属性，并标成"推断"。

### 根因（数据链排除法）

逐层排除：organized 源数据存在 → chunks.jsonl 完整 → 向量库存在 → bge-m3 实际复现检索 top20 **无任何"自发"字样**。结论：数据不缺失、检索能命中，错误描述是 LLM **生成阶段顺带编造**，非检索缺陷。现有 prompt「禁止凭记忆编造规则」只防"完全不知道→瞎编"，防不住"主体正确→顺带扩展未检索属性"。

### 方案选择

- **A（主药，`PromptBuilder`）**：system prompt 新增两条规则——①每条规则事实必须有检索依据，检索未提供的禁止凭记忆补全，影响完整性先 `reportDataGap` 再如实说明；②职业核心机制以"基础职业能力"检索结果为准，变体文本与基础页冲突时以基础页为准（除非问题明确指向某变体）。
- **B（辅药，`SearchService`）**：class 库**基础职业页**（tocPath 恰为 `职业 → 基础职业 → X`）排序时相似度 +0.03（仅排序用，不改 `Document.score`），并扩容候选集 topK+3。动机：class 库女巫变体/巫术 chunk 226 个 vs 基础页 16 个，变体噪声重，top5 中变体常占 4 个（含「灵脉守卫是自发施法者」），与基础页原文「必须预先选择并准备法术」**直接矛盾**，加剧 LLM 不确定性；而基础页与变体相似度咬紧（差 <0.02）时变体噪声会压过基础页。
- **实现粒度**：用户拍板选「**轻量：topK 扩容 + 重排**」——不引入查改写/分类器，用 tocPath 结构化字段识别基础页，加分仅影响排序、不污染数据。
- **安全性论证**：问变体时基础页相似度天然 <0.55（低于阈值不在候选集），加分无影响，不会误伤变体问法。

### 改动

| 文件 | 改动 |
|---|---|
| `PromptBuilder.java` | PROMPT 新增两条规则（断言必须有检索依据 / 职业核心机制以基础页为准） |
| `SearchService.java` | 新增 `classBaseBonus`/`classExtraCandidates` 字段（`@Value` 可配），`search()` class 模块扩容 + `boostedScore()`/`isBaseClassPage()` 加分重排；15 参主构造器加 `@Autowired` 解决多构造器装配（2026-08-16 注入方式规范化后改为 `@Autowired` 字段 + `@PostConstruct` 组装，构造器移除，规则见根 CLAUDE.md） |
| `application.yml` | `pf.search.class-base-bonus: 0.03`、`pf.search.class-extra-candidates: 3` |
| `PromptBuilderTest` | +2 测试（prompt 含两条约束） |
| `SearchServiceTest` | +4 测试（基础页略低相似度加分排前 / 问变体不误伤 / 非 class 不加分 / 扩容 topK 透传） |

### 验证

- **检索层**：真实 bge-m3 复现三类基础问法，top5 基础页从 1~3 个提升到 3~4 个，`职业特性` chunk 稳居 top1。
- **端到端**（agent 重启后）：
  - 问法一「职业等级表+豁免+法术位」：不再出现"自发施法"断言、不再标"推断"——检索未提供就如实不补全；20 级截断数据明确标注"基于表格规律的推断"。
  - 问法二「女巫是准备施法者还是自发施法者」：有依据明确回答"准备施法者"，引用 APG 职业特性原文；同时如实区分灵脉守卫变体是自发施法者（符合规则②：未指向变体以基础页为准）。

### 教训

- 排查"Agent 答错"必须做数据链排除（数据 → 检索 → 生成），本次初判"数据缺失"被实际检索复现推翻。
- prompt 的"禁止编造"防不住"顺带扩展"，需显式约束"断言必须有依据 + 未检索不补全"。
