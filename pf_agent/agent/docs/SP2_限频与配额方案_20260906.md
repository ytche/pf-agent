## 1. 背景与定位

开源单体计划第 2 子项目（SP1 持久化已收口）。`/api/chat` 当前无鉴权无限制、接口外露（AuthInterceptor 是放行占位），存在脚本滥用 → DeepSeek token 成本失控风险。本批落地 F-010（按 IP 限频）与 F-011（匿名每会话轮次配额），两项均**默认关闭、配置开启**（用户拍板：开源自部署零摩擦优先；托管部署在 yml 打开即获保护）。

## 2. 目标 / 非目标

**目标**：
1. F-010：`/api/chat` 按 IP 固定窗口限频，默认 20 次/分钟，超限返回 429 + JSON 错误体。
2. F-011：匿名用户每会话累计 20 轮配额，超限返回 429 + JSON 错误体；新会话（无 conversationId）不受限。
3. 两项默认关闭；开启后内存/jdbc 两种存储模式下语义一致。
4. 前端识别 429 展示专属文案（不再笼统「服务异常」）。
5. jdbc 侧补 `total_rounds` 累计轮数列（Flyway V2 迁移），**修正 SP1 D3「配额复用 message_rounds」的错误假设**——message_rounds 会被 F-005 裁剪钉在上限，不能作累计配额依据。

**非目标**：
- 不做登录/账号体系、不做按用户/按 IP 每日配额（微服务版的事）。
- 不动 AuthInterceptor 占位（登录接入点，留给微服务版）。
- 不做分布式限频（单实例内存计数；多实例属微服务版范畴）。
- 不限 `/api/chat/feedback` 与 `/api/health`；不改检索/prompt/评测行为。

## 3. 设计决策（D1~D8）

- **D1 限频落点**：新增 `RateLimitInterceptor implements HandlerInterceptor`，注册进既有 `WebConfig` 拦截器链，仅拦 `POST /api/chat`。不引 Bucket4j 等外部依赖——单实例场景自研内存固定窗口足够（KISS）。
- **D2 限频算法**：按 IP 固定窗口——`ConcurrentHashMap<ip, {windowStartEpochMinute, count}>`，每分钟窗口重置；超限 429。窗口边界允许 2 倍突发属已知可接受特性（成本控制场景不需要精确滑动窗口）。map 惰性清理过期窗口项防膨胀。
- **D3 IP 提取**：默认 `request.getRemoteAddr()`；`pf.rate-limit.trust-forwarded-for: true` 时取 `X-Forwarded-For` 首跳（反向代理部署用，默认 false 防伪造）。
- **D4 配额计数**（两种存储统一语义 = 累计轮数，不裁剪）：
  - jdbc 模式：`chat_conversation` 新增 `total_rounds` 列（Flyway `V2__add_total_rounds.sql`：`ALTER TABLE chat_conversation ADD COLUMN total_rounds INT NOT NULL DEFAULT 0`），`JdbcChatMemory.doAdd` 每轮 +1（按 `rows.size()/2`），**永不裁剪**；`message_rounds` 语义不变（保留轮数）。
  - memory 模式：`chatMemory.get(cid, Integer.MAX_VALUE).size() / 2` 现算（InMemoryChatMemory 无裁剪，条数即累计；零新增状态）。
  - 封装在 `AnonymousQuotaService`（@Component，`pf.quota.enabled=true` 时装配）内，按 `ChatConversationRepository` 是否可用（ObjectProvider）选路径——存储细节不外泄。
- **D5 默认开关**（用户拍板）：`pf.rate-limit.enabled: false`、`pf.quota.enabled: false` 默认全关；`pf.rate-limit.per-minute: 20`、`pf.quota.anonymous-rounds: 20`。
- **D6 配额检查位置**：`ChatController.chat()` 中、`chatService.ask()` 之前——超配额**在 LLM 调用前 fail-fast，零 token 成本**。conversationId 为空（新会话）直接放行。
- **D7 超限响应**（用户拍板）：429 + JSON 错误体——限频 `{"error":"rate_limited","message":"请求过于频繁，请稍后再试","retryAfterSeconds":N}`；配额 `{"error":"quota_exceeded","message":"本会话免费额度已用完（20 轮）。请开启新会话继续提问。"}`。前端 `index.html` 的 fetch 分支识别 `r.status===429` 解析 JSON 展示 message，其余非 200 维持现状。
- **D8 与 F-005 的边界**：配额（20）= 裁剪保留轮数（20）时，开启配额后 F-005 裁剪实际不会触发（第 21 轮被配额挡住）；默认关闭配额时裁剪照常。两者独立配置互不影响，文档注明即可，不做耦合逻辑。

## 4. 已知限制（文档声明，不修）

- 匿名配额按会话 ID（前端 localStorage）计数：清缓存换新会话即重置。**防君子不防小人**，真正的成本控制靠将来登录版（微服务）。
- 共享出口 IP（NAT/校园网）下按 IP 限频可能误伤同人网段——阈值 20/分对真人宽松，可接受；部署侧可调。
- 内存模式重启后配额计数清零（无持久化），与 F-003 内存语义一致。

## 5. 配置汇总（application.yml 新增，默认关闭）

```yaml
pf:
  rate-limit:
    enabled: false            # F-010 按 IP 限频开关
    per-minute: 20            # 每 IP 每分钟 /api/chat 上限
    trust-forwarded-for: false # 反向代理部署时开，取 X-Forwarded-For 首跳
  quota:
    enabled: false            # F-011 匿名会话配额开关
    anonymous-rounds: 20      # 每会话累计轮数上限（达上限 429，新会话重新计）
```

## 6. 任务分解（执行顺序）

1. **T1 V2 迁移 + total_rounds 累计**：`V2__add_total_rounds.sql` + 实体加列 + `JdbcChatMemory.doAdd` 累计 +1/轮 + `JdbcChatMemoryTest` 补断言（累计不受裁剪影响：21 轮后 message_rounds=20 但 total_rounds=21）。
2. **T2 限频器**：`RateLimitInterceptor` + `WebConfig` 注册（仅 `/api/chat`）+ 配置项 + 单测（窗口内放行/超限 429/窗口重置/XFF 开关/惰性清理）。
3. **T3 配额服务**：`AnonymousQuotaService`（双模式计数）+ `ChatController` 检查点 + 单测（jdbc/memory 两路、20 轮边界第 21 轮 429、新会话放行）。
4. **T4 前端 429 文案**：`index.html` fetch 分支识别 429 展示 message。
5. **T5 真 PG 冒烟自跑 + 交付文档**：jdbc 模式 V2 迁移 + 配额全链（21 轮 429）自跑记录；装配三态（全关/只开限频/只开配额）验证。

## 9. 风险与回滚

| 风险 | 缓解 |
|---|---|
| V2 迁移在有数据的库上执行 | `ADD COLUMN ... DEFAULT 0` 是 PG 在线安全操作（11+ 不重写表）；冒烟库已含 V1 数据可实测 |
| 拦截器顺序影响既有 AuthInterceptor | WebConfig 显式注册顺序：Auth → RateLimit（先后不敏感，各自独立 preHandle） |
| 固定窗口边界 2x 突发 | 已知接受（D2），成本控制场景阈值本就保守 |
| 回滚 | 单批次 revert；默认全关，不启用等于零影响 |
