## 1. 背景与定位

开源单体计划收口后，用户拍板两项方向调整：① 默认持久化（对话历史进 PG，不再默认内存）；② 单体补齐用户注册登录（原计划留给微服务阶段，现提前到单体做一版，JWT 方案与未来拆分兼容）。本批不动任何检索/回答业务逻辑。

现状勘察（k3 亲测）：

- SP1 已有 `JdbcChatMemory` + Flyway V1/V2（`chat_conversation`/`chat_message`），`pf.chat.memory: memory` 默认，`@ConditionalOnProperty` 二选一装配。
- `AuthInterceptor` 为占位（preHandle 直接 return true，`config/AuthInterceptor.java`）。
- 依赖现状：已有 JPA / Flyway / postgresql / **h2**；**无 spring-security-crypto、无 JWT 库**——本批需新增两个轻量依赖（见 D3），不引入完整 Spring Security 栈。
- compose 的 pg 目前是可选 profile；SP6 刚发布的开源库 README 写着「默认内存」——文档需同步。

## 2. 目标 / 非目标

**目标**：PG 持久化成为代码与部署双默认；用户注册/登录/JWT 鉴权闭环（表 + 接口 + 拦截器 + 前端表单）；compose 默认起 PG；文档同步。

**非目标**：不做按用户配额/限频（F-011 匿名配额维持现状，按用户配额另行立项）；不做邮箱验证/找回密码/第三方登录；不做角色权限体系；不上 Spring Security 全家桶；不改检索与回答行为；不动旧库→新库同步。

## 3. 设计决策（D1~D7）

- **D1 持久化默认化**：`application.yml` 默认 `pf.chat.memory: jdbc`，datasource 默认值 `jdbc:postgresql://localhost:5432/pf_agent`（用户名/密码默认 `pf_agent`，env 可覆盖）。**测试豁免**：`src/test/resources` 覆盖为 `memory`（或测试用 H2——执行方评估，取简单可靠者），保证 `mvn test` 在无 PG 环境（含 CI runner）依旧 247+ 全绿。`pf.auth.enabled=true` 时**强制要求 jdbc 模式**（用户表在 PG），启动 fail-fast 校验并给出明确错误信息。
- **D2 用户表（Flyway V3）**：`V3__user_account.sql`——
  ```sql
  user_account(
    id            BIGSERIAL PK,
    username      VARCHAR(64) UNIQUE NOT NULL,   -- 登录名，大小写不敏感由应用层归一
    password_hash VARCHAR(72) NOT NULL,          -- BCrypt
    nickname      VARCHAR(64),                   -- 可选展示名，默认=username
    created_at    TIMESTAMPTZ NOT NULL,
    last_login_at TIMESTAMPTZ
  )
  ```
  最小够用，不预留角色/邮箱字段（将来微服务用户库重新设计，本表不背演进包袱）。
- **D3 依赖与算法**：新增 `spring-security-crypto`（只用 `BCryptPasswordEncoder`，不引入 security 全家桶）+ `io.jsonwebtoken:jjwt-api/impl/jackson`（0.12.x）。JWT HS256：payload 放 `sub=username`、`uid`，有效期默认 72h（`pf.auth.token-ttl-hours`）；密钥 `pf.auth.jwt-secret`（env `PF_AUTH_JWT_SECRET`），yml 给开发默认值 + 注释警告「生产必须覆盖」，`pf.auth.enabled=true` 且密钥仍为默认值时启动 WARN 提示（不阻断，自部署场景友好）。
- **D4 鉴权接口**（`AuthController`，`/api/auth/**` 全豁免拦截）：
  - `POST /api/auth/register`：username（3~64 字符，字母数字下划线中文均可，去首尾空白后归一）+ password（≥8 位）→ 校验唯一性 → BCrypt 入库 → 直接签发 JWT 返回（注册即登录）；
  - `POST /api/auth/login`：校验 → 更新 last_login_at → 签发 JWT；
  - `GET /api/auth/me`：带 token 返回当前用户信息（前端恢复登录态用）；
  - 错误码语义化：`username_taken` / `invalid_credentials` / `invalid_request`，HTTP 400/401/409 对应，前端可直接消费。
- **D5 AuthInterceptor 落地**：`pf.auth.enabled=false`（默认）→ 全放行（现状不变）；`true` → `/api/chat`、`/api/chat/feedback` 需 `Authorization: Bearer <jwt>`，校验失败 401 `{error: "unauthorized"}`；豁免：`/api/auth/**`、`/api/health`、静态资源与 `/`。解析出的 username 放入 request attribute（`ChatService` 暂不消费，留给将来按用户配额/按用户会话隔离——本轮问答仍按 conversationId 匿名语义，**不改变现有会话行为**）。
- **D6 前端**：`static/index.html` 加登录/注册表单（顶部栏或弹层，样式随现有页面风格）：token 存 localStorage；`fetch` 统一带 Authorization 头；401 时清 token 并引导登录；`pf.auth.enabled=false` 时前端**不显示**登录入口（新增 `GET /api/auth/status` 返回 `{enabled: boolean}`，前端启动时探测）。
- **D7 compose 与文档**：`docker-compose.yml` 的 pg 移出 profile 成为默认服务；app `depends_on: pg (condition: service_healthy)`（pg 已有 healthcheck）；app environment 默认 `PF_CHAT_MEMORY=jdbc` + datasource 指向 `pg` 服务。`.env.example`、README（快速开始/配置表/「默认内存」表述）、`docs/DEPLOYMENT.md`（部署形态、环境变量表加 `PF_AUTH_*`）同步。**注意**：开源库 `ytche/pf-agent` 的同步不在本批（用户人工决定同步机制），但 README 改动要在交付文档中标记「需同步到新库」。

## 5. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 默认 jdbc 导致 `mvn test` / CI 无 PG 环境挂掉 | D1 测试豁免；T1 第一步就是验证 CI 绿（本地无 PG 跑 `mvn test` 必过） |
| JWT 密钥默认值被生产沿用 | D3 启动 WARN；DEPLOYMENT 三坑节后追加说明 |
| 注册接口被刷库 | 复用 SP2 限频：`/api/auth/**` 纳入 `pf.rate-limit` 拦截范围（开关同源，默认关） |
| 前端 401 与匿名配额 429 混淆 | 错误体结构区分（`unauthorized` vs `quota_exceeded`），前端分别引导 |
| 老部署升级后「历史会话丢失」观感 | 内存会话本就不持久，无回归；DEPLOYMENT 注明升级即切库 |
