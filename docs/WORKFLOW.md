# 多 Agent 协作开发流程

生效日期：2026-09-16
设计依据：`docs/superpowers/specs/2026-09-16-multi-agent-workflow-design.md`

本文件定义 pf_agent 仓库的分角色开发流程。CLAUDE.md 中有压缩版红线，本文件是完整版，按需读取。

## 角色

| 角色 | 形态 | 职责 |
|------|------|------|
| 主 Agent | 内置默认 | 流程编排 + 最终验收：派单（附红线摘要）、中转打回、对照验收标准逐条核对、向用户汇报结论 |
| architect | `.kimi-code/agents/architect.md` | 设计：产出方案文档（改动范围、模块划分、扩展点、风险、验收标准草案），落盘 `docs/design/`。只读代码、只写方案文档，**不碰实现代码** |
| coder | 内置 coder，不定制 | 按方案实现 + 自测；交付代码与结构化提交说明（改动文件、方案覆盖情况、自测内容、**已知未覆盖点**声明） |
| tester | `.kimi-code/agents/tester.md` | 读方案制定用例 → 黑盒测试（真实调用）→ 审计 coder 测试代码 + 白盒补测（重点边界条件）→ 出具测试报告。只能写测试代码与报告，不改实现 |

验收由主 Agent 承担，不设独立 acceptor；tester 报告是验收的强制输入。

## 分级触发

| 级别 | 典型任务 | 链路 | 留档 |
|------|----------|------|------|
| 轻量 | 配置修改、脚本小 bug、文档更新 | 主 Agent 直接做 → tester 针对性验证 → 主 Agent 验收 | 不留档，报告只回消息 |
| 标准 | 新功能、新模块、跨文件改动 | architect → 用户拍板 → coder → tester → 主 Agent 验收 | 方案 + 测试报告落盘 |
| 大工程 | 新 pipeline、架构调整 | 标准链路前加方案评审，用户拍板后才动工（"讨论阶段不动手"） | 同上 |

## 交接物

- **方案文档**：`docs/design/方案_<主题>_<日期>.md`，含改动范围、模块划分、扩展点、风险、**验收标准草案**。它是 coder 与 tester 的共同输入——子代理上下文隔离，派单时给文件路径，不口头转述。
- **coder 提交说明**：改动文件清单、方案覆盖情况、自测内容、已知未覆盖点（不许隐瞒）。
- **测试报告**：按 tester 模板输出，缺陷分 Blocker / Major / Minor 三级；标准/大任务落盘 `docs/test-reports/测试报告_<主题>_<日期>.md`，**落盘后同步登记到 `docs/test-reports/README.md` 索引表**（维护动作挂在流程里，不靠自觉）。
- **验收结论**：对照验收标准逐条核对 + tester 报告摘要 + 明确结论（通过/打回）。验收反馈文档维持放 `docs/handover/`。

## 迭代回路

1. **tester 不通过**（报告含 Blocker/Major 或结论不通过）→ 主 Agent 把缺陷清单（含复现步骤）派回 coder，修完 tester 回归。coder 与 tester 不直接对话，主 Agent 中转并负责过滤无效缺陷、仲裁分歧。**上限 3 轮**，超限停下来向用户升级，说明卡点，由用户拍板（放宽标准 / 改方案 / 重来）。
2. **主 Agent 验收打回**按原因定路线：
   - 实现未达方案验收标准 → 打回 coder（不经过 tester）；
   - 方案本身有缺陷 → 回 architect 修订，方案改动需用户重新拍板；
   - 需求理解有误 → 找用户澄清，不动工。
3. **Minor 缺陷**（不影响功能正确性的问题）由用户拍板：放行并登记 KN（接入 `docs/已知问题记录.md`），或打回。主 Agent 不擅自放行。

## 缺陷级别定义

- **Blocker**：功能不可用、崩溃、数据损坏、主流程走不通。
- **Major**：核心功能有缺陷但有绕过办法，或重要非主流程场景出错。
- **Minor**：不影响功能正确性——格式小瑕疵、罕见边缘场景、日志/提示不准、文档小错。

## 问题归因与数据版本闭环（2026-11-11 起，F-012）

问题（数据缺失、Java 消费偏离、检索错误、生成编造）统一按**四层归因**：数据层 / 消费层 / 检索层 / 生成层，每个问题指定一个**主责层**并记录**跨层因果链**。完整判定标准、构建与消费规则、可复制模板见 **`docs/templates/问题归因与变更验收模板.md`**（本文件不复制模板全文）。

- **证据三阶段**：登记只需最小字段（疑似原因必须标注「疑似」）；定方案前必须完成分层排证；闭环前证据完整（真实验证结果、实例加载标识、端到端复现、源文档同批同步）。
- **构建范围**：局部改动走 `build status` 识别影响面 → 重建 → verify/check；共享层或影响面不清走 `build all --force` + `build check`。`build check` 只证明产物与状态一致，不替代重建。变更、manifest、`build_state.json` 与相关文档同一提交，`vectorizer/output/` 不入库。
- **消费闭环**：chunks 变化 → DVG + 重灌 + 目标实例真实问答；独立 JSON 变化 → 重启消费者 + 验证，不无条件重灌。数据侧输出是 Java 侧输入唯一事实源。
- **事实源**：KN/AKN 源登记库是唯一问题事实源，模板只规定条目格式，不产生第二份问题清单。
- **角色映射（缺项即打回）**：
  - **architect**：方案文档必填分层排证结论（主责层、因果链、修复落点、端到端验收方式）；不填不出方案。
  - **coder**：提交说明必填构建证据（status/重建/check 指纹）与消费证据（重灌/重启 + 被测实例标识）；只有局部绿不算交付。
  - **tester**：必查原问题端到端复现，消费类修复必须在真实加载新产物的实例上验证，不接受「应该已生效」。
  - **主 Agent**：验收时逐条核对上述证据，缺项即打回，不因「改动很小」豁免登记最小字段和闭环证据。
  - **轻量任务**可简化角色链（省 architect），但不豁免登记最小字段与闭环证据，简化理由记入 mission notes。

## 派单规范（主 Agent 遵守）

子代理看不到主会话对话历史，派单任务描述必须包含：

1. 任务目标与背景（自包含）；
2. 相关文件路径（方案文档、被测对象、参考文档）；
3. 项目红线摘要（如：基线文件不可改、利用已有扩展点禁止业务特判、Java 命名/注入规范、cicd 统一验收入口）；
4. 期望的交付物形态（落盘路径 / 最终消息格式）。

## Tower 模式映射（2026-09-24 固化，用户拍板）

Tower 模式下工作以 mission 为单位并行推进（各自独立 worktree + 分支），角色映射与强制动作如下：

| 环节 | Tower 形态 | 强制要求 |
|------|-----------|---------|
| architect | 方案 mission（只读调研 `survey`，或产出方案文档的 build mission） | **有设计空间的任务必须先出方案再实现**：跨模块改动、数据库迁移、鉴权/安全、新工具/新功能、召回或检索语义变更。方案落 `docs/design/`，用户拍板后实现 mission 才开工 |
| coder | build mission worker | 交付须含结构化报告：改动文件清单、任务逐条对照、自测与验证证据、已知未覆盖点（不许隐瞒） |
| tester | **reviewer 必须是 tester 角色** | 评审任务书必须写明按本文件「角色」节的 tester 职责执行：黑盒真实调用验证 + 审计 worker 的测试代码 + 白盒补边界条件 + 缺陷分 Blocker/Major/Minor 三级 + 明确结论。**只审代码不算通过** |
| 主 Agent 验收 | 塔合并（`TowerMerge`）+ 验收汇总 | 每批全部合并后由塔出验收汇总：对照验收标准逐条核对 + tester/reviewer 结论摘要 + 明确通过/打回。验收反馈落 `docs/handover/` |

补充硬性条款：

1. **轻量任务可按「分级触发」简化**（配置修改、文档更新、单文件小改）：可省 architect，但必须有独立验证环节，且简化理由记入 mission notes。
2. **任何流程简化必须写进 mission notes**（随 mission 台账可审计），**禁止静默省略**。
3. **内容类源数据修改红线不变**：worker 不得自行修改 `pf_rules_md_organized/` 的内容类改动；塔须以独立醒目条目报用户单独审批，**禁止混进批量拍板清单**。
4. **评审迭代上限**：同一 mission 评审 5 轮，或连续两轮同类缺陷 → 停下报用户，由用户裁决改派 / 拆分 / 降范围（与「迭代回路」同一精神，轮次上限按 tower 协议执行）。
5. **测试报告与索引登记**：评审结论若产出测试报告，按「交接物」节落 `docs/test-reports/` 并同步登记 `docs/test-reports/README.md`。
6. **共享文件归属**：`pom.xml`、`application.yml`、迁移目录等共享文件在任一时刻只归一个实现 mission 所有，避免并行撞车。
