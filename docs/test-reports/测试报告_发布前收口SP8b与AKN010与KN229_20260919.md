## 白盒审计结果

### 1. 既有测试质量（coder 提交）

- BookFilterTest 7 用例、EmbeddingTimeoutTest 4 用例均为真测试：断言具体（containsExactly、超时毫秒级断言、isInstanceOf(ResourceAccessException)），无 xfail/注释掉的断言/弱断言。
- EmbeddingTimeoutTest 使用真实本地 HttpServer 延迟响应 + `ApplicationContextRunner` 验证 @Value Duration 绑定落到 OllamaApi 底层 request factory，质量高。
- SearchServiceTest +2 用例覆盖两条接入路径。

### 2. BookFilter 边界审计结论

- **大小写**：`toLowerCase(Locale.ROOT)` 双侧归一，大小写边界真实覆盖（含 Turkish-i 陷阱规避）。
- **空白**：metadata 侧 `trim()` 覆盖（补测证实 " CRB " 命中）；**配置侧 books 条目未 trim**——含首尾空白的配置项会被静默归一成带空格串、永远不匹配（见缺陷 D-3）。
- **全半角**：仅大小写归一，不做宽度归一。全角 "？" 不被黑名单 "?" 剔除（补测钉死）。当前数据侧 92 条 `?` 为 ASCII（KN228），无实际影响；若未来出现全角问号需另登记。
- **whitelist + 空 books 列表**：行为为「全部已知书剔除、未知值按 unknown-book-keep」，实现与类注释口径一致、合理（空列表=已知书集合为空），补测已钉死。
- **metadata 缺 book_abbreviation 键**：归为未知，默认 unknown-book-keep=true 保留，防假缺口，合理。
- **黑名单剔 "?" 对检索的影响**：feat 库 92 条 `?` chunk 被剔。这 92 条是 KN228 裁定的「page_1367 超魔专长一览混排无法单一归书」设计保留项，内容本身可检索（专长正文在），被剔的是混排列表 chunk。符合方案 J4 过渡拍板（黑名单剔确定脏值，清洗完成前不误伤）；冒烟中专长问答正常召回，未见影响。建议：数据侧完成清洗后切换 whitelist 时再评估一次召回。
- **接入位置**：search（blank 剔除后、排序 limit 前）与 searchByMetadata（合并去重后、排序分页前）均正确，被剔条目释放 topK 名额，语义正确。getByChunkId 点查不过滤，符合设计（按 id 精确取回不应静默丢条目）。

### 3. EmbeddingConfig 超时审计结论

- **@ConditionalOnMissingBean 接管真实性**：EmbeddingConfig（用户配置）先于 OllamaAutoConfiguration 注册，其 OllamaApi 生效、自动装配回退（既有 hasSingleBean 断言 + 自定义超时值落到 bean 上双重证据）。补测进一步核实 **bean 依赖链**：`ollamaEmbeddingModel` 内部的 `ollamaApi` 字段与上下文唯一 OllamaApi 实例同一引用（isSameAs 通过）——超时确实作用在检索实际使用的模型上，非孤儿 Bean。
- **WebClient.Builder 传默认 builder 副作用**：无。embed/chat 均走阻塞 RestClient，WebClient 仅流式路径使用（应用不使用）。OllamaApi 构造器字节码直接解引用该参数，传 null 会 NPE，给默认 builder 是唯一正确做法。
- **read-timeout 120s 与批量导入**：主代码全部 embed 调用点（grep 核实）均为单条文本调用（`embed(String)`/`embed(Document)`），无 `embed(List)` 批量单调用；启动导入 7847 条为逐条 embed，单条远小于 120s，兼容。启动导入仅在向量库文件缺失时发生（本次冒烟实测 8 库全部跳过）。
- **超时语义**：超时→ResourceAccessException→FallbackEmbeddingModel 降级链成立（慢服务器实测 200ms 超时在 2s 休眠结束前触发）。
