日期：2026-11-12 ｜ 执行：M37 统一验收（临时实例）｜ 评测 commit：`1acfd3e`（dev/pf-agent 合并 tip）｜

## 结论

- 武僧清规问答 3 次端到端耗时 **33.03 / 25.02 / 27.91 秒**，与 2026-11-10 单次 41.87 秒
  同量级；本轮回答均正常（HTTP 200、9~16 条来源、8 项清规齐全）。
- 拆分后 **LLM 调用耗时占 73%~87%**（3 次 20.37~25.10 秒，6~9 次调用），工具执行占
  13%~27%（3.29~7.85 秒，9~13 次调用），两者之外的服务端开销每次 < 0.1 秒。
- 本报告中的 LLM 耗时是**LLM 调用端到端耗时（含网络）**。当前埋点无法把网络传输与服务端
  生成拆开，因此不能把耗时直接归因于网络；工具耗时是进程内实测，不含网络。
- 本阶段只测量，不做优化。按收益排序的优化建议见 §4。

## 1. 环境与方法

- 统一临时实例：Java 17 + `pf-agent-0.2.0.jar`，端口 **18080**（未占用常驻 8080）；
  PostgreSQL 16 临时容器 `m37-pg`（端口 55432）；`-Duser.home=/tmp/m37` 隔离
  `tool_calls.jsonl`；向量库为 `~/.pf_agent` 的只读副本；本机 Ollama `bge-m3` +
  DeepSeek `deepseek-flash`。
- 每次问答独立新会话，问题固定为「武僧清规有哪些内容？」。
- 数据来源：AKN-023 请求级埋点 `tool_calls.jsonl` 中 `recordType=request_summary`
  记录（`totalDurationMs` / `llmCallCount` / `llmDurationMs` / `toolTotalMs` /
  `toolRounds`）及同一 `requestId` 下的工具明细记录。
- 端到端耗时另由调用方墙钟独立记录，与埋点 `totalDurationMs` 交叉核对（差值 < 60ms）。

## 3. 工具明细

| 轮次 | vectorSearch | keywordSearch | getEntryById | 其它 |
|---|---|---|---|---|
| run1 | 3 次 / 0.85s | 5 次 / **6.55s** | 2 次 / 0.34s | getEntryLinks 1/0s、listDataGaps 1/0.07s、reportDataGap 1/0.04s |
| run2 | 1 次 / 0.25s | 2 次 / 1.46s | **10 次 / 1.58s** | — |
| run3 | 3 次 / 0.56s | 4 次 / **6.56s** | 2 次 / 0.35s | — |

观察：

1. **LLM 是主要成本**：每轮 6~9 次 LLM 调用，累计 20~25 秒；即使工具耗时最低的 run2，
   LLM 仍占 86.6%。
2. **keywordSearch 是主要工具成本**：run1/run3 各 4~5 次调用累计 6.5 秒，且存在同一
   查询族反复检索；run2 改用 getEntryById 逐条取文（10 次 1.58 秒），工具总耗时反而最低。
3. **轮次越多越慢**：run1 工具轮次 8、LLM 9 次，端到端最长；run2/run3 轮次 5。
4. run1 的 `gapReported=true` 表示模型本次额外记录了数据缺口（仍返回 8 项清规与 10 条
   来源），不是缺项或失败；run2/run3 未记录 gap。
5. 每次 API 调用的网络耗时无法从 LLM 端到端耗时中剥离，本报告不把它解释为网络问题。

## 4. 优化建议（按预期收益排序）

1. **减少工具轮次与 LLM 调用次数（收益最高）**：3 次共 21 次 LLM 调用、35 次工具调用。
   在 prompt/工具契约中要求模型对同一批清规一次性并发/批量取文，避免
   「检索→逐条取文→再检索」的串行循环；目标把 5~8 轮压到 2~3 轮。预计直接减少
   多次 LLM 往返，是最主要收益来源。
2. **合并重复检索（次高）**：keywordSearch 在 run1/run3 各 4~5 次、累计 6.5 秒，
   存在同义/子串重复查询。可在请求内对 `(tool, arguments)` 做幂等缓存，或让
   keywordSearch 一次返回同族条目，减少重复执行。
3. **减少逐条 getEntryById 次数**：run2 用 10 次 getEntryById 换取了较低工具耗时，但
   增加了消息体与上下文；可提供批量取文参数（一次传多个 chunk_id），降低调用次数与
   token 增量。
4. **检索侧优化（视第 1~3 项落地后再评估）**：vectorSearch/keywordSearch 单次耗时已较低
   （毫秒级到 1 秒级），优先度低于减少调用次数；不要在未拆分网络前调 embedding/索引。
5. **网络与服务端生成拆分（观测增强，不是直接提速）**：如需进一步归因，可在 LLM 客户端
   记录连接/首字节/完整响应时间；当前埋点只能给出「LLM 端到端（含网络）」。

> 上述均为后续优化建议，本批不改问答行为、不调参、不重跑向量库。
