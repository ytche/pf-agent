## 三、测试代码审计结论

1. **断言有效性**：coder 新增 34 例断言均为行为断言（返回串内容、Mockito verify + ArgumentCaptor 取值、排序结果 containsExactly、isSameAs 身份断言），无 `assertNotNull` 式摆设；错误路径均断言 `verifyNoInteractions(searchService/collector)`，确认未发生副作用查询。
2. **无"为绿而绿"迹象**：多个用例具备反证价值——如 `searchByMetadataQueryAllMergesAndDeduplicatesAcrossStores` 用同 chunk_id 验证库内去重与跨模块各留一条；`searchTitleTokenMatchBoostsChunk` 系列给出 0.65/0.69 的差值构造，排序加权错误即红。
3. **命名瑕疵（Minor，见缺陷 2）**：`searchByMetadataQueryUnknownOrFieldListsAvailableWithoutQuery` 方法名声称测"orFilters 未知字段"，实际覆盖的是"gte level 缺 className"提示；`searchByMetadataQueryLevelComparisonWithoutClassNameReturnsHint` 才是真覆盖。用例本身有效，仅命名误导。
4. **缺口（已由补测闭合）**：coder 未覆盖 J1 截断恰好边界（8000/8001）、J2 lte 未知字段、orFilters-level 无 className、J3 limit 下界、keyword 反向排除、all 跨库短路、offset 越界、book 排序。均非"断言错误"，而是边界遗漏。

## 四、缺陷清单

| # | 分级 | 位置 | 描述 |
|---|---|---|---|
| 1 | **Minor**（留拍板） | `SearchService.java:228-229`（配合 `RetrievalTools.java:132-137`） | J2 `limit` 只钳上界不钳下界：`query.limit=-5` 时 `Math.min(-5, 500)=-5`，`Stream.limit(-5)` 抛 `IllegalArgumentException`；工具层 catch 后把**英文异常原文**返回给 LLM（如 "java.lang.IllegalArgumentException" 系消息），违反方案"错误返回可读提示"约定。对照：J3 的 limit 已做 `Math.max(limit,1)` 下界钳制（RetrievalTools.java:242）。修复成本低（工具层一行 `Math.max(1,…)` 或沿用 J3 写法），但触发概率低（LLM 传负 limit 少见），建议随下一批修。 |
| 2 | **Minor**（留拍板） | `RetrievalToolsTest.java:387`（`searchByMetadataQueryUnknownOrFieldListsAvailableWithoutQuery`） | 测试命名与实意不符：名称称测"orFilters 未知字段自纠"，实际 query 是 `gte={level:3}`，命中的是 level-缺-className 提示分支。orFilters 未知字段路径现由补测 `searchByMetadataQueryUnknownLteField…` + 既有 filters 未知字段用例间接覆盖，orFilters 专属未知字段用例仍缺一个（如 `orFilters={foo:[x]}`）。可改名或补一例。 |

无 Blocker / Major。
