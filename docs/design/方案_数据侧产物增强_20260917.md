## 背景与目标

PF Agent 数据工程（pf_data/phase1/vectorizer/）已有 8 个类目的 chunks.jsonl 产物（法术 4172 / 职业 13922 / 规则 7847 / 装备 5385 / 专长 6032 / 种族 3654 / 背景特性 1222 / 技能 556）。不动手讨论结论摘要：

- **D1（P0）**：专长模块 book 字段存在约 739 条非规范值（23 个中文书名，实测比背景估计的 ~350 条更多）；规则模块 188 条 `book="?"`。修复并在 verify 加断言防回退。
- **D2（P1）**：仿 `spell_list_export.py` 先例，为 feat/race/equipment 导出自描述、带版本的权威清单 JSON，供 Java 侧枚举类工具消费（参考 SpellListService 消费 spell_lists.json 的方式）。
- **D3（P2）**：职业 chunk text 中嵌 markdown 成长表（等级/BAB/强韧/反射/意志/特殊/每日法术），解析为结构化产物；覆盖率不全如实处理。
- **D4（P3，仅评估）**：评估 CHM 源数据（pf_rules_md_organized/）中 FAQ/勘误的实际储量，给"值不值得补录"的结论，不动手。

## 方案设计

### D1 book 脏数据修复（P0）

**修复方式（两类）**：

1. **专长 739 条中文书名 → ASCII 缩写**：在 feat processor 的来源解析链路注入中文→缩写映射表，落点二选一（见备选方案）：
   - **推荐**：扩展 `config/feat_sources.json` 的既有结构——每个 source 条目增加 `abbr_candidates`（中文书名 → 规范缩写），`resolve_source` 通道 1 取箭头段后若无 ASCII 尾部则查表归一。该 config 已是"专长特有来源书补充表"的既定扩展点（feat.py:108-122），`FEAT_SOURCES` 从文件加载，加条目不改代码结构。
   - 映射表内容：从源文件 `> 来源：中文名（English）→ X →` 引用块本身提取规范缩写（23 个书名一一核对源文件登记），新增书需同步在 `verify_feats.py` 登记不变量。
2. **专长 100 条 `?`**：
   - `page_1367.md` 92 条：修复前须先勘察该文件（CLAUDE.md 红线：先理解后向量化，读源文件确认是单来源还是混排）。若单来源 → 登记 FEAT_SOURCES 映射修复；若混排无法单一归书 → 按 KN106 口径登记为设计保留并更新 `--max-book-unknown`（当前 feat invariants 未传 `--max-book-unknown`，需核对默认上限）。
   - `造物专长一览` 8 条：既有 `ApplyFeatCreationSourcePromote` 后处理专管（feat.py:249 注释），沿该扩展点补齐来源或登记豁免。
3. **规则 188 条**：不动（KN195/KN196 已裁定），仅确认 invariants 上限与实测一致（238 ≥ 188 ✓）。

**结构不变量（改处理模块前须列出，源自 CLAUDE.md 约束）**：① chunk 总数不变（只改 book 字段，不重排分块）；② chunk_id/doc_id/component_type 不变；③ book_name_cn/book_name_en 随缩写归一同步填充（保持三字段一致）；④ source_confidence 不变；⑤ 种族/装备/职业/法术等类目不出现新增 `?`。

**verify 断言清单（新增到 verify_feats.py / verify_data_invariants）**：
- `book_abbreviation` 不在中文黑名单（23 个中文书名全量枚举，防回退）；negative test：修复前的样例 chunk（抽样 ≥10 个 chunk_id 硬编码进测试）断言 book 已非中文。
- 专长 `book="?"` ≤ 修复后顶格值（棘轮：修好 page_1367 则上限压到 8+余量；若裁定保留则登记 KN 并写明理由）。
- 规则 invariants `--max-book-unknown` 维持 238 不变。
- pytest：映射表单测（23 个映射逐一断言 config 可加载、abbr 合法 `{2,10}` ASCII、cn/en 非空）。

**重跑与同步影响**：book 字段变更属既有产物改动，必须重跑 `python3 -m vectorizer.cicd verify --category feat`（禁止直跑 pipeline）。重跑后 chunks.jsonl 的 739+ 条 book 字段变化 → Java 侧向量库 `~/.pf_agent/vector_store_*.json` 中对应向量的 metadata 与新 chunks 不一致 → **需要在方案拍板后由主 Agent 安排 Java 侧重灌（reindex）专长类目**，方案阶段不重灌。

### D2 权威清单导出（P1）

新建三个导出脚本，与 spell_list_export.py 同构（独立脚本、幂等、自校验断言、对账报告、产物 gitignore、脚本入库、随类目 output 目录放置）：

- `pf_data/phase1/feat_list_export.py` → `vectorizer/output/专长/feat_lists.json`
- `pf_data/phase1/race_list_export.py` → `vectorizer/output/种族/race_lists.json`
- `pf_data/phase1/equipment_list_export.py` → `vectorizer/output/装备/equipment_lists.json`

**数据源选择**：以各模块 chunks.jsonl 为权威（title + aliases + component_type 过滤主条目类型：feat/race(alt_race)/gear），而非回读 CHM 源 md——与 spell_list_export 不同（法术列表页需从源页解析环级结构；feat/race/equipment 无此结构，chunks 本身即权威清单）。产物字段带 `source_chunk_id` 天然交叉，不丢溯源。

**产物 schema（v1.0，自描述）**：

```json
{
  "version": "1.0",
  "generated_from": "vectorizer/output/<类目>/chunks.jsonl",
  "category": "feat",
  "entries": [
    {
      "name": "寓守于攻", "name_en": "Combat Expertise",
      "book": "CRB", "book_name_cn": "核心手册",
      "component_type": "feat",
      "chunk_id": "feat-xxx",
      "aliases": []
    }
  ],
  "excluded_component_types": ["feat_index", "feat_intro"],
  "stats": {"total": 5000, "by_book": {"CRB": 900}, "chunk_id_null": 0}
}
```

- feat 附加 `prerequisites.raw`（已有结构化字段，白送）；race 附加 `race_type`（若 metadata 有）；equipment 附加 `price`/`slot`（若 metadata 有，先勘察）。
- 名称归一：同 spell_list_export 的 `fold_ws`/`fold_lower` 工具函数抽出到共用模块（如 `vectorizer/exploration/common_text.py` 新小模块）供四个导出脚本复用，避免复制粘贴。
- 自校验断言：entries 数 ≥ 阈值下界（feat ≥ 5000、race 主条目 ≥ 300、equipment gear ≥ 2200，取 invariants 现量的保守 90%）；无空 name；chunk_id 无重复；无 excluded component_type 混入（negative）。

**接入 cicd**：是否把导出脚本挂进 pipeline finalize 链？**推荐不挂**（与 spell_list_export 同待遇：独立脚本手动/发版时跑），避免改动冻结的 POSTPROCESSORS 顺序；但将"产物存在且 version 匹配"加入 verify 链作为软检查（文件缺失只 WARN，防环依赖——导出依赖 pipeline 产物，pipeline 内嵌导出会成环）。

### D3 职业成长表结构化导出（P2）

新建 `pf_data/phase1/class_table_export.py` → `vectorizer/output/职业/class_tables.json`：

1. 扫描职业库 chunks，按 D3 现状的严格正则命中 `class_overview`（表头行 `等级|基本攻击加值|强韧` + 数据行）。
2. markdown 表解析：表头行定 6 个语义列（等级/BAB/强韧/反射/意志/特殊），其后若紧跟纯数字行则判定为法术位环号子表头，剩余列数 = 环数；数据行逐行解析，BAB 保留原文（`+6/+1` 多攻形态，结构化留给 Java 侧或本脚本展开为数组），豁免保留 `+x`，特殊能力文本原样，每日法术 `-`→null、数字→int。
3. 职业键归属：`doc_id` 目录前缀（`核心职业/吟游诗人/...` → `吟游诗人`；变体职业的表归其宿主职业，键冲突时保留多个并记 `doc_id` 溯源）。职业键归一复用 spell_list_export 的 `CANONICAL_CLASS`/`CLASS_ALIASES` 思路（值引用同一常量，抽到共用模块）。
4. 覆盖率如实处理：产物含 `coverage` 字段——`parsed_classes`（成功解析职业清单）、`missing_classes`（对照 `spell_list_export.CLASS_LISTS` 27 职业 + class_overview 中出现的其他主职业，列出无成长表职业及其 doc_id 依据）。缺失职业列清单进对账报告，不编造数据。
5. schema：

```json
{
  "version": "1.0", "category": "profession",
  "classes": {
    "吟游诗人": {
      "source_chunk_id": "...", "source_doc_id": "...",
      "max_level": 20, "has_spell_table": true, "spell_levels": 6,
      "levels": {
        "1": {"bab": "+0", "fort": "+0", "ref": "+2", "will": "+2",
              "special": ["迷魂曲"], "spells": {"0": 4, "1": null}}
      }
    }
  },
  "coverage": {"parsed": ["..."], "missing": [{"class": "...", "reason": "..."}]}
}
```

6. 自校验断言：解析职业数 ≥ 15（实测约 20 个标准职业有"表：XX"形态，下界留余量）；每个解析职业 levels 键连续（1..max_level 无缺级，缺级即解析失败 FAIL）；BAB/豁免格符合 `[+-]\d+` 或 `+N/+M` 形态；非施法职业 `has_spell_table=false` 时无 spells 字段。
7. 与 D2 同待遇：独立脚本、不挂 pipeline、verify 软检查。

### D4 FAQ/勘误评估（P3，仅评估）

交付物为评估小节（本方案附评估结论段落，或独立评估文档），步骤全只读：
1. 全树扫描 `pf_rules_md_organized/`（`grep -l FAQ|勘误|Errata`，含 `【FAQ】`、`> FAQ`、`译注` 等形态），按类目/书分组统计条数与体量（字节数）。
2. 对照 chunks.jsonl 现存 67 条，计算"已入库率"与"源储量/未入库量"。
3. 抽样核对 5~10 处源内容的类型（官方 FAQ / 论坛搬运 / 译注），评估信息价值与整理成本。
4. 输出结论：补录价值（高/中/低）+ 若值得，给出补录路径建议（作为独立 Processor 输入源或 chunks 补充），**本次不实施**。

## 备选方案与取舍

- **D1 修复落点**：备选 A 是新增独立后处理器 `BackfillFeatBookAbbrev`（挂 POSTPROCESSORS 链尾）——被否：POSTPROCESSORS 顺序已冻结（教训 B1），且该链是 finalize 阶段，而来源解析在 processor.resolve_source，后置修补违反单一职责；config 扩展（推荐）走既有 FEAT_SOURCES 加载点，不动链结构。
