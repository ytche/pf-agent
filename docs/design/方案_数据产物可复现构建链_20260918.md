# 方案：数据产物可复现构建链（从 md 到全部产物的权威构建顺序）

日期：2026-09-18 / 状态：**已拍板（2026-09-18）**

> 独立任务，先于 D1~D4（数据侧产物增强）实施。用户原话要点：独立脚本产物必须纳入
> "数据库建库脚本 + 版本更新 SQL"式的完整复现方案，否则不允许独立脚本存在。

## 背景与目标

### 需求（用户原话摘要）

"独立脚本如何保证数据产物按标准流程复现？现在 chunks 可以跑 pipeline 重新生成，
脚本独立的话，将来如何一步一步从 md 生成到最新版本的数据产物？类似建库脚本 + 版本
更新 sql，需要一个完整解决方案才允许独立脚本存在。有没有第三方框架可直接使用？"

### 现状痛点（已核实）

1. **链路现状**：`pf_rules_md_organized/`（源 md，git 管理）→ `python3 -m vectorizer.pipeline --category <cat>` → `chunks.jsonl` + `index.json` → `verify_*` + `verify_data_invariants` 闸口。统一入口 `python3 -m vectorizer.cicd verify --category <cat>` 四步链（cicd/verify.py）。
2. **独立脚本产物**：`spell_list_export.py` → `spell_lists.json` + 对账报告（vectorizer/output/法术/），游离于 pipeline/cicd 之外——**没有任何入口声明"从 md 到 spell_lists.json 的构建顺序"**（全仓 grep 仅脚本自身引用，无 Makefile/编排引用）。
3. **孤儿证据**：phase1 根目录有 5 个 `regen_*_chunks.sh`（regen_feat_chunks.sh 等），内容已收敛为单行转发 cicd verify（决策 B 的教训：双份编排漂移）；后处理链本身已内建进 pipeline finalize（feat_chain.py / spell_chain.py 是 POSTPROCESSORS 组件）。但 spell_list_export 及未来 D2/D3 导出脚本没有等价物。
4. **产物间依赖无声明**：chunks.jsonl →（导出脚本）→ spell_lists.json →（Java 启动）→ vector_store_*.json。谁依赖谁、按什么顺序重放、输入指纹是什么，全部靠人记。
5. **"哪个产物最新"无判定手段**：产物 gitignored（spell_list_export.py:9 注释 F-012 先例），git 里没有指纹记录。

### 目标

- 从 md 源到**全部**数据产物（7 个 cicd 类目 + skill（direct）chunks + 独立脚本产物 + 向量库重灌触发点）有**唯一权威构建顺序**，单命令全量重建、增量重建、`status` 查询。
- 输入变化检测（指纹），不是 mtime 猜。
- 与 cicd 四步链的关系明确（复用而非分叉）。
- 产物 schema version 校验（消费前校验 version 字段，防 Java 侧读到旧 schema）。
- 无重外部依赖引入成本（单机、Python、产物是小 json/jsonl 文件）。

## 第三方方案调研结论

| 方案 | 是什么 | 本项目适配度 | 引入成本 | 结论 |
|---|---|---|---|---|
| **dbt** | SQL 世界数据转换建模框架（DAG、测试、文档） | 低——围绕数仓 SQL/model 语义，chunks 生成是 Python 文件处理，无 SQL 层 | 高：新元数据目录、概念错位 | 不选 |
| **DVC** | 数据版本控制 + 可复现流水线（`dvc.yaml` 声明 stages 的 deps/outs，`dvc repro` 按文件 hash 增量重建，`dvc.lock` 记录指纹） | 中——"声明式 DAG + 内容指纹 + `dvc.lock` 指纹记录"思想完全对口；但它为大文件/远端存储/git 外数据设计，我们的产物已是 gitignored 小文件、单机无远端同步需求 | 中：引入 .dvc/ 元数据、新 CLI、CI 需装 dvc，`dvc repro` 与 cicd 四步链两套编排叠加 | 思想吸收，工具不引入 |
| **doit** | 纯 Python Make（file deps + targets，内容变化增量重建，DAG 执行） | 中高——dodo.py 写 Python 任务，`doit` 自动增量；但任务粒度需要自己包 cicd verify，且新增一个 DSL/依赖 | 中：团队需学 doit 语义，debug 栈多一层 | 备选（见下） |
| **Make** | 通用构建编排 | 低——mtime 非内容指纹，Windows 不友好，无 schema 校验概念 | 低 | 不选 |
| **Alembic 式迁移链** | schema 迁移（版本号 + up/down 脚本链） | 部分对口——"版本更新 sql"的类比核心：**构建步骤本身版本化、按序重放** | —— | 思想吸收：构建定义文件带 build_version，重放即按 manifest 顺序执行，等价于"全部 up 脚本按序跑" |
| **自研轻量 manifest + 编排器** | 声明式构建清单（JSON：产物 → 命令 → 输入指纹 → schema version）+ `vectorizer/build.py` 编排 | 高——与既有"单一事实源（教训 B）"完全同构；零新依赖；Python 实现可直接 import 现有模块复用指纹/断言逻辑 | 低：单文件 manifest + 单模块编排器 + 单测 | **推荐** |

调研依据：[DVC 官方（data pipelines as build system）](https://doc.dvc.org/start)、[DVC GitHub（reproducible pipeline DAG）](https://github.com/treeverse/dvc)、[doit PyPI（incremental builds / DAG）](https://pypi.org/project/doit/)、[dbt/DVC 对比实践](https://pdpspectra.com/blog/dvc-vs-lakefs-data-versioning-when-you-need-what/)。一句话：**DVC/doit 解决的是"多机协作 + 大数据 + 远端存储"的问题，本项目真正缺的是"权威构建顺序 + 指纹 + 版本校验"这一层，自研 200 行内可覆盖，引入框架反而叠加第二套编排。**

## 方案设计（推荐：声明式构建清单 + 轻量编排器）

### 总体结构

```
pf_rules_md_organized/ (md 源, git)
        │  (① 输入指纹)
        ▼
build_manifest.json  ──声明──▶  类目 chunks 构建步（cicd 7 类目走四步链，skill 直跑）
        │                       导出步（spell_list_export 及 D2/D3 未来脚本）
        ▼
vectorizer/output/<类目>/chunks.jsonl  ──▶  spell_lists.json / *_lists.json / class_tables.json
        │  (② 产物指纹 + schema version 校验)
        ▼
vectorizer/state/build_state.json  (指纹快照, git 管理 = "dvc.lock" 角色)
        │
        ▼
Java 侧向量库重灌触发点（标注 build_id，Java 侧比对后 reindex）
```

### 1. 构建清单 build_manifest.json（单一事实源）

落盘 `pf_data/phase1/vectorizer/build_manifest.json`，git 入库。声明式、人可编辑：

```json
{
  "build_version": "1.0",
  "updated": "2026-09-18",
  "defaults": {"cwd": "pf_data/phase1", "python": "python3"},
  "artifacts": [
    {
      "name": "chunks.feat",
      "kind": "category_pipeline",
      "category": "feat",
      "outputs": ["vectorizer/output/专长/chunks.jsonl", "vectorizer/output/专长/index.json"],
      "inputs": ["pf_rules_md_organized/专长/**", "pf_rules_md_organized/*.md"],
      "config_deps": ["vectorizer/config/feat_sources.json", "vectorizer/config/feat_types.json"],
      "schema": {"file": "vectorizer/output/专长/chunks.jsonl", "version_field": null},
      "via": "cicd"
    },
    {
      "name": "lists.spell",
      "kind": "export_script",
      "script": "spell_list_export.py",
      "outputs": ["vectorizer/output/法术/spell_lists.json"],
      "inputs": ["pf_rules_md_organized/职业/**", "vectorizer/output/法术/chunks.jsonl", "vectorizer/output/职业/chunks.jsonl"],
      "schema": {"file": "vectorizer/output/法术/spell_lists.json", "version_field": "version", "expected": "1.0"},
      "via": "direct"
    }
  ],
  "consumers": [
    {"name": "java_vector_store", "type": "external_process",
     "inputs": ["vectorizer/output/*/chunks.jsonl"], "note": "Java 启动时按 build_state.json 的 build_id 比对决定是否重灌"}
  ]
}
```

要点：
- `via: "cicd"` 的步**不重写验证逻辑**，命令就是 `python3 -m vectorizer.cicd verify --category <cat>`（复用四步链，禁止分叉——教训 B 双份编排的直接规避）；`via: "direct"` 的导出步命令为 `python3 spell_list_export.py`。
- 输入分两类：`inputs`（内容进指纹）与 `config_deps`（代码/config 进指纹，pipeline 行为由 config 驱动，config 变了必须重建——D1 修复 feat_sources.json 即此场景）。
- `schema` 段：产物 schema version 校验声明（json 产物查 `version` 字段；jsonl chunks 走 verify_data_invariants 闸口，schema 段只登记）。

### 2. 编排器 vectorizer/build.py

命令：`python3 -m vectorizer.build <all|artifact名|status|check> [--force]`（cwd=phase1）：

- **指纹**：sha256 文件内容哈希，输入集合 = `inputs` glob 展开 + `config_deps` + 脚本自身内容 + `build_manifest.json` 自身。指纹计算复用现成 hashlib，不引依赖。
- **build_state.json**：落盘 `vectorizer/state/build_state.json`（**git 入库**，扮演 dvc.lock 角色——这是"版本更新 sql"的锚点：任何一次产物生成都在 git 留下指纹记录，可回答"当前产物对应哪版源+脚本"）。
- **all**：按 manifest 顺序拓扑执行：类目 chunks 步（按序串行；同类目内无交叉）→ 导出步（依赖对应类目 chunks 输出）。每步执行前比对指纹，未变且产物存在 → skip；变 → 执行，失败即终止（set -e 语义）。
- **增量**：`python3 -m vectorizer.build` 默认增量；`--force` 全量重建（等价"从 md 一步到最新产物"的标准流程，即用户要的"建库脚本全量跑"）。
- **status**：打印每个 artifact 的 指纹状态（fresh/stale/missing）、输出存在性、schema version 实际值 vs 期望值——回答"哪个产物最新"。
- **check**：只校验不构建——schema version 断言 + 产物存在 + 指纹一致性，CI 可挂（见 §4）。
- 幂等性保证：cicd 步与导出脚本本身均幂等；build.py 不重写任何处理逻辑，只做调度+指纹。

### 3. 增量与并行

- 串行拓扑足够（全量重跑分钟级，现有 regen 习惯即串行）；`--jobs N` 留作二期（各类目步相互独立，仅导出步依赖 chunks 步，天然两阶段 DAG）。一期不做并行，避免与冻结的 POSTPROCESSORS/闸口顺序产生调试面。
- 失败的步：终止并打印"已完成 X/Y，失败步：name"，不产生 state 更新（state 只在步成功写指纹）。

### 4. 与 cicd / CI 的关系

- **cicd verify 语义不变**：`--category <cat>` 仍是类目级权威验收。build.py 是"跨类目 + 导出产物"的上层编排，对类目步只调用不替代。
- **CI 集成（建议二期）**：新增可选步骤 `python3 -m vectorizer.build check --all` 挂 CI（校验产物与 manifest/state 一致 + schema version 匹配），防止"改了源 md/脚本却忘重跑产物"的漂移。**一期不动 .github workflow**，先本地落地跑稳。
- **过渡方案（本方案拍板后、全量落地前）**：D1~D4 仍可开工——coder 遵守过渡纪律：凡改动影响某 artifact 的 inputs/config_deps，必须显式重跑该 artifact 的构建步并在 commit message 标注 `build: <artifact>`；build.py 落地后此纪律由工具强制。这回答"排在 D1~D4 之前"的时序问题：理想顺序是先本方案后 D1~D4，但二者不互锁。

### 5. 向量库重灌触发点（声明，不实施 Java 侧）

- build_state.json 顶层含 `build_id`（= 全部指纹的聚合 sha256 + 时间戳）与每 artifact 指纹。
- manifest 的 `consumers` 段声明 Java 向量库消费哪些产物；Java 侧方案负责实现"启动时比对本机 vector_store 的 build_id 与 build_state.json，不一致则提示/触发重灌"。本方案只在 state 中提供 build_id 字段与消费映射，不碰 Java 代码。

### 6. 版本演进（"版本更新 sql"等价物）

- `build_version`（manifest 顶层）：构建定义自身的版本。manifest 结构变更（增删字段、改指纹口径）时 +1，并在 `changelog` 数组登记（日期/变更/影响 artifact 列表）。
- 产物 schema version 校验：manifest 每 artifact 声明 `expected`，`check`/步成功后断言实际 `version` 字段——防"脚本升级了 schema 到 2.0 但 Java 还按 1.0 读"。
- 重放语义：任意历史 commit checkout 后跑 `python3 -m vectorizer.build --force`，按该 commit 的 manifest + 脚本重建产物，state 重新生成——这就是"建库脚本 + 更新脚本按序重放"的完整复现。

## 备选方案与取舍

1. **引入 DVC（dvc.yaml + dvc repro + dvc.lock）**：思想最成熟（内容指纹 + 声明式 DAG + lock 文件），但引入第二套编排与 CLI，CI 需装 dvc；且 DVC 的远端存储/git 外数据模型对本项目是过度设计。**不选，吸收其 lock/fingerprint 思想进自研**。
2. **引入 doit（dodo.py）**：功能对口（增量 + DAG），纯 Python；但任务仍需逐层包装 cicd verify，团队多学一个 DSL，debug 栈多一层，且指纹口径/schema 校验仍要自研。**保留为备选：若自研编排器一期后维护成本显形，可平移到 doit，manifest 结构可基本保留。**
3. **Make/Makefile**：零学习成本但 mtime 指纹不可靠、无 schema 校验、Windows 不友好；与"指纹 + 版本"核心需求错位。**不选**。
4. **把导出脚本全部内建进 pipeline finalize（消灭独立脚本）**：从根上消除"独立脚本"问题；但 spell_list_export 先例已拍板"脚本入库、产物 gitignored"，且 D2/D3 新增导出若全走 POSTPROCESSORS 会触碰冻结链顺序（教训 B1），export 依赖跨类目 chunks（法术列表依赖职业库 chunk_id 交叉，pipeline 单类目跑无法表达跨类目依赖）。**不选作为唯一方案；可作为单类目不跨类目导出步的远期归宿。**

取舍核心：**本项目缺的不是执行引擎（cicd verify 已是权威执行），而是"权威顺序 + 指纹 + 版本锚点"的声明层**。声明层自研最薄，且与既有"单一事实源"教训直接对齐。

## 风险与缓解

| 风险 | 缓解 |
|---|---|
| build.py 成为"第二套编排"漂移源（重蹈教训 B） | 类目步唯一命令就是 cicd verify；build.py 只做调度/指纹/校验，不含任何处理逻辑；单测断言 manifest 中 via=cicd 步的命令串与 cicd/verify.py 装配表一致（防手工抄错） |
| 指纹口径漏依赖（改了 X 没触发重建） | inputs/config_deps 两段式 + 脚本自身入指纹；`status` 暴露每步指纹明细便于审计；一期可接受保守策略：git diff 与 status 双看 |
| build_state.json 入库后与产物漂移（state 说 fresh 但产物被删/改） | state 同时记录每产物内容 sha256，`status`/`check` 发现产物哈希不符即报 stale；CI 二期挂 check 兜底 |
| 全量重建耗时被低估导致没人敢跑 | 现状 regen 脚本已被接受（决策 B 后日常使用）；--force 提供标准全量路径并打印耗时 |
| manifest 手写维护负担 | 仅新增/删除 artifact 时编辑（低频）；单测校验 manifest 结构（必填字段、路径存在、category 合法） |
| 冻结红线 | 不动 cicd verify 四步链语义、不动 POSTPROCESSORS 顺序；manifest 与 build.py 均为新增文件；CI workflow 一期不改 |

## 验收标准草案

1. `python3 -m vectorizer.build status` 能列出全部 artifact（9 个：7 cicd 类目 + skill + spell_lists）及其 fresh/stale/missing 状态、schema version 实际值。
2. 连续两次 `python3 -m vectorizer.build`（无改动）：第二次全部 skip，退出码 0。
3. 修改任一输入（如 touch+改内容 `pf_rules_md_organized/专长/` 下任一 md）后 status 显示对应 artifact stale，`python3 -m vectorizer.build` 只重建受影响步，其余 skip。
4. 修改 `vectorizer/config/feat_sources.json` 后 status 显示 chunks.feat stale（config_deps 指纹生效）。
5. `--force` 全量重建：7 类目经 cicd verify 四步链全过 + skill 直跑、spell_lists 自校验断言通过，产物重生成。
6. schema 校验：手工把 spell_lists.json 的 `version` 改为 `"0.9"`，`build check` 非零退出并指明文件与期望/实际版本。
7. build_state.json 入库且内容含 build_id + 每 artifact 输入/产物 sha256；git 历史可回溯任一 commit 的指纹。
8. 单测：manifest 结构校验、cicd 命令串一致性断言、指纹计算（改内容→变、改 mtime→不变）、拓扑排序（导出步在依赖类目步之后）。
9. negative test：manifest 指向不存在脚本/产物路径 → build 在装载期报错退出，不静默跳过。
10. 与 D1~D4 的衔接：manifest 中为 D2/D3 预留的 artifact 条目可在其实施时按同一模式追加（验收以"追加一条 manifest 条目 + 脚本入库"为完成定义）。

## 实施步骤建议

1. **批 1（核心）**：`vectorizer/build_manifest.json`（先登记 7+skill 类目 + spell_lists）+ `vectorizer/build.py`（status/build/check/--force）+ 单测；git commit。可与任何只读工作并行。
2. **批 2（衔接）**：D1~D4 实施时，新导出脚本（feat/race/equipment 清单、class_tables）按本方案模式各追加一条 manifest 条目；D1 修复 feat_sources.json 后通过 build 触发 chunks.feat 重建验证指纹链。
3. **批 3（加固，二期）**：CI 挂 `build check`；`--jobs` 并行；Java 侧 build_id 比对消费（属 Java 方案）。

单命令摘要（给 coder 的验收路径）：
