## 背景与目标

PF 1e 规则问答 Agent 现有 4 个检索/记录工具（RetrievalTools.java）。产品反馈评估产出 J1–J7 改进清单（优先级 P0→P3），本方案覆盖全部七项，其中：

- **J1 getEntryById（P0）**：按 (module, chunk_id) 点查完整原文，绕过 vectorSearch 800 字符截断；
- **J3 listDataGaps（P0）**：只读读取 data_gaps.jsonl，防重复上报缺口；
- **J2 searchByMetadata 增强（P1）**：or / 比较运算符 / sort / limit+offset / 跨模块；
- **J4 book 白/黑名单（P1）**：检索按来源书过滤，需处理脏数据过渡期；
- **J6 条目引用链（P2，已泛化）**：不止法术——全模块"见 XX"式条目引用解析，分层落地（Layer 0 元数据解析 → Layer 1 离线抽取入 metadata → Layer 2 完整引用图），推荐 Layer 0 + Layer 1；
- **J7 keywordSearch（P3）**：先跑"精确术语查询失败率"实测探针（不变），并附 BM25 四条实现路线的成本分析供选型拍板，**本期不实现工具**。

红线：新工具均为增量，不动检索/回答核心编排语义；测试基线 287 全绿只增不减；风格遵守 camelCase、方法按访问级别排序、@Autowired 字段注入。

### 引用链数据勘察（2026-09-18 实测，pf_data/phase1/vectorizer/output/*/chunks.jsonl）

**① aliases 覆盖（顶层字段，非常驻 metadata——mapper 已映射入向量库）**：

| 模块 | chunks | aliases 非空 | 其中含中文 |
|---|---|---|---|
| 法术 | 4172 | 4171（99.98%） | 9 |
| 专长 | 6032 | 5925（98.2%） | 26（多为英文原名，如 "COURAGE IN NUMBERS (TEAMWORK)"） |
| 职业 | 13922 | 9247（66.4%） | 9086（中文别名覆盖最好） |
| 装备 | 5385 | 4515（83.8%） | 54 |
| 种族 | 3654 | 2654（72.6%） | 20 |
| 规则 | 7847 | **0** | 0 |
| 技能/背景特性 | 556 / 1222 | 大部分非空 | 少量 |

结论：title（中文）+ aliases（多为英文原名）已构成跨语言条目名索引；规则模块无别名但 title 即条目名（章节名），Layer 0 解析可行。

**② 文本"见 XX"式引用形态与密度**（正则抽样，剔除"见后文/见原书/看见"类噪声）：

| 模块 | 可解析跨条目引用（估） | 典型句式 |
|---|---|---|
| 法术 | ~150（另有 257 条 mythic 链走 base_spell_* 结构化字段） | "（见进阶玩家指南…）" |
| 专长 | ~100 | "（见法术赎罪术说明）" |
| 规则 | ~360（多为"见核心规则书454页"页码型） | 页码型为主，条目名型少 |
| 职业 | ~340（含 "见传送术Teleport" 等真条目引用） | "（见传送术Teleport）" |
| 装备/种族/技能/背景特性 | ~600 合计 | 页码/章节型为主 |

噪声比高："见"字命中 5300+ 处，真条目引用占比 **<20%**（页码型"见本书 N 页"无法解析为条目）。纯文本在线抽取收益低、误抽风险高——**Layer 1 应离线做、带人工/规则校验**。

**③ base_spell_* 缺失根因（数据存在，schema 未带上）**：
- 数据侧：`postprocess/spell_chain.py`（L159–210）已向 **257 条** mythic 法术 chunk 写入顶层 `base_spell_chunk_id/title/book`（法术/chunks.jsonl 实测 257 条命中）；另有 `subschool_variants` 1 条。
- Java 侧断点：`SpellChunk.java` L13 注释明言"忽略未知字段（如后续向量化版本新增的 base_spell_chunk_id 等）"——record 白名单丢弃顶层字段，`SpellChunkMapper.java` L22–28 的 metadata 映射（chunk_id/doc_id/title/book/aliases…）不含 base_spell_* → 线上库无此键。**修复成本低：SpellChunk record 加 3 字段 + mapper putNonNull，复用 SpellMetadataReplayTool 重放即可**。
- 另有现成的**结构化引用信号未利用**：专长 metadata `prerequisites`（3390/6032 条非空，自由文本，内嵌其他专长/属性名）；法术 `spell_level.class`（法术→职业结构化多对多）；法术 `domains`（法术→领域）。这些走 Layer 0 即可解析一部分。

**④ 向量匹配的现有能力（不建引用图）**：P0-B2 的 title/aliases 词元加权（SearchService.java L99–103、L265–271）已能把"查询词元命中 title/aliases"的条目加分 0.05 抬升，但只作用于**排序加权、不做精确解析**——LLM 拿不到"该条目引用了谁"的显式结构。J7 探针会量化这条路还剩多大缺口。

## 方案设计

### 通用约定

- 所有新工具仍为 `@Tool` 方法加在 `RetrievalTools`，返回字符串、命中走 `collector.add` 挂溯源，错误返回可读提示（对齐 v1.5 B1 惯例）。
- 新配置全部挂 `pf.search.*` / `pf.gaps.*`，带 @Value 默认值兜底（对齐 yml 注释惯例）。
- **J2/J4 触发的工具描述（@Tool description）与 PromptBuilder 引导改动属于"回答链路 prompt 变更"，需重跑评测集**（见风险节）。J1/J3/J6/J7 不触发。

### J1 getEntryById（P0）

点查完整原文，给 LLM 一个绕过截断的通路：

```
@Tool getEntryById(
  @ToolParam String module,     // 同 VALID_MODULES
  @ToolParam String chunkId)    // 工具返回中的 chunk_id
```

实现：
- `SearchService` 新增 `public Document getByChunkId(String module, String chunkId)`：对目标 store 构造 `filterExpression = eq("chunk_id", chunkId)` + `similarityThresholdAll()` + topK 1，返回首条或 null。走现有 FilterExpressionBuilder 通路，**不新增 store 访问机制**。
- 返回格式：`标题 / 来源(书+缩写) / 模块 / 完整正文（不截断，但受 pf.search.entry-result-chars:8000 上限保护，防 oversize chunk 爆上下文）` + `[#N]`。
- 工具描述引导："拿到 vectorSearch/searchByMetadata 命中但需要**完整原文**（如全文条款、表格）时使用；chunkId 必须来自此前工具返回结果的 chunk_id 字段"。vectorSearch 的 formatFragments 输出中**补充打印 chunk_id**（当前 formatFragments 只打标题/来源/内容，未暴露 chunk_id；formatCompact 同样补一行），否则 LLM 无从拿到点查入参。
- 未命中返回可读提示："该 (module, chunkId) 无匹配条目，chunk_id 需来自检索结果"。

### J3 listDataGaps（P0）

```
@Tool listDataGaps(
  @ToolParam(required=false) Integer limit,     // 默认 pf.gaps.list-default-limit:20，上限 100
  @ToolParam(required=false) String keyword)    // 对 question/reason 子串匹配，可空
```

实现：
- `DataGapRecorder` 同包新增读取方法（或拆 `DataGapReader` @Component，复用 `pf.gaps.file-path`）：反向读 JSONL（最新在前），逐行 Jackson 解析，keyword 命中过滤，limit 截断；文件不存在/为空返回 "暂无数据缺口记录"。单行损坏跳过并计 warn（不整体失败）。
- 返回紧凑列表：`时间 | question | reason` 每行 ≤ 120 字符截断。
- PromptBuilder 追加引导："调用 reportDataGap 前，先用 listDataGaps 检查是否已有相同缺口记录，避免重复上报"。
- **只读，绝不写**；reportDataGap 行为不变。

### J2 searchByMetadata 增强（P1，已拍板：一次全放开 + 参数对象）

**拍板意见（2026-09-18）**：or/范围/排序/分页/跨模块一次全放开，但扩展参数必须收敛为**参数对象**，一个 @Tool 方法不摊多参数。修订后设计：

```
@Tool searchByMetadata(
  @ToolParam String module,                  // 单模块；或 "all" 跨模块（新）
  @ToolParam MetadataSearchQuery query)      // 参数对象（见下）

// com.pfagent.agent.rag.MetadataSearchQuery（POJO，Jackson 反序列化驱动）：
record/class MetadataSearchQuery {
  Map<String, String> filters;               // AND 精确条件（沿用旧语义，可空）
  Map<String, List<String>> orFilters;       // 组内 OR：{book:[CRB,APG]}（可空）
  Map<String, String> gte;                   // 比较下限：{level:"3"}（可空）
  Map<String, String> lte;                   // 比较上限（可空）
  String sortBy;                             // title|level|book，可空=默认序
  String sortOrder;                          // asc|desc，默认 asc
  Integer limit;                             // 默认 pf.search.metadata-default-limit:50，上限 enumeration-top-k
  Integer offset;                            // 默认 0
}
```

兼容性决策：旧 `filters` 第二参数并入 `query.filters` 字段——**原签名 `searchByMetadata(String module, Map filters)` 废弃**（同一方法名改签名，旧参数形态由 query.filters 承接；@Tool schema 由 Spring AI 从 POJO 生成，LLM 侧无历史包袱，向后兼容只对内部调用方有意义，而唯一调用方是 LLM 工具循环，无内部代码调用）。

实现要点：
- **校验在工具层**：query 为 null 时按空查询处理（返回"请提供至少一个过滤条件"可读提示）；字段名校验沿用 `filterTranslator.availableFields(module)` 白名单（module="all" 时取八模块字段并集），未知字段返回可用字段清单让 LLM 自纠（对齐既有惯例）。
- **FilterTranslator 扩展**：translate 方法签名改为接收 MetadataSearchQuery（或新增 translateQuery），输出升级为"条件组"结构——AND 组 + OR 组 + GTE/LTE 组，由 SearchService 用 `builder.and/or/gte/lte` 组装。字段名仍全部经翻译层映射为扁平键，**LLM 永不接触 FilterExpression 字符串**（防线不变）。spell 的 level 比较沿用组合键逻辑（须带 className，gte/lte 作用于 `spell_level_<职业>`）。
- **orFilters 用 builder.or(eq...) 或 builder.in(key, values)**（SimpleVectorStore/PGVector 均支持 IN）；gte/lte 用 builder.gte/lte（值为字符串数字可比较）。
- 跨模块 "all"：`resolveStores` 已有；命中合并后**按 (module, chunk_id) 去重**，limit/offset 在合并后施加，formatCompact 行首补模块名。
- sort：内存排序（结果集 ≤ enumerationTopK=500，不改检索语义），title 字典序、level 数值序（spell 取第一个 spell_level_* 值）、book 字典序；非法 sortBy/sortOrder 返回可用值清单。
- **空结果回退策略**：空结果时返回文本固定附引导——`"无命中。建议：减少一个过滤条件（如去掉 book）或改用 vectorSearch；确认数据缺失再 reportDataGap"`，不自动改写查询（自动改写属编排语义，红线不动）。
- **PromptBuilder 引导**：① 过滤条件从宽到窄，一次只加一个条件；② orFilters 用于"多本书/多个值任一命中"，不要用它代替枚举；③ level 比较必须带 className；④ 无结果先放宽再转 vectorSearch，勿直接 reportDataGap。
- limit 默认 50 + metadata-result-chars 截断双保险（防 F-002 类 26K 字符复发）。

### J4 book 白/黑名单过滤（P1，数据脏期过渡）

配置驱动，检索侧默认开启：

```yaml
pf:
  search:
    book-filter:
      enabled: true          # 总开关
      mode: blacklist        # blacklist | whitelist
      books: ["?", "怪物"]    # 黑名单示例：脏值/低质书
      unknown-book-keep: true # 命中脏值/未知书（如中文书名混入缩写位）时是否保留
```

- 实现位置：`SearchService.search` 与 `searchByMetadata` 结果流上统一加 `BookFilter`（新 @Component，@Autowired 进 SearchService）：按 `book_abbreviation` metadata 判断。白名单模式下未知/脏值条目**默认保留**（`unknown-book-keep: true`），黑名单模式下同样保留（黑名单只剔除列名值）。
- **脏数据期过渡 rationale**（实测：feat 中文书名混入 ~391+ 条、rule `"?"` 188 条、「怪物」843 条）：若直接按"缩写白名单"硬剔，这些条目会全部消失造成假缺口；故过渡期用黑名单剔除确定的垃圾值（`?`），中文书名条目保留并计入 `~/.pf_agent/book_dirty_report.jsonl`（启动时或检索时惰性采样记录，供数据侧修复清单），待数据侧清洗完成后（feat 缩写位修复、rule `?` 回填）再切 whitelist 模式。
- LLM 侧不暴露 book 过滤参数（防 LLM 自行构造书名单出错）；这是**全局检索策略**，走配置而非工具参数。
- Prompt 不改动（LLM 无感知）；但白/黑名单切换会改变检索结果 → 触发评测重跑（见风险节）。

### J6 条目引用链（P2，已泛化：全模块引用解析）

**拍板意见（2026-09-18）**：引用链能力不局限法术——"原文规则上各模块都有引用，把这个能力提供给 Agent"。基于 2026-09-18 逐模块勘察（见"引用链数据勘察"节），原"法术引用链"方案作废，重写为分层设计：

#### Layer 0：纯元数据解析（零数据侧依赖，本期落地）

不抽取任何文本引用，只把**已入 metadata 的结构化关系**暴露成工具能力：

1. **跨模块条目名点查（核心增量）**：新建 `EntryResolver`（@Component）——启动时从八个向量库构建内存索引 `标题/alias（大小写不敏感、全半角归一）→ (module, chunk_id)`（spell 4172 + feat 6032 + class 13922 + … 共 42790 条，索引体积估 <10MB）。能力：
   - 供新工具 `resolveEntry(name)`：LLM 拿到 "见 XX" 中的名字（或用户口语名）→ 返回精确命中条目的 (module, title, book, chunk_id)；多义时返回候选清单。命中走 `collector.add` 挂溯源。
   - 供 searchByMetadata 的 spell className 解析、J7 的子串匹配复用（一处索引多处用）。
2. **已结构化的模块内引用**：
   - 法术 mythic 链：`base_spell_*` 257 条（修复 SpellChunk record + SpellChunkMapper 映射 + metadata 重放后可用）；
   - 法术→职业：`spell_level_<职业>`/`has_spell_<职业>` 已是显式边；
   - 专长→专长：metadata `prerequisites` 3390 条非空，用 EntryResolver 做名匹配解析出"前置专长"边（自由文本，仅解析能精确匹配的片段，匹配不上不硬解析）。

新工具签名：

```
@Tool getEntryLinks(
  @ToolParam String name,              // 条目名或 chunk_id（module 可选参数辅助消歧）
  @ToolParam(required=false) String module)

返回: 该条目的三层链接（各有则列、无则省略）：
  - 基础/变体（base_spell_* 解析）
  - 引用它的（反查：哪些条目 prerequisites/文本引用了它——Layer 0 只覆盖 prerequisites 与 spell_level 反向）
  - 它引用的（prerequisites 解析出的条目、职业环级表）
每条给 title + module + book + chunk_id，LLM 可继续 getEntryById 拿原文。
```

成本：纯 Java 增量（EntryResolver + 工具方法 + SpellChunk 三字段），零数据侧新产物；索引构建一次（@PostConstruct，扫 42.8K 条 metadata，<1s）。**这是"给 Agent 引用能力"的最大收益/成本比**。

#### Layer 1：离线文本引用抽取入 metadata（数据侧批次，中期）

数据侧离线跑抽取脚本（复用 spell_chain.py 的 postprocess 模式）：对 chunks.jsonl 文本做"（见 X）/详见《Y》"模式抽取 → 用全库 title/aliases 做候选校验（仅保留精确/别名命中，<20% 噪声可滤掉）→ 写回 chunk 顶层 `entry_links: [{name, target_chunk_id, module}]`（或失败时仅存 name）→ Java 侧 mapper 白名单加字段 + metadata 重放。LLM 侧零改动（getEntryLinks 透明多出一层"文本引用"）。

成本：数据侧脚本 + 一轮人工抽检（估全库真条目引用 1000–1500 处，抽检 100 条即可估精度）；Java 侧成本同 base_spell_* 修复。收益：覆盖"见传送术Teleport"这类 Layer 0 解析不了的边。**推荐做，但排在 Layer 0 之后**（Layer 0 上线后看 listDataGaps/tool_calls 里引用类问题占比再启动）。

#### Layer 2：完整引用图（不推荐，记录备查）

离线建图数据库/邻接表 + 图上问答（多跳路径如"专长 A 的前置链"）。成本：数据侧建图管道 + 存储 + 查询服务，收益对"规则问答"边际低（引用链 1–2 跳已覆盖产品诉求）。**不立项**。

#### 落地路径与 prompt 引导

- **SP8a/c 实现 Layer 0**（EntryResolver + resolveEntry + getEntryLinks + SpellChunk 三字段修复）；Layer 1 立项与否由 Layer 0 上线后的工具调用统计决定。
- PromptBuilder 引导："拿到条目名但不知道它在哪个模块/需要引用链（变体、前置、谁引用了它）时，用 getEntryLinks；拿到 chunk_id 需要原文用 getEntryById"。

### J7 keywordSearch（P3，选型成本分析 + 实测探针，本期不实现工具）

分两步：先跑**实测探针**（原有设计不变），再按探针结论与下方成本分析拍板选型。

#### 第一步：实测探针（主代码零改动，可立即执行）

1. **样本**：从 `~/.pf_agent/tool_calls.jsonl` 抽取全部 vectorSearch/searchByMetadata 调用 join `data_gaps.jsonl`/`annotations.jsonl`；另构造精确术语集 200 条（法术/专长/装备确切中文名，取自 spell_lists.json 与 feat title 全量，自动生成 + 人工抽检）。
2. **执行**：200 条术语逐条跑 `search(term, 对应模块)`，"失败"= 确切条目 title 未出现在 topK（以 chunk_id 比对）；记录 rank、相似度、被谁挤占（rankedScore 分解）。
3. **对照**：同一批术语跑 title/aliases 子串匹配原型（一次性脚本，扫 store metadata）。
4. **判定线**：vectorSearch 失败率 >15% 且子串原型 <5% → 确认缺口，进入选型；否则记录结论关闭 J7。
5. 产物：`qa/keyword_gap_probe.py` + `qa/keyword_gap_report.md`。

#### 第二步：选型成本分析（四路线）

**语料基数（2026-09-18 实测）**：八模块 42,790 chunk，正文合计 ~1200 万字符（avg 264 字符/条）；向量库持久化 JSON 共 614MB（主要是 embedding，与下列索引相互独立）。

| | ① Lucene 嵌入式 | ② PG 全文检索 | ③ 纯 Java 内存 BM25 | ④ title/aliases 子串（近似） |
|---|---|---|---|---|
| 新增依赖 | lucene-core + lucene-analysis-smartcn（合计 ~8–10MB jar） | 无新依赖（SP7 已有 PG）；但中文需 **zhparser/pg_jieba 扩展**（PG 插件，部署/容器镜像成本） | 零依赖（手写或 Apache 工具类） | 零依赖 |
| 索引构建/更新 | 启动时或灌库后全量建一次，落到 `~/.pf_agent/lucene_index/`（MMapDirectory）；数据侧重灌后需删除重建（可挂 metadata-replay 类开关） | chunk 文本**不在 PG**（在 jsonl/向量库 JSON）——需新建"chunk 文本同步表 + tsvector 列"，灌库链路加长；重建靠同步脚本 | 启动时全量构建；内存大，须持久化到磁盘（自研序列化）否则每次启动 20–60s | 复用 J6 EntryResolver 的 title/alias 索引，**零额外构建** |
| 内存/磁盘 | 堆外（MMap），磁盘索引估 30–80MB；堆增量 <50MB | 索引在 PG（磁盘），应用无内存增量；PG 表 +tsvector 约占文本量 1.5–2 倍（~40MB 级） | **最重**：中文需 bigram 才有区分度，12M 字符 ≈ 11M bigram 词元，postings 全量驻堆估 300–600MB；unigram 省内存但中文检索质量差 | <10MB（title+alias 倒排） |
| 中文分词 | smartcn 内置（词典质量中等，规则术语够用）；jieba 需另引 jieba-analysis 及词典文件 | zhparser（SCWS）或 pg_jieba，均非 PG 自带，容器化有额外工序 | 自研 bigram/unigram，无分词依赖，质量下限低 | 子串匹配天然无分词问题 |
| 维护成本 | 中：索引版本与向量库版本需对齐，多一个失效状态 | 高：双写一致性（向量库 jsonl ↔ PG 表）、扩展升级、备份面扩大 | 高：索引格式自研、重建慢、OOM 风险需调优 | 极低：随向量库启动重建 |
| 检索质量 | BM25 全文真排序，覆盖正文任意词 | 同 ① | BM25 裸版，无词频饱和调优时弱于 ① | 只命中条目名/别名，正文内术语查不到（如"触感抑制"写在效果里而非标题） |
| 与现有架构契合 | 好：独立组件，不动 SimpleVectorStore | 差：SP7 引入 PG 是为鉴权/持久化，为检索再造同步链路属过度延伸 | 中：纯进程内，但内存预算与现有单体定位（桌面级部署）冲突 | 最好：与 J6 Layer 0 共用一份索引 |

**推荐**：
- **首选路线 ④ + 已有 title/aliases 词元加权（P0-B2）组合**，作为 keywordSearch v1：成本近零、质量覆盖"用户给出确切术语名"这一主场景（J7 原始痛点就是精确术语查询失败）；
- **若探针证明正文术语缺口真实存在**（如法术效果里被引用的条目名检索不到），再走路线 ①（Lucene 嵌入式）——它是四条路里唯一"真 BM25 全文 + 可控内存 + 生态标准"的组合，索引目录与向量库 JSON 同放 `~/.pf_agent/` 统一生命周期管理；
- 路线 ② 不推荐（为检索把文本搬进 PG 是架构过度延伸，双写一致性是长期债）；路线 ③ 不推荐（中文 bigram postings 300–600MB 堆内存，与 SP6 开源单体/桌面级部署定位冲突，且无分词器的 BM25 质量未必打过 ① smartcn）。
- **决策依赖探针数据**：拍板前建议先跑第一步，用 200 术语失败率决定 ④ 是否够用、① 是否值得引依赖。

## 备选方案与取舍

1. **J1 复用 searchByMetadata 的 title eq 而非 chunk_id 点查**：不选。title 不唯一（变体/同名跨书），chunk_id 才是稳定主键（SpellMetadataReplayTool L88、SourceCollector L110 均以 chunk_id 为 join/去重键）。
2. **J2 让 LLM 直接传 FilterExpression 字符串**：不选。绕过 FilterTranslator 后字段名拼写错误变成底层报错，破坏"错误返回字段清单自纠"的既有防线（RetrievalTools L91–93）。
3. **J4 做成 LLM 工具参数（books 白名单由模型传）**：不选。书名单是产品策略不是用户意图，LLM 构造易错且难审计；配置驱动 + 脏数据报告留痕更可控。
4. **J2 不增强、引导 LLM 多次单条件查询模拟 OR**：不选（实测上会放大工具轮次，max-tool-rounds 10 下循环超限风险；F-002 复盘已有教训）。
5. **J6 检索时在线抽取文本"见 XX"引用**：不选。勘察实测噪声比 >80%（"见后文/见原书/见本书 N 页"），在线抽取误解析会喂给 LLM 假引用链；离线抽取 + title/alias 校验后才入 metadata（Layer 1）。
6. **J6 直接建完整引用图（Layer 2）**：不选。规则问答引用链 1–2 跳已够，建图管道/存储/查询服务成本与收益不匹配。
7. **J7 路线 ③ 纯内存 BM25**：不选。中文需 bigram 才有区分度，12M 字符 postings 全量驻堆估 300–600MB，与 SP6 开源单体/桌面部署定位冲突；路线 ② PG 全文不选（chunk 文本不在 PG，为检索造双写同步链路过度的延伸）。详见 J7 节成本表。
