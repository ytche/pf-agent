## 背景与目标

数据侧 D2 已完成并拍板 ✅（2026-09-22）：`feat_list_export.py` / `race_list_export.py` / `equipment_list_export.py` 三个导出脚本仿 spell_list_export 先例，产出权威全清单 JSON（含幂等 `source_fingerprint`），与 chunks.jsonl 同目录、带对账报告。实测产物：

| 产物 | 路径 | 条数 | 特有字段 |
|---|---|---|---|
| 专长清单 | `pf_data/phase1/vectorizer/output/专长/feat_lists.json` | 4080（全部 component_type=feat） | `feat_type[]`（如 ["战斗","团队"]）、`prerequisites_raw`（694 条为空） |
| 种族清单 | `pf_data/phase1/vectorizer/output/种族/race_lists.json` | 111（全部 race_overview） | `race_group`、`ability_adj`、`bio_type`、`size`、`speed`、`senses` |
| 装备清单 | `pf_data/phase1/vectorizer/output/装备/equipment_lists.json` | 2675（gear 2424 / weapon 141 / armor 110）+ `sections[]`（表碎片说明） | `price`、`weight`、`slot` |

三文件公共 schema（实测 entry0 keys）：`name / name_en / book / book_name_cn / component_type / chunk_id / doc_id / aliases[]`；顶层含 `version("1.0") / generated_from / source_fingerprint(sha256:…，源 chunks.jsonl 指纹) / category / entries[] / excluded_component_types / stats{total, by_book, by_component_type, chunk_id_null}`。装备多一个 `sections[]`（`equipment_intro` + `sunk_table_fragments`，Java 一期**不消费**，见风险节）。

目标：给 Agent 一个枚举工具，回答"专长/种族/装备有哪些（某来源书/某类别/某关键词）"这类权威全清单问题；支持过滤/分页/排序；每条结果带 [#N] 溯源；与 searchByMetadata/vectorSearch 边界清晰。

**工作队列拍板要求**：本方案在「泛化 listEntries(module) vs 按模块分工具」中做决策——**推荐泛化单工具**（见方案设计与备选方案）。

## 现状分析

### 消费先例（均在 `pf_agent/agent/src/main/java/com/pfagent/agent/rag/`）

- **SpellListService.java**：`@PostConstruct load()`（L158–175）启动同步加载、文件缺失/解析失败降级 `available=false` 不炸启动；别名索引 `buildAliasIndex`（L177–187）+ `resolve()`（L67–76）；`@JsonIgnoreProperties(ignoreUnknown = true)` 全容错；结果字符护栏复用 `pf.search.metadata-result-chars`（4000）。
- **ClassTableService**（J5，RetrievalTools L504–536 消费）：同类加载模式；溯源走 `searchService.getByChunkId(module, chunkId)` 点查真实 chunk，未命中降级合成 Document——**B4 溯源直接复用此通路**（J1 已建 `getByChunkId`）。
- **工具注册**：RetrievalTools `@Component` + `@Tool` 方法，`ChatService` `ToolCallbacks.from(retrievalTools)` 反射注册，**新增 @Tool 方法零注册成本**（SP8 已确认先例）。

### 相关工具边界现状

- `searchByMetadata`（RetrievalTools L102–159）：向量库元数据过滤。其余模块可用字段仅 `book / componentType / title`（工具描述 L91）——**做不了 feat_type/race_group/price 等维度**；且元数据缺失/脏值风险已由 spell_level 35% 缺失先例（F-007）证实。这正是 D2 清单要补的洞。
- `getSpellList`（L456–482）：法术清单，输入是**职业×环级**二级嵌套结构，与 feat/race/equipment 的**扁平 entries+过滤**形态本质不同。
- `vectorSearch`：语义片段检索，不负责权威枚举（AKN-001：列举式提问须走直查工具）。

### 参数对象规则

CLAUDE.md L233（2026-09-18 起）：Java 方法参数超过 5 个应收敛为参数对象。`listEntries` 若散参化需 module + keyword + book + type + limit + offset + sortBy ≥7 个——**必须参数对象**。

## 方案设计

### 核心决策：泛化 `listEntries` 单工具（推荐）

**工具签名**：

```java
@Tool(description = """…（见下）…""")
public String listEntries(
    @ToolParam(description = "清单模块: feat(专长) / race(种族) / equipment(装备)") String module,
    @ToolParam(required = false,
        description = "过滤/分页参数对象，全字段可空。无条件时返回该模块统计概览") ListEntriesQuery query)
```

**参数对象**（新 record，与 `MetadataSearchQuery` 同包同风格）：

```java
public record ListEntriesQuery(
    String keyword,              // name/name_en/aliases 子串（大小写不敏感、全半角容错）
    Map<String, String> filters, // AND 精确匹配，可用字段随模块（见下表）
    Map<String, List<String>> orFilters, // 组内 OR，如 book:["CRB","APG"]
    Integer limit,               // 默认 50，硬上限 200（对齐 metadata-default-limit 惯例）
    Integer offset,              // 默认 0
    String sortBy                // "name"(默认) | "book"
) { boolean hasAnyCondition(); }
```

**各模块可用过滤字段**（写进 @Tool description，字段名错误返回可用字段清单让 LLM 自纠——对齐 searchByMetadata L126 先例）：

| module | 可用 filters 字段 |
|---|---|
| feat | `featType`（单项精确；orFilters.featType 多值）、`book`、`hasPrerequisites`("true"/"false") |
| race | `raceGroup`、`size`、`bioType`、`book` |
| equipment | `componentType`("weapon"/"armor"/"gear")、`slot`、`book` |

> `keyword` 独立字段而非 filter：三模块通用且是子串语义，与 AND 精确匹配的 filters 语义不同，混进 filters 会误导 LLM。filters 值统一字符串（race 的 size="中型" 等原文值），实现侧自行比对。

**返回行为**：

1. **无条件（query 空或全 null）**：返回该模块统计概览——`「专长」权威清单共 4080 条，按专长类别：战斗 1xxx、团队 xxx…；按书：CRB 205、APG 170…；请提供 keyword 或过滤条件查看具体清单`。统计直接来自 JSON 的 `stats` + entries 内存聚合（启动时已加载，零 IO）。
2. **有条件**：`序号. 中文名（English）[书] | 属性段 | chunk_id: xxx [#N]` 逐行，属性段按模块：feat→`类别:战斗/团队 | 前置:钢铁意志`（无前置省略）；race→`分组:概述 | 体型:中型 | 速度:20尺`（ability_adj/senses 仅在结果 ≤20 条时附，防长行刷屏）；equipment→`类型:weapon | 价格:6,500 gp | 重量:12`。超 `pf.search.metadata-result-chars`（4000）截断 + 提示翻页（offset），对齐 formatCompact（L719–745）与 F-002 护栏。
3. **无命中**：返回"无命中 + 建议放宽条件或转 vectorSearch"，不回 reportDataGap（对齐 searchByMetadata L155）。
4. **limit 越界**（>200 或 <1）：钳制到合法范围并在返回头部注明（对齐 listDataGaps L375 先例）。

**排序**：默认按 name（中文按 unicode 排序即可，稳定即可用）；sortBy=book 时按 book 再按 name。不暴露 sortOrder（枚举场景降序需求极低，少一个参数少一类错）。

### 新服务：ListExportService

新建 `@Component ListExportService`（与 SpellListService/ClassTableService 同包并列），**一个服务承载三模块**（三 JSON 同构，一个加载器循环三个配置路径）：

- **加载**：`@PostConstruct load()` 遍历三模块 `@Value` 路径（`pf.list-exports.feat-file-path` / `race-file-path` / `equipment-file-path`，默认值对齐 D2 实际落点 `../../pf_data/phase1/vectorizer/output/{专长,种族,装备}/{feat,race,equipment}_lists.json`）；逐模块独立容错——某文件缺失/解析失败只置该模块 `available=false`，不影响其余两模块；启动日志打印各模块解析条数（与 stats.total 对账）+ `source_fingerprint`（数据一致性追溯用，比对 `generated_from` 可知清单对应哪版 chunks）。
- **模型**：`@JsonIgnoreProperties(ignoreUnknown = true)` 全容错（先例 SpellListService L230 等）；公共字段一个 `ListEntry` record，模块特有字段（feat_type/prerequisites_raw/price/weight/race_group/ability_adj/bio_type/size/speed/senses/slot）全部放同一 record 的可空字段（三模块共用一个 record，空字段格式化时省略——字段全集 <15 个，比分模块 record 少两套重复定义）。
- **别名索引**：每模块 name+name_en+aliases → 条目列表（允许同名多书共存，resolve 返回 List 不做唯一约束——与法术清单"职业唯一"语义不同）。
- **过滤执行**：内存 Stream 过滤（三清单合计 6866 条，全量内存，过滤成本可忽略）；keyword 匹配 name/name_en/aliases 子串 + `toHalfWidth` 全半角容错（对齐 keywordSearch 描述承诺）。
- **溯源**：返回的每条 entry 用其 `chunk_id` 走 `searchService.getByChunkId(module, chunkId)` 批量点查（截断前实际展示的条目才挂，对齐 formatCompact"被截断未展示的不标注"惯例）；点查未命中的条目降级合成 Document（title=name，metadata 带 chunk_id/doc_id）——**保证 [#N] 不缺席**，并 warn 日志登记数据一致性技术债务候选（F-002 ② 先例）。
- **不提供运行时刷新**：沿用 SpellListService/ClassTableService 先例（重启加载）；`source_fingerprint` 仅日志留痕。数据侧重跑产物后重启生效。

### RetrievalTools 改动

- 新增 `listEntries` 一个 @Tool 方法（骨架对齐 getSpellList/getClassTable：available 检查 → 空参/未知模块自纠 → 执行 → 挂溯源）。
- @Tool description 写清边界：何时用（"XX 有哪些/全部/清单"式权威枚举、按书/类别/关键词数清单）、何时不用（规则机制/条目正文走 vectorSearch/getEntryById；法术清单走 getSpellList；职业成长数值走 getClassTable；元数据关系反查走 searchByMetadata/getEntryLinks）。

追加一条引导（对齐 J5 引导格式）：

新增工具 + 引导属回答链路 prompt 变更 → **触发评测重跑**（口径：溯源 ≥52/53、诚实 ≥50/53、结构 ≥2.89）。

## 备选方案与取舍

1. **按模块分三个工具（getFeatList / getRaceList / getEquipmentList，各配独立 Service）**：不选。三模块公共 schema 同构（9 个公共字段实测一致），过滤/分页/溯源/容错逻辑 100% 可复用；分工具意味着三份几乎相同的 @Tool description、三个 Service、三套加载配置——工具面膨胀 3 倍而能力零增量。分工具的唯一优势是每工具 description 更短更聚焦，但可用"module 参数 + description 内的字段分节表"达到同等 LLM 可辨性（searchByMetadata 八模块共用一个工具即为成功先例，L71–101）。
2. **泛化工具同时收敛 getSpellList（四合一 listEntries 覆盖 spell）**：不选。法术清单是"职业×环级"二级嵌套（输入是 className+level，不是过滤条件），且 spell_lists.json 结构与三 D2 清单不同（classes 嵌套 levels）；硬塞进统一过滤模型会破坏 getSpellList 已验证的调用体验，改造收益（少一个工具）远小于风险（回归法术枚举链路，需重跑法术相关全部评测）。本期 getSpellList/getClassTable 保持原样，仅在 listEntries description 写明边界。
3. **按 SpellListService 先例每模块一个 Service、复用公共加载器**：不选（相比本方案）。公共逻辑（加载/容错/过滤/溯源）放 ListExportService 内部按 module 分派即可，三个空壳 Service 只是套娃。
4. **消费装备 sections[]（表碎片）**：不选。一期清单枚举以 entries 为准；sections 的 sunk_table_fragments 是数据侧的对账说明（33 个碎片），面向排障而非 Agent 枚举，二期如有"表格行级查询"需求再立项。

## 风险与缓解

| 风险 | 缓解 |
|---|---|
| feat 全清单 4080 条，LLM 要求全量返回刷屏 | 无条件只给统计概览；有条件结果受 metadata-result-chars 截断 + max-limit 200 钳制 + 翻页提示（F-002 护栏先例） |
| 数据侧重跑 chunks 后清单与向量库版本错位（chunk_id 点查未命中） | 降级合成 Document + warn 日志；启动日志对账 stats.total 与解析条数；fingerprint 留痕便于 DVG 登记 |
| race 清单 book 全为 "?"（by_book 实测 111 条全 "?") | 如实展示 book=未知来源（诚实先例）；race 过滤维度靠 race_group/size/bioType；不编造来源 |
| 装备 price/weight 为原文字符串（"6,500 gp"/"—"），无统一数值类型 | 原样展示不解析（忠实查表原则，同 J5"原文返回"）；数值比较类问题引导 vectorSearch |
| 同名条目跨书共存（如多书重印专长） | 不过滤、全部列出并各标 [书]；keyword 命中多条是正确行为 |
| JSON 后续版本微调（version 1.0 → 2.0） | ignoreUnknown 全容错；未知字段不报错；集成时以实际产物对齐 record |
| 新增工具 + prompt 引导 → 回答链路变化 | 触发评测重跑（溯源 ≥52/53、诚实 ≥50/53、结构 ≥2.89） |
| sections[] 不消费但存在于装备 JSON | ignoreUnknown 天然忽略；方案已声明一期范围 |
