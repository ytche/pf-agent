## 2. 实现要点（对照设计决策）

### T1 · `total_rounds` 累计列（修正 SP1 V1 错误假设）

- **V1 注释错误**（`message_rounds 冗余轮数（F-005 裁剪 + SP2 配额复用）`）：F-005 会把 `message_rounds` 钉在 historyRounds=20 上限，不能作累计配额依据。D4 改为新增 `total_rounds` 累计列。
- `V2__add_total_rounds.sql`：`ALTER TABLE chat_conversation ADD COLUMN total_rounds INT NOT NULL DEFAULT 0;`——标准 PG 语法，11+ 在线安全不重写表，含存量数据（真 PG 存量 1 会话 40 条上执行成功，见 §4.1）。
- `JdbcChatMemory.doAdd`：`conversation.setTotalRounds(conversation.getTotalRounds() + rows.size() / 2)`，在 setMessageRounds 之后、**独立于裁剪收窄逻辑**（上方 `total` 变量已被裁剪改写成上限，累计值必须只增不减，故不复用它）。
- 实体构造器 `totalRounds=0`，`@Column(name="total_rounds", nullable=false)`；V2 起 `ddl-auto=validate` 通过（实体 ↔ schema 对齐）。

### T2 · F-010 按 IP 固定窗口限频（RateLimitInterceptor）

- **D1 落点**：`HandlerInterceptor` 注册进既有 WebConfig 链，`addPathPatterns("/api/chat")` **精确匹配**——`/api/chat/feedback` 与 `/api/health` 不在限频范围（非目标）。Auth 在前各自独立 preHandle。
- **D2 算法**：`ConcurrentHashMap<ip, long[]{windowStartMinute, count}>`；`compute` 原子处理窗口重置（`current[0] != windowStart` 则覆盖为新窗口计数 1）。窗口边界至多 2 倍突发，文档声明接受。
- **防膨胀**：活跃键数 > 10 000 时 `cleanupExpiredWindows()` 全量扫除窗口起始非当前分钟的条目。
- **D3 IP**：默认 `getRemoteAddr()`；`pf.rate-limit.trust-forwarded-for=true` 取 `X-Forwarded-For` 首跳（`split(",")[0].trim()`），默认关防伪造。
- **D7 响应**：429 + JSON `{"error":"rate_limited","message":"请求过于频繁，请稍后再试","retryAfterSeconds":N}`（N = 距本分钟结束秒数）。Servlet API 无常量，429 字面量 + 注释。
- **D5 装配**：`@Component @ConditionalOnProperty(name="pf.rate-limit.enabled", havingValue="true")`；WebConfig 用 `ObjectProvider<RateLimitInterceptor>` 可选注册，absent 跳过 = 默认零行为变化。

### T3 · F-011 匿名会话轮次配额（AnonymousQuotaService）

- **D4 计数（两模式统一 = 累计轮、不裁剪）**：封装在 `AnonymousQuotaService`（memory 包）内——`ObjectProvider<ChatConversationRepository>.getIfAvailable()` 非空判 jdbc → 读 `total_rounds`；否则 memory → `chatMemory.get(cid, MAX).size() / 2`（InMemory 无裁剪，条数即累计）。存储细节不外泄。
- **故障降级**：计数查询 RuntimeException 吞掉记 warn 返回 0（放行）——配额是成本护栏，不因配额侧故障挡住问答主链路（对齐 JdbcChatMemory D6 降级风格）。
- **D6 检查点**：`ChatController.chat()` 改返回 `ResponseEntity<?>`；配额服务经 `ObjectProvider` 注入（默认关时 null 跳过检查）。`conversationId != null && !blank && quotaService.isExceeded(cid)` → 429 `{"error":"quota_exceeded","message":"本会话免费额度已用完（N 轮）。请开启新会话继续提问。"}`（N 由配置拼）——**在 `chatService.ask` 之前 fail-fast，超配额不触发 LLM 零 token 成本**。conversationId 为空（新会话）直接放行，不查计数（`verify never isExceeded` 断言）。
- **第 N 轮边界语义**：检查发生在 ask（内部 add）前，故第 20 轮请求开始 used=19<20 放行 → add 累计 20；第 21 轮请求开始 used=20≥20 → 429。第 20 轮正常、第 21 轮被拒。
- **D8 与 F-005 边界**：配额=20 = 保留轮数 20，开启配额后 F-005 实际不会触发（21 轮被配额挡在 LLM 前）；两者独立配置，无耦合逻辑。文档声明。

### T4 · 前端 429 文案

- `index.html` fetch 分支：`r.status === 429` 时解析后端 JSON 抛 `d.message`（专属文案），其余非 200 维持「服务异常，请稍后重试」。

## 4. 真实 PG 冒烟自跑记录（全部亲跑，勿留给验收方）

**环境**：`docker start pf-pg`（复用容器，PG 16.15，库 `pf_agent`，**含 V1 schema + SP1 冒烟存量数据 1 会话 40 条**——正好实测「含存量数据执行 V2」）；真实 DeepSeek API（key 自 zshrc，不落盘不打印）+ 本地 Ollama bge-m3 + 8 向量库加载。`mvn spring-boot:run` 启动，开关经 `--spring-boot.run.arguments` 注入（`PF_CHAT_MEMORY` 等 env 走 Spring 松散绑定）。

### 4.1 场景 A · jdbc + 全关：V2 迁移应用到存量库 + total_rounds 真写 ✅

- 启动日志：`Migrating schema "public" to version "2 - add total rounds"` / `Successfully applied 1 migration … now at version v2`；随后 `Started AgentApplication`，`ddl-auto=validate` 下**零 schema 错误**（实体 totalRounds ↔ V2 列对齐）。
- `\d chat_conversation` → `total_rounds | integer | not null | 0`；`flyway_schema_history` v1/v2 均 success。
- 存量会话基线：`message_rounds=20, total_rounds=0`（V2 默认），40 条消息（满仓）。
- 对其发 1 次真实问答「火球术是几环法术？」→ 200，回答「3环」。
- 查库终态：`total_rounds=1`（写入累计），`message_rounds=20`（满仓裁剪仍钉 20），消息仍 40 条（裁剪删最旧 2 + 新增 2 同事务）。
- → **D4 核心语义真 PG 实证**：doAdd 累加不裁剪；V2 列 Hibernate 读写正确。

### 4.2 场景 B · jdbc + quota 开：配额全链 429 + 新会话放行 ✅

- 前置：`UPDATE chat_conversation SET total_rounds=20` 模拟该会话累计已达配额上限（真实 21 轮累加逻辑 H2 单测已证；真机达 429 无需烧 20 次真实 LLM）。
- 同会话发 1 次 → **HTTP 429**（0.174s fail-fast）：`{"error":"quota_exceeded","message":"本会话免费额度已用完（20 轮）。请开启新会话继续提问。"}`——未触发 LLM（瞬时返回）。
- 新会话（无 conversationId）发 1 次 → **HTTP 200**，正常返回 + 新 conversationId（放行、计数重置）。

### 4.3 场景 C · memory + rate-limit 开（per-minute=2）：固定窗口 429 + 窗口恢复 + XFF 忽略 ✅

- 连发 3 次同 IP：第 1、2 次 200（真实问答），**第 3 次 HTTP 429（0.003s 拦截器拦截）**，body：`{"retryAfterSeconds":25,"error":"rate_limited","message":"请求过于频繁，请稍后再试"}`。
- **窗口恢复**：等待分钟翻转（sleep 16s 至下一分钟）→ 同 IP 再发 **HTTP 200**（新窗口重置）。
- **XFF 忽略**（trust-forwarded-for=false 默认）：带 `X-Forwarded-For: 9.9.9.9` 仍 429——计数走 remoteAddr，XFF 被忽略。

### 4.4 场景 D · memory + rate-limit + trust-forwarded-for=true：XFF 按首跳独立计数 ✅

per-minute=2，两组 XFF 交替：

| 请求 | XFF | 结果 | 解读 |
|---|---|---|---|
| #1 | 10.0.0.1 | 200 | a 桶 =1 |
| #2 | 10.0.0.2 | **200** | b 独立桶 =1（若 XFF 被忽略按 remoteAddr，此刻已累计 2 应 429）——证明 XFF 生效 |
| #3 | 10.0.0.1 | 200 | a 桶 =2 |
| #4 | 10.0.0.1 | **429** | a 桶自身超 2/min |
| #5 | 10.0.0.2 | **200** | b 不受 a 超限影响（独立计数） |

**装配三态总览**：A（jdbc+全关）启 ✓、B（jdbc+quota）启 ✓、C/D（memory+ratelimit 开/关 XFF）启 ✓；默认全关「零行为变化」由 AgentApplicationTests @SpringBootTest（memory 全关上下文）与场景 A（jdbc 全关）双证。

| 项 | 说明 |

| **内存模式真机 429 未跑** | 需同会话真实烧 20 轮 LLM 才达 429，成本不值且无新信息——计数/边界（38→19 未超、40→20 恰达上限、20 轮拒绝第 21 轮）已由 `AnonymousQuotaServiceTest.memoryPath…` + `ChatControllerTest` 单测证明；jdbc 全链真机已验证（§4.1/4.2）。k3 复验 V3「内存一遍」可直接真机或采信单测边界 |
| **真机 21 轮累加未逐轮烧 LLM** | doAdd 累加正确性由 H2 真库 21 轮测试 + 真 PG 1 轮 0→1 实证组合覆盖；达 429 的 21 轮前置用 SQL 设 total_rounds=20 模拟（列语义即累计值，合法等价）。如需逐轮 21 次真问答复验，k3 可自行执行 |
| **XFF 真机单源限制** | 本机 curl 恒 remoteAddr=127.0.0.1，无法构造「同直连不同 XFF」区分桶时 remoteAddr 的净效应；场景 D 以「XFF 不同即独立桶」证明 XFF 生效（若忽略 XFF 会因 remoteAddr 累计提前 429），关闭态由场景 C 证明「带任意 XFF 仍按 remoteAddr」。两侧证据互补 |
| **限频真机窗口恢复等 60s** | 窗口翻转等待属物理时间，真机等待 16s 跨分钟实测一次；多分钟翻转语义由单测 `windowResetOnNextMinute`（改内部 map 模拟，不 sleep）覆盖 |
| **固定窗口 2 倍突发 / 共享出口 IP 误伤** | 方案 §4 已知限制，文档声明，未做耦合处理（D2 接受） |
| **多实例并发写 / 分布式限频** | 单实例内存计数 + 同会话事务，多实例属微服务版范畴，非本批范围 |
