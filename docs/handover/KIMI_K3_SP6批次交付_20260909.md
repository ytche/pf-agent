## 2. 实现要点（对照方案 D1~D7）

### D1 新库整形 → git archive 干净树（非 `checkout --orphan`）
方案建议 `git checkout --orphan` 切干净历史。T6 实测改用 **`git archive` 导出跟踪文件到临时目录再单 commit**，效果等价且更稳：
`git archive` 只导出已跟踪文件 → 天然剔除 `kimi-export-session_*.md`、`.claude/`、`.pytest_cache/`、IDE 文件等 D4 排除项与全部 `.git` 历史（无需临时 checkout 覆盖工作区）。产物 = 无历史继承、含 dev 基线 + SP6 六 T 全部内容的一张干净快照。

### D2 许可与声明三件套
- `LICENSE`（996.ICU 中文）+ `LICENSE_EN`（996.ICU 英文）——代码适用。
- `NOTICE.md`——数据部分单独声明：Paizo Community Use Policy 声明段 + OGL（PF1e SRD）说明 + 中文社区翻译 credit + 「个人学习/非商业社区用途，版权归原作者」+ 异议联系方式。
- README 顶部显著免责段（与 NOTICE 同义）。

### D3 配置外置
`.env.example` 覆盖全部环境变量；README 配置表覆盖 `application.yml` 全键；`docs/DEPLOYMENT.md` 写入**三个已知坑**：① 多 dash 属性 env 绑定不一致（`PF_RATELIMIT_PER_MINUTE` ✗ / `PF_RATELIMIT_PERMINUTE` ✓）；② SP5 `fallback-enabled` yml 显式 false 覆盖「cloud 主默认兜底」设计（需删行或 true）；③ cloud 主通道每次检索每 store 一次 embed 调用（V5② 实测单问 ~60 次）。

### D4 公开范围清单
排除 `kimi-export-session_*.md` / `.claude/` / `.pytest_cache/` / IDE 文件；其余全量公开（docs/handover 过程文档、pf_data 规则数据、qa 评测集均随库发布）。T6 实测核对：导出树 10278 文件，排除清单命中 **0**，`0` 符号链接。

### D5 Docker（与方案有一处偏差，见 §6）
`pf_agent/agent/Dockerfile` multi-stage：`maven:3.9-eclipse-temurin-17` 构建 → `eclipse-temurin:17-jre` 运行，非 root（uid 10001）；根 `docker-compose.yml`：`app`（GHCR 镜像，默认依赖 ollama）+ `ollama`（首启 entrypoint 自动拉 bge-m3）+ 可选 `pg` profile；卷挂 `./data ↔ /home/appuser/.pf_agent` 持久化向量库；无 healthcheck（jre 镜像无 curl，注释说明就绪判定口径）。`.dockerignore` 排除 target/qa 产物。

### D6 CI（与方案有一处命名偏差，见 §6）
仓库已有**数据侧 `ci.yml`**（向量化数据质量闸口，Python vectorizer，paths 收窄 `vectorizer/**`）——Java workflow 不能占用该文件名，故命名 **`agent-ci.yml`**：
- `agent-ci.yml`：push main/dev-pf-agent/feat/** + PR，paths `pf_agent/agent/**`，setup-java temurin 17 + `mvn test -B`。
- `docker.yml`：tag `v*` 或 workflow_dispatch → build-push 推 `ghcr.io/ytche/pf-agent`（semver + latest，GITHUB_TOKEN `packages: write` 内完成，无额外密钥）。

## 6. 遗留与披露

1. **D5 偏差：JRE 17 而非方案草案的 21**。Dockerfile 注释与提交已明示：pom `<java.version>17</java.version>`，`17-jre` 与编译目标一致且更小，运行行为等价。方案 §3 D5 原文写 eclipse-temurin 21，本批取 17 并在 Dockerfile 注释留痕。
2. **D6 命名偏差：Java workflow 命名 `agent-ci.yml` 而非 `ci.yml`**。`ci.yml` 已被数据侧向量化闸口占用（paths 收窄 vectorizer/**），两个 workflow 并存、各自 paths 收窄互不触发空跑。
3. **`ci.yml` 数据闸口随公开库保留（决策点）**：T2 曾预判该 workflow 在干净 clone 上会因依赖 gitignored 产物而失败；T6 实测**意外正向**——源数据已入库，CI 现场跑 pipeline 全绿（§3）。它只在 `vectorizer/**` 改动时触发，对公开库 Java 演进无噪音，但每次触发跑 5 类目全矩阵、占用公开库 Actions 配额。保留与否交用户拍板（默认建议保留：数据 gate 是仓库既有信誉机制，公开后可复现即有价值）。
4. **`docker pull` 补验边界**：private 阶段本机 token 无 `read:packages`，无法拉 private package（403）；翻转 public 后包公开可匿名拉取补验（命令 §7）。
5. **Docker 实跑（V4）留验**：本机 Docker Hub 不可达阻断本地 compose；真实镜像已由 GitHub Actions 侧构建推送验证（§4.5），本地 compose up 留 k3/翻转后实跑。
6. **Release 预构建数据包未在 T6 上传**（方案 D5「包由本批 T6 上传一次」）：Release 属 public 动作，private 阶段不适宜；翻转 public 后从旧开发库打包向量库（`~/.pf_agent/*.json`，~600MB）+ 数据分发包上传，README 已按可下载预构建数据包叙述，届时补上传即可。
7. **开发流同步约定待建**（D1「定期同步到新库」另行约定）：本批只做首发。旧库 `pf_agent`（私有，含全历史）继续开发；如何定期同步到新库 `pf-agent`（干净历史）——分支/PR 或 squash 同步机制，待用户与 k3 约定（建议：旧库起独立发布分支，squash 推送新库 main）。
8. **CI 卫生提示（非阻塞，建议下批顺手）**：agent-ci 中 `actions/setup-java@v4` 已 deprecated（提示迁 v5）；docker 三个 action 与 checkout 触发 Node20 deprecation 警告（GitHub 侧自动 fallback Node24，暂无影响）。数据侧 ci.yml 的 setup-python 同理。
9. **README badge**：T2 已从 README 移除数据侧 ci.yml 的 badge（避免纯净 clone 上误导）；agent-ci + docker GHCR 两 badge 指向新库 `ytche/pf-agent`。当前 private 阶段 badge 显示为占位，翻转 public 后即点亮。
