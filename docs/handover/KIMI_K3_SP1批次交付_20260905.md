## 2. 落地调整（相对方案/计划，k3 验收时请重点看）

T5 采用 TDD：先写边界测试，**暴露并修复了 T3 代码两个潜伏缺陷**（不在方案预测内，均不改变对外行为与检索语义）：

### 2.1 裁剪 seq 起点 bug：count ≠ max seq（`JdbcChatMemory.doAdd`）

- **原实现**：seq 从 `countByConversationId`（= 假定 seq 从 1 连续）起递增；裁剪删「seq ≤ toDelete（基于 count 的差值）」。
- **缺陷**（T5 边界测试 `trimStartsWhenExceedingHistoryRounds` / `trimAdvancesWindowOnFurtherAdds` 暴露）：一旦触发裁剪删掉最小 seq，count 就不再等于 max seq——
  1. 下一轮以 count 为 seq 起点会**复用已存在 seq 撞行**；
  2. 删除阈值基于 count 差，空洞下删不到最旧现存行，库内会**超 20 轮**。
- **修正**：seq 分配以 `findTopByConversationIdOrderBySeqDesc` 取真实 max seq 为起点；裁剪改**窗口制**——删 `seq ≤ (本次末 seq − 2*historyRounds)`，空洞下窗口仍从 seq 最旧侧推进，库内恒保留最近 20 轮。`ChatMessageRepository` 增 `findTopByConversationIdOrderBySeqDesc`。
- **验证**：21 轮后恰好 40 条、首条=第 2 轮；22 轮后仍 40 条、窗口推进到第 3 轮起（复用会致 >40，测试锁死）。

### 2.2 clear 依赖 DB 外键级联 → 显式删（`JdbcChatMemory.doClear`）

- **原实现**：`deleteById(conversation)`，消息靠 schema FK `ON DELETE CASCADE` 级联。
- **缺陷**（T5 评审发现）：`@DataJpaTest` 用 Hibernate 按实体建表（实体无对象关联，不生成 FK），clear 测试在 H2 会残留消息——「测试环境与生产 schema 不一致」。
- **修正**：clear 走同一 `TransactionTemplate` 事务，**先显式 `deleteByConversationId` 删消息、再删会话**；H2/PG 行为一致，schema 侧 CASCADE 仅作生产兜底。`ChatMessageRepository` 增 `deleteByConversationId`。

### 2.3 测试基建两处适配

- `JdbcChatMemoryTest` 加 `@DataJpaTest(properties = "spring.flyway.enabled=false")`：`@DataJpaTest` 默认仍激活 Flyway，会把 PG 方言 `V1__init.sql`（TIMESTAMPTZ 等）拿到 H2 跑而失败；关闭后由 Hibernate 按实体 create-drop 建表（表结构对齐靠 2.2 的解耦）。真实 V1 schema + PG 行为仍由 k3 的 V2 手工冒烟兜底（方案 §8 风险表已列）。
- `ChatMemoryAutoConfigurationTest` 的 Runner 补 `ApplicationConversionService` bean：Runner 不加载 Boot 自动配置，`AgentConfig.clientHttpRequestFactory` 的 `@Value "60s"→Duration` 无转换器会 UnsatisfiedDependency。
