## 三、发现的问题

### 1. 【P0 阻断】`@Lob` 与 V1 schema TEXT 类型冲突，jdbc 模式按文档配置无法启动

- **现象**：`pf.chat.memory=jdbc` + 方案注释态 yml 的 `ddl-auto: validate`（D7 指定形态）→ Hibernate 校验 `chat_message.content`：`@Lob String` 映射 CLOB → PG 侧期望 `oid` 列，而 `V1__init.sql` 建的是 `TEXT` → 启动即 `SchemaManagementException`。
- **为何单测没拦住**：`JdbcChatMemoryTest` 关闭 Flyway 后由 Hibernate create-drop 建表（H2 下 @Lob 自洽），测试库与生产 schema 天然不一致——正是方案 §8 预判的「H2 方言差异」风险，冒烟兜底生效。
- **为何运行时其实没错**：PG `text` 列用 setString 读写本无问题，错只在 validate 类型比对。若删掉 validate 反而能跑——但 D7 明确要 validate，不能靠绕。
- **修复要求**：去掉 `ChatMessageEntity.content` 的 `@Lob`（String↔text 类型码同为 VARCHAR，validate 通过；内容长度由 schema TEXT 保证）。**验收标准**：`ddl-auto=validate` 下 jdbc 模式正常启动。
- **附带肯定**：fail-fast 行为符合 D6——炸在启动、错误信息明确，不是静默降级。

### 2. 【P2 规范】方法排序红线 4 处违规（CLAUDE.md：静态同级优先、`@PostConstruct`/`@Test` 按访问级别参与排序）

| 文件 | 违规 |
|---|---|
| `memory/JdbcChatMemory.java` | `init()`（private @PostConstruct）排在 public 方法之前；`toMessage`/`toRole`（静态 private）排在 `doAdd`/`doClear`（private）之后 |
| `memory/JdbcChatMemoryTest.java` | `round()`（静态 private，L57）排在 9 个 @Test（package）之前 |
| `config/ChatMemoryAutoConfigurationTest.java` | `runner()`（private，L28）排在 @Test 之前 |

交付文档 §5 V5 自查「方法按访问级别排序 ✓」结论不实，下不为例。

波动归因（逐题比对 6 轮历史全量评测：baseline/baseline2/cp4/stage2/stage2_r2/本次）：

- **结构**：历史波动带 146~150（out_baseline 自身就是 146），本次 146 在带内；「≥2.96」闸口对应 148，属特定轮次读数而非硬回退。
- **诚实**：历史波动带 48~50，本次 47 略破下限，3 题失败逐题解剖：
  - `easy-2`（虹光法墙七色表）：历史 flaky（stage2_r1 亦败）。本次 LLM 明确答了「未能从检索结果中完整取得」——**诚实表态了，但用词不在评测器固定词表**（`HONEST_PHRASES` 仅 6 词，不含「未能」）→ 误判 0。评测器词表局限 + 模型波动，与 SP1 无关。
  - `easy-14` / `medium-26`：检索溯源均命中（1/1，sources 922/112 条），但 LLM 中途调 `reportDataGap` 后在最终答案自信作答、不承认缺口 → 按规则评 0。这是模型「报缺口却不认账」的行为不一致，发生在 SP1 改动面之外（prompt/工具/ChatService 全程零 diff）。
- **结论：V4 通过**。SP1 唯一可能波及的检索维度满分持平；诚实/结构波动均可归因到 LLM 随机性与评测器词表，与本批改动面无因果链。
- **登记观察项**（非本批修）：① LLM 报 gap 但最终答案不承认的行为不一致；② `HONEST_PHRASES` 词表过窄（漏「未能」类表述）。建议后续评测/prompt 批次统一处理。
