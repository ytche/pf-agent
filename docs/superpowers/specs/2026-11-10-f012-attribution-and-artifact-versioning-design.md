## 1. 背景与现有基础

F（功能想法）012 要解决的问题有两类：

1. 排障时把数据缺失、Java 消费偏离、检索错误和生成编造混为一谈，导致修错层。
2. 数据脚本或源文已改变，但产物、构建状态、Java 消费和文档没有同步，旧产物被误当成新结果。

现有机制已经覆盖大量版本复现需求：

- `build_manifest.json` 声明产物、输入、配置依赖、脚本和 schema；
- `build_state.json` 入库保存输入与产物指纹，产物本身继续 gitignored；
- `python3 -m vectorizer.build` 支持增量、强制重建、status 和 check；
- 类目 `cicd verify` 提供 pytest → pipeline → verify → 不变量的权威链；
- CI 已执行 `build all → build check`，从裸 checkout 重建产物再对账；
- DVG 已登记 Java 消费与数据侧产物偏离；
- `docs/WORKFLOW.md` 已有任务分级、评审和验收流程。

因此本项不新建版本平台，剩余工作是统一**四层归因、分阶段证据、提交原子性和消费闭环**。

## 2. 目标与非目标

### 2.1 目标

1. 用统一层级和证据链判断问题应修数据、消费、检索还是生成。
2. 允许登记时保留未知项，但定方案前必须完成分层排证，闭环必须证据完整。
3. 明确局部和共享层改动的重建范围，防止只读旧产物或只跑 check 误绿。
4. 让脚本、源文、manifest、build_state 和相关文档在同一提交中可追溯。
5. 区分 chunks 与独立 JSON 的 Java 消费同步方式，确保真实使用新产物。
6. 用轻量 WORKFLOW 规则和可复制模板落地，不增加常驻文档膨胀。

### 2.2 非目标

- 不引入 DVC、doit、数据库问题跟踪系统或第二套构建编排。
- 不把 `vectorizer/output/` 改为 git 入库。
- 不要求每个小改动都无差别全库重灌或全量重建。
- 不回写全部历史 KN；历史条目只在再次更新时补新口径。
- 不在规划、审计或总结过程中顺手修复新发现问题。
- 不新增运行时代码、数据库表或 CI 平台；若实施发现具体既有缺口，另立任务。

| 决策点 | 结论 |

## 4. 四层归因模型

| 层级 | 负责范围 | 典型例子 | 核心证据 |
|---|---|---|---|
| 数据层 | 源文、chunk 边界、元数据、独立清单产物 | 武僧清规未入 chunks；rule_version 缺失 | 源文位置、chunk_id、产物 diff、verify |
| 消费层 | Mapper、schema 兼容、向量库/JSON 加载与重灌 | 产物已修复但 store 未重灌；Java 漏读字段 | 产物与 store 对账、加载日志、DVG、真实读取 |
| 检索层 | 模块路由、召回排序、过滤、分页和工具决策 | 正确 chunk 排不进 topK；offset 失效 | 工具参数、tool_calls、候选排名、锚点 |
| 生成层 | 回答断言、引用、诚实性和展示 | 检索正确但模型顺带编造；来源标错 | 完整问答、检索上下文、回答与引用对照 |

### 4.1 主责层与因果链

- 每个问题指定一个主责层，同时记录跨层因果链，不强制只能选一层。
- 主责层决定主要修复位置；其他相关层分别写清需要的同步或验证动作。
- 例如“数据缺失 → store 未重灌 → 检索不到 → 回答缺项”，主责层是数据层，消费层必须重灌，检索与生成只需验证恢复。
- 例如“检索已包含正确原文 → 模型顺带补写未检索属性”，主责层是生成层；检索噪声若只是加重因素，不得改写成数据缺失。

### 4.2 环境因素

网络、Ollama、数据库等运行故障不另造第五层。按它直接破坏的环节归主层，并在原因中注明环境因素。例如 embedding 调用悬挂导致检索失败，主责层是检索层，原因记录 Ollama；向量库文件损坏导致消费失败，主责层是消费层。环境因素导致的产物或库损坏，修复与证据动作仍按第 6、7 节的对应类型执行；环境因素只影响归因说明，不改变 DVG、重建或重灌要求。

## 5. 分阶段证据门槛

### 5.1 登记时：最小字段

- 问题现象、期望与实际、复现方式；
- 疑似主责层，并明确标注“疑似”或“已证实”；
- 已有证据和未验证假设；
- 源文档链接、优先级和下一步。

登记时不要求全链路排证，但疑似原因不得写成已确认根因。

### 5.2 定方案前：分层排证

按实际链路列出：

```text
源文 → 数据产物 → Java 消费 → 检索工具 → 生成回答
```

逐项标记正常、异常、未验证及对应证据，最后确定：

- 主责层；
- 跨层因果链；
- 修复落点；
- 需要同步的消费和文档；
- 原问题的端到端验收方式。

禁止用生成提示词掩盖数据缺失，用数据重跑掩盖工具错误，或用重灌掩盖 Mapper/schema 不兼容。

### 5.3 闭环前：完整证据

- 修改文件与方案覆盖情况；
- 验证命令和真实结果，不只写“应该通过”；
- 产物重建、测试和指纹对账；
- Java 重灌或重启及真实消费验证；记录被测实例的端口/进程或加载标识，证明它已加载新产物；
- 原问题端到端复现；
- 源 KN/AKN/F/DVG、一期临时汇总和项目索引同批同步；
- 已知未覆盖点和新发现问题另行登记，不静默扩大本批范围。

## 6. 构建与提交规则

### 6.1 局部改动

局部源文、模块处理器或单 artifact 导出脚本变化时：

1. 先运行 `python3 -m vectorizer.build status`，以 stale 集合识别受影响 artifact；
2. 核对 manifest 的 inputs/config_deps/script 是否覆盖实际依赖；若语义上应有变化但 status 全 fresh，先按依赖漏配排查，不能据此跳过重建；
3. 重建受影响 artifact；
4. 运行对应 verify、聚焦测试及必要的模块回归；
5. 运行 `python3 -m vectorizer.build check` 对账；
6. 更新 build_state 和相关文档，与变更同提交。

`build check` 只证明当前产物与已有状态一致，不能替代重新生成。

### 6.2 共享层或影响面不清

共享处理层、公共依赖、指纹口径变化，或无法可靠界定影响面时：

```bash
python3 -m vectorizer.build all --force
python3 -m vectorizer.build check
```

同时：

- 补全 manifest 依赖登记，避免共享文件漏入指纹；
- 运行数据侧全量测试和受影响模块的真实回归；
- 不用“局部测试绿”替代共享层全量证据。

### 6.3 提交原子性

同一提交包含：

- 脚本、配置和源文变更；
- manifest 变更；
- 重建后的 `build_state.json`；
- 同批设计、问题状态和索引文档。

`vectorizer/output/` 继续 gitignored。CI 从裸 checkout 执行 `build all → build check`，验证该提交能重新生成并对账，不依赖本机旧产物。

## 7. Java 消费闭环

| 变更类型 | 必需动作 | 不应做的动作 |
|---|---|---|
| chunks 内容、边界或元数据变化 | 登记 DVG，重灌受影响向量库，核对条数/字段/锚点；重启或确认目标运行实例已加载新库，并在该实例上真实问答 | 只重灌文件或只重启就宣称新 chunks 已生效 |
| 独立清单 JSON 或 schema 变化 | 重启对应消费者，验证版本、计数和真实工具结果 | 无差别重算向量 embedding |
| Java Mapper/兼容逻辑变化 | Java 测试 + 数据读取对账 + 必要的重灌或兼容验证 | 用 Java 二次加工掩盖产物偏离 |
| 仅 Java 展示或工具逻辑变化 | Java 测试和真实调用 | 跑无关数据全量重建 |
| 仅文档变化 | 文档链接、口径和索引检查 | 无意义地重建数据或重灌 |

数据侧输出仍是 Java 侧输入的唯一事实源。任何重放、补丁或手工修库按 DVG 规则登记并给出清偿路径。

## 8. 规范与模板落地

### 8.1 文件

1. `docs/WORKFLOW.md`
   - 新增“问题归因与数据版本闭环”节；
   - 固定四层、证据阶段、构建范围、提交和消费规则；
   - 链接独立模板，不复制整份模板；
   - 将证据门槛映射到现有角色：architect（轻量任务为主 Agent）在方案中必填分层排证，coder 在提交说明中必填构建与消费证据，tester 必查原问题和实例验证，主 Agent 缺项即打回。轻量任务可简化角色链，但不豁免登记最小字段和闭环证据。

2. `docs/templates/问题归因与变更验收模板.md`
   - 提供可复制的登记、分层排证、修复、构建、消费和闭环六段；
   - 明确疑似/已证实、正常/异常/未验证等标记；
   - 提供验证命令与结果表、文档同步清单。

3. 根 `CLAUDE.md`
   - 只保留一条红线和上述文档指针，不加入模板全文。

4. `docs/项目文档总索引.md`
   - 登记 WORKFLOW 新节与模板入口。

### 8.2 登记事实源

KN/AKN 源登记库仍是问题事实源，模板只规定其条目格式，不生成另一份需要同步的独立问题实例：

- 新条目在 KN/AKN 正文内按模板六段填写；
- 不在 `docs/templates/` 下保存填好的问题实例；
- 设计、计划和测试报告作为独立证据文档链接到 KN/AKN，不替代条目状态；
- 一期临时汇总仍是查阅视图，条目状态、范围和下一步变化时继续与源 KN/AKN 同批更新。

### 8.3 模板示例

模板附两个短例，防止四层被机械套用：

- KN（数据侧已知）108（源条目 `KN108`，`pf_data/phase1/docs/已知问题记录.md`）：数据层主责，消费层重灌，检索和生成只做恢复验证；
- AKN（Agent已知）003（源条目 `AKN-003`，`docs/已知问题记录_agent.md`）：生成层主责，检索噪声只是加重因素，不记成数据缺失。

### 8.4 历史问题处理

- 不批量回写历史 KN。
- 新登记问题必须在 KN/AKN 条目正文使用模板。
- 现存问题下次更新时补齐主责层和证据链。
- 一期临时汇总与对应源文档继续同批更新，模板不能替代该同步规则。

## 9. 验收标准

1. WORKFLOW 与模板覆盖四层、主责层、因果链及三阶段证据门槛，并映射到 architect/coder/tester/主 Agent 或轻量任务对应角色。
2. 模板能分别指导数据、消费、检索和生成问题，不要求无关层跑无意义验证。
3. 局部/共享重建规则明确，status 用于识别影响面，check 不被描述成重建。
4. 提交原子性与 output gitignored 的表述无矛盾。
5. chunks 与独立 JSON 的消费动作区分明确，并验证实际加载新产物的实例。
6. 两个示例的归层与既有 KN108、AKN-003 结论一致，源条目路径可查。
7. KN/AKN 唯一事实源与模板的关系明确，不新增双源问题实例。
8. 根 CLAUDE 只增加短红线与指针，项目索引和一期源文档同步。
9. 文档链接和 Markdown 检查通过；本批不改 vectorizer 或源文，`build status` 不得因本批产生新的 stale。若执行 `build check`，结果应保持改动前值，不以它证明文档质量。
10. 本项为文档规范实施，不伪造运行时代码测试或真实问答证据。

## 10. 后续实施方案边界

本 spec 只固定设计，不代替实施计划。后续实施应保持轻量：

1. 编写独立模板和两个示例；
2. 更新 WORKFLOW、根 CLAUDE 指针和项目索引；
3. 同步 F（功能想法）012 源 TODO 与一期临时汇总；
4. 执行文档检查和现有构建链 check；
5. 如发现具体代码或 CI 缺陷，只登记并另立任务，不在本规范批次顺手修复。
