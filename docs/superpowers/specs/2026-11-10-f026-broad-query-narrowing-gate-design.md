## 1. 背景与现状

“CRB 里所有类型的规则条目”“CRB 所有专长”这类提问可能触发跨模块或单模块的大范围枚举，带来多轮工具调用、上下文增长、token 消耗和较长等待。

当前系统没有独立意图分类器，LLM 在 `ChatService` 的手动工具循环中自主决定是否检索。已有防线分别解决不同问题：

- `searchByMetadata` 无业务条件时直接拒绝；
- `listEntries` 无业务条件时返回内存统计概览；
- `enumeration-top-k=500` 限制每个向量库的元数据检索候选数；
- 工具轮次、上下文字符数和结果字符数提供后置兜底。

这些机制都没有在首次大查询前向用户提供收窄建议，也没有“用户确认后按原范围继续”的统一交互。

## 2. 目标与非目标

### 2.1 目标

1. LLM 在检索前识别可能产生较大查询量的问题，先返回可执行的收窄建议和示例。
2. 同时覆盖跨模块和单模块宽查询，不仅拦截绝对无条件查询。
3. 工具层对“无业务条件或仅来源书条件”提供确定性的最低护栏。
4. 用户明确确认后可按原范围查询，同一逻辑查询可继续分页。
5. 保持 500 条上限及 capped 诚实口径，不把门禁放行等同于无限量查询。
6. 持久化实际到达工具层的 BLOCKED/ALLOWED 事件，且遥测故障不影响主问答。

### 2.2 非目标

- 不新增独立前置 LLM 路由器或每次请求额外的分类模型调用。
- 不为判定大范围而先执行一次全量 count。
- 不新增八模块精确计数系统；数量概览只复用现有轻量能力。
- 不把 `vectorSearch`、`keywordSearch`、`getEntryById`、`getSpellList` 等点查或已有概览入口纳入新护栏。
- 不提高或取消 `enumeration-top-k=500`。
- 不做会话级永久放行、一次性确认令牌或前端按钮。
- 不持久化模型直接给出的提示词层建议，不新增建议工具。
- 不把门禁当作鉴权或安全边界。

## 3. 已确认的核心决策

| 决策点 | 结论 |
|---|---|
| 覆盖范围 | 跨模块和单模块宽查询都覆盖 |
| 判定依据 | 语义范围为主，现有轻量概览为辅，不先跑大查询验证 |
| 机制 | 提示词引导 + 工具护栏，沿用现有模型决策链 |
| 工具范围 | `searchByMetadata` + `listEntries` |
| 最低硬规则 | 无有效业务条件或仅来源书条件 |
| 首次明确全量要求 | 仍先建议一次；窄范围完整枚举不拦 |
| 建议内容 | 范围说明 + 2～4 个收窄示例 + 已有概览选项 + 原范围继续选项 |
| 放行方式 | 该逻辑查询的每次工具调用显式 `allowBroadQuery=true` |
| 翻页 | 业务条件不变的每页都携带；业务条件改变后重新判断 |
| 无条件查询 | 明确确认后允许执行无条件分页 |
| 500 上限 | 不变；capped 时不得宣称真实全量 |
| 事件 | 只持久化工具护栏 BLOCKED/ALLOWED |
| 事件降级 | 尽力写入，失败或 memory 模式不阻断主流程 |

## 4. 整体链路

1. 用户提问后，现有 LLM 决策链先判断查询范围，不新增前置分类模型。
2. 对宽问题，LLM 直接返回范围说明、收窄示例和后续选项，不先执行条目检索。
3. 对明确小范围问题，正常调用现有工具，不触发门禁。
4. 若 LLM 未提前收敛，两个目标工具对最低宽条件形态返回护栏提示，不执行条目检索。
5. 用户明确确认后，LLM 根据会话上下文为该逻辑查询设置 `allowBroadQuery=true`。
6. 同一业务条件的后续分页继续携带放行字段；改模块或业务过滤条件后重新判断。
7. 放行后按现有分页、结果字符预算和 capped 规则执行。
8. 首次建议不是数据缺失：不调用 `reportDataGap`，没有来源编号，不产生 `gapReported=true`。

会话记忆只保存用户问题与最终助手回答的既有机制不变。模型可依据前一轮建议和用户回复作出放行声明，服务端不保存“已确认”状态。

## 5. 语义判定与建议契约

### 5.1 应提前收敛的示例

- “CRB 里所有类型的规则条目。”
- “CRB 所有专长，完整列出，不要省略。”
- “把某本书里的装备全部列出来。”

即使用户首次就明确要求完整大清单，也先给一次建议。确认后继续是用户可选路径，不得直接拒绝全量需求。

### 5.2 不应仅因列举词而拦截的示例

- “武僧清规有哪些内容？”——具体主题，小集合。
- “女巫 1 环法术有哪些？”——职业和环级明确。
- “CRB 的火球术是什么？”——具体条目。
- “CRB 关于状态效果的规则有哪些？”——书和主题明确。

“全部 / 所有 / 有哪些”本身不是充分触发条件。`limit/offset/sort` 只是展示参数，不是业务收窄条件。

### 5.3 建议内容

首次建议应简短包含：

1. 为什么当前范围可能很大；
2. 2～4 个与原问题相关、可直接照抄的收窄示例；
3. 对已有轻量概览能力的模块，提供“先看看数量”的选择；
4. “仍按原范围查询”的明确选择。

示例必须形成有效业务收窄，不能只是把“所有类型”改成“所有专长”后再次落入同一个仅书护栏。

示例：

> 这个范围会覆盖多个模块，结果可能很大。你可以先试：
>
> ①“CRB 的战斗专长有哪些？”
>
> ②“CRB 的女巫 1 环法术有哪些？”
>
> ③“CRB 的肩部奇物有哪些？”
>
> ④“CRB 关于状态效果的规则有哪些？”
>
> 也可以说“查看专长/种族/装备数量概览”，或“仍按原范围查询”。

不自动查询数量。用户选择概览时只调用已有轻量概览；没有该能力的模块继续提供收窄示例，不用 500 上限内的 total 冒充真实总数。

## 6. 工具参数与放行矩阵

### 6.1 新字段

`MetadataSearchQuery` 和 `ListEntriesQuery` 新增可空布尔字段：

```text
allowBroadQuery
```

- null 或 false 均表示未放行；
- 不计入 `hasAnyCondition()`；
- 不是业务过滤条件；
- 只允许 LLM 在用户明确确认后为该逻辑查询设置 true；
- 同一业务条件的每页调用都携带，offset/limit/sort 可变化；
- module、book 或任一业务过滤条件变化后，不沿用旧确认。

`allowBroadQuery` 是模型根据对话作出的声明，不是服务端可验证的授权令牌。本批接受这一边界，以工具事件和端到端测试约束使用；500 上限仍是实际安全兜底。

### 6.2 行为矩阵

| 调用形态 | 未放行 | `allowBroadQuery=true` |
|---|---|---|
| 无业务条件 | metadata 返回收窄建议；listEntries 保持现有概览 | 两个工具都执行无条件分页查询 |
| 仅 `book/orFilters.book` | 两个工具都返回护栏建议，不检索条目 | 执行查询 |
| 书 + 主题/类别/职业等条件 | 工具硬护栏不拦截 | 执行查询 |
| 仅分页或排序参数 | 仍视为无业务条件 | 按无条件分页执行；仅传分页/排序而未放行不构成确认 |
| 非宽条件查询 | 正常执行，不记录门禁事件 | 正常执行，不记录门禁事件 |

“仅来源书”包括单书、多书 OR 以及只含书条件的组合。书与 keyword、主题、类别、职业、环级等任一有效业务条件组合后，不属于工具硬护栏的仅书形态；提示词层仍可根据完整问法判断它是否过宽。

listEntries 的非空白 keyword（包括 keyword-only）继续计为有效业务条件，工具层不按关键词长度猜测语义宽度。单字符或泛关键词可能仍然产生大结果集，由提示词层提前收敛；空白 keyword 沿用现有无效条件校验。本批接受工具层不拦截泛关键词的边界，不新增长度阈值。

### 6.3 无条件放行

为支持 metadata 的无条件放行，`SearchService` 需要显式支持“无用户过滤表达式”的查询路径，不能再把空条件直接跳过或构造空表达式。

新增的无条件路径必须保证跨页确定性：未显式指定排序时使用 `title → module → chunk_id` 升序及唯一键兜底；显式排序时也追加 `module → chunk_id` 作为同值兜底。该默认排序只约束新增无条件路径，不改写既有条件查询的默认顺序。

无条件放行只绕过交互门禁：

- 模块可用性不变；
- 现有全局过滤不变；
- 单库 `enumeration-top-k=500` 不变；
- 跨模块合并、去重和 capped 语义不变；
- 分页与结果字符预算不变。

因此“允许无条件查询”不等于“保证取得数据库真实全部条目”。达到 capped 时必须沿用“实际命中可能更多”的诚实提示。

## 7. 工具护栏建议

未放行的宽条件工具结果应向 LLM 明确说明：

- 未执行条目检索；
- 触发原因是 `no_conditions` 或 `book_only`；
- 可补充哪些类型的业务条件；
- 若用户已明确选择原范围继续，应使用 `allowBroadQuery=true` 重试；
- 不得把护栏结果描述为“查询无结果”或“数据缺失”。

`listEntries` 无业务条件且未放行时保持现有统计概览，不把概览误报成条目清单。仅书条件的 listEntries 调用则返回护栏建议，不执行条目搜索。

## 8. 持久化事件

### 8.1 范围

新增 `query_gate_event` 表和 V6 migration，只记录实际到达工具层的两类事件：

- `BLOCKED`：宽条件调用未放行，条目检索被拦截；
- `ALLOWED`：宽条件调用携带 `allowBroadQuery=true`，允许执行。

以下情况不记录该表事件：

- 模型直接给出的提示词层建议；
- 非宽条件的正常查询；
- 轻量概览；
- 未进入两个目标工具的问答。

因此该表衡量“工具层门禁”，不代表全部提示词层拦截，也不能单独用于计算所有建议的展示率。

### 8.2 字段

| 字段 | 含义 |
|---|---|
| `id` | 数据库生成的事件 ID |
| `created_at` | 事件时间 |
| `conversation_id` | 当前请求所在会话 ID |
| `question` | 当前请求级用户问题，采用 ToolCallTracker 口径；翻页时可能是“继续” |
| `tool_name` | `searchByMetadata` 或 `listEntries` |
| `module` | 当前模块或 all |
| `event_type` | BLOCKED / ALLOWED |
| `reason` | no_conditions / book_only |
| `query_json` | 当前查询参数 JSON，包含业务条件和 offset/limit/sort |

每次实际护栏判定记录一行。ALLOWED 的后续翻页也记录，分析时按会话、工具和 query_json 中的业务条件关联同一逻辑查询，不能假设 question 始终是最初的大范围问题。

不保存回答正文、来源快照或 LLM 完整上下文。

### 8.3 写入与降级

- 复用现有 telemetry 包、JDBC 条件装配、编程式事务和 `ObjectProvider` 风格。
- `ToolCallTracker` 新增当前请求上下文的只读 accessor，事件写入器从该 ThreadLocal 获取 conversation_id/question；不得让 LLM 在工具参数中伪造这两个字段。
- 工具在未执行 `begin()` 的单测、管理直调等场景没有请求上下文时跳过事件写入，主流程继续，不写空会话事件。
- JDBC 模式写 PostgreSQL；memory 模式没有持久化服务。
- 写入失败或未装配只记 WARN，建议、拦截、放行和查询主流程继续。
- 不向用户宣称事件已入库，不回退 JSONL，不增加第二存储路径。

## 9. 错误处理与边界

- 护栏结果不是空结果，不触发 `reportDataGap`。
- 放行字段缺失、null 或 false 都按未放行处理。
- 参数校验先于门禁判定；非法模块、未知过滤字段、空过滤值或非法分页参数按现有顺序返回，且不产生 BLOCKED/ALLOWED 事件。
- 放行字段不能修正上述非法输入，现有错误提示继续生效。
- 无条件放行不能绕过模块可用性和既有全局过滤。
- capped 时不得输出“已翻完真实全量”；沿用单库与跨模块各自正确的 capped 文案。
- 遥测失败不改变工具结果，也不把查询失败伪装成门禁事件。

## 10. 测试与验收

### 10.1 提示词与端到端行为

覆盖：

1. “CRB 里所有类型的规则条目”先给建议，首次响应前无条目检索；
2. “CRB 所有专长，完整列出”仍先建议；
3. 建议包含有效收窄示例、已有概览选项和原范围继续选项；
4. 用户回复“仍按原范围查询”后，工具携带放行参数执行；
5. “武僧清规有哪些”“女巫 1 环法术”“CRB 的火球术”等不触发门禁；
6. 放行后改问另一本书或改变业务条件，不沿用旧确认；
7. 首次建议无来源编号、无 `gapReported=true`，不虚构数量或查询结果。

### 10.2 工具与服务测试

覆盖：

- Jackson 对 `allowBroadQuery` 缺省、显式 false、显式 true 的三态反序列化；缺省必须为未放行；
- `allowBroadQuery` 不影响 `hasAnyCondition()`；
- 无条件、仅书、多书 OR、书 + 收窄条件、keyword-only、空白 keyword、仅分页/排序参数；
- metadata 与 listEntries 的未放行拦截；
- 两种工具的仅书放行和无条件放行；
- 同一条件多页携带放行，业务条件变化后重新判断；
- metadata 无用户过滤表达式时的真实服务路径及默认/显式排序的跨页稳定性；
- 未放行时查询服务不被调用；
- 500 上限、跨模块合并和 capped 文案零回归；
- 工具 schema 无悬空 `$ref`，现有非法参数校验不变。

既有测试按有意行为变更迁移，而不是作为意外失败处理：

- `ListEntriesQuery` record 构造器统一补新组件，普通旧行为用例传 null/false；
- 需要继续覆盖原仅书格式化与分页的用例显式传 true，未放行用例改断言护栏建议；
- metadata 无条件旧固定文案断言改为门禁建议断言；
- 禁止为保留旧断言而删除新门禁测试或跳过测试。

### 10.3 事件测试

覆盖：

- BLOCKED/ALLOWED 字段完整，reason 正确；
- 每次护栏判定一行，offset/limit 可用于区分翻页；
- 非宽查询、轻量概览、提示词层直接建议及参数校验失败无事件；
- 请求上下文来自 ToolCallTracker，未 begin 时跳过事件且主流程正常；
- JDBC 写入成功；
- memory 模式与写库异常只记 WARN，主流程结果不变；
- 不保存回答正文或来源快照。

### 10.4 回归与文档

- Java 全量测试通过，现有问答评测无不接受回归。
- 数据侧无需修改产物；若实施触及共享数据脚本，仍按同版本和构建检查规则执行。
- 闭环时同步 F-026、一期临时汇总、项目文档总索引、工具说明和数据库迁移说明。
- 不把 AKN-023 的性能优化顺带纳入；端到端可记录耗时作为观察，但不预设本功能一定降低所有问答延迟。

## 11. 后续实施方案应拆分的边界

本 spec 只固定设计，不代替实施计划。后续计划至少区分：

1. 查询参数、护栏判定和无条件查询路径；
2. 提示词引导、建议文案与放行对话；
3. V6 事件表、写入服务与降级；
4. 工具单测、事件测试、真实 Agent 场景和评测；
5. 文档同步与闭环。

实施不得把 F-025 的清单去重混入同一代码改动；两者只在端到端清单场景中共同回归。
