## 1. 问题

F-026 宽查询收窄门禁已上线，但放行完全由模型通过入参 `query.allowBroadQuery=true` 自行声明，
**服务端不保存也不校验任何放行状态**。`PromptBuilder` 仅以文字要求“改模块、改书需重新确认”。

实测：同会话先确认「CRB 所有类型的规则条目」宽查询，再改模块问「CRB 所有专长」，
2 次复跑中 1 次沿用放行直接执行、1 次正确重新建议；新会话首轮建议正确。

## 2. 已确认决策

| 决策点 | 结论 |
|---|---|
| 修法 | **服务端指纹校验**：放行状态由服务端记录与校验，不再依赖模型遵循提示词 |
| 指纹口径 | **只按 module + book**；同书同模块内增删其他过滤条件不再要求确认（用户明确选择，接受其放宽） |
| 状态存放 | **内存按 conversationId 存**，重启失效；生命周期随会话 |
| 校验失败 | **退回收窄建议**，响应与首次宽查询一致，由模型把建议转达用户；不引入新错误文案 |
| 验收 | 单测 + 真实模型同会话复现 3 次须 3/3 重新建议 + 53 题全量无回退 |

## 3. 实施要点

- 在宽查询门禁判定处（`BroadQueryGuard` / 相关工具入口）增加会话级放行记录：
  - 首次宽查询（无有效放行）→ 返回收窄建议，并记录该会话当前建议的 `module + book` 指纹。
  - 后续 `allowBroadQuery=true` 且指纹与记录一致 → 放行；同一条件的后续翻页同样放行。
  - 指纹不一致（换模块或换书）→ 忽略 `allowBroadQuery=true`，按首次宽查询退回收窄建议，并更新记录指纹。
- `limit`/`offset`/`sortBy`/`sortOrder`/`allowBroadQuery` 不参与指纹。
- 工具层需要能拿到当前 `conversationId`：若现有工具调用上下文未传递，需新增会话上下文传递机制
  （这是本项主要技术风险，实施前先确认可行路径，不得退化为全局单例状态）。
- V6 `query_gate_event` 增加“指纹不匹配被驳回”的可观测记录（沿用现有事件表，不新建表）。
- 会话删除/重启后的清理：内存记录随会话生命周期失效即可，不做持久化。

## 4. 不做

- 不做一次性放行令牌机制。
- 不把放行状态写入 PG 或 V7 快照。
- 不改 F-026 的建议文案与 500 上限。
- 不引入“条件变窄免确认”之外的额外规则（本项连变窄也不特殊处理，因为指纹只看 module + book）。

## 5. 验收

1. 单测：指纹匹配放行、换模块驳回、换书驳回、同条件翻页放行、无会话上下文时的行为。
2. 真实模型：同会话先确认宽查询再改模块提问，连跑 3 次须 3/3 重新给出收窄建议。
3. 53 题全量评测无回退。
